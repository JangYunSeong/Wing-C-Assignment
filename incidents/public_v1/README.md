# 공개 사례 v1 — 부서 결정적 사건 대용 [확정: 2026-11-03]

부서 결정적 사건(context.md §4.5)이 모이기 전까지 공통 과제의 **원리(심층 구조)·함정 재료**로 쓰는 공개 사례.
직군마다 기본 1건(`<직군>.json`). 공개 사후 분석·기술 블로그·논문을 **우리 말로 요약**하고 출처 URL 을 단다 (원문 복제 아님). 지원자 데이터 아님.

기능형 과제용 사례를 더 둘 수 있다 — `<직군>.<이름>.json` 에 `templates`(그 재료를 숨은 테스트로 시험할 수 있는 템플릿)를 적는다.
기능형 과제는 직군 템플릿이 시험할 수 있는 추가 사례를, 디버깅형(이슈형) 과제는 기본 사례를 쓴다 [확정: 2026-11-09 사용자 — 2건 허용 + 템플릿별 선택].
그런 추가 사례가 여럿이면 **공고 id 해시로 고정 배정**한다 — 같은 공고는 늘 같은 재료, 명세 `source_incident` 에 남아 승인자가 본다 [확정: 2026-11-09 사용자].
이미 만든 명세로 다시 돌릴 때는 명세의 `source_incident` 그대로 쓴다. 사례를 더하면 일부 공고의 배정이 바뀐다 (재료가 바뀌면 기능형 판 지문도 바뀌어 새 판).
예: 프론트엔드 기본 사례(여러 탭이 같은 로컬 DB 에 씀)는 실제 브라우저가 필요해 jsdom 템플릿으로 시험할 수 없어, 기능형은 추가 사례 3건
(`sw.frontend.stale-response`·`double-submit`·`optimistic-rollback` — 검색 응답 경쟁·중복 제출·낙관적 갱신 되돌리기) 중 해시 배정.
데이터 엔지니어 기본 사례(필터 없는 메타데이터 조회로 생성 파일 행이 중복돼 크기 상한을 넘고 전파 장애)는 배치 템플릿의 숨은 테스트 재료가 아니라, 기능형은 추가 사례
`data.eng.batch-rerun`(늦게 온 데이터·재실행·부분 출력 — Airflow Best Practices, 2026-11-09)을 쓴다 (`data/python-duckdb`).

| 필드 | 뜻 |
|---|---|
| `incident_id` | `pub:<직군>:<슬러그>` — 명세 `source_incident` 에 남는다 |
| `symptom` / `root_cause` | 겉 증상 / 실제 원인 |
| `naive_fix` / `why_naive_fails` | 흔한(AI 가 낼 법한) 처방 = 함정 후보 / 왜 틀리나 |
| `deep_structure` | 업종·소재를 바꿔도 유지할 원리 (과제 `invariant` 의 재료) |
| `surface` | 바꿀 수 있는 표면 |
| `avoid_terms` | 과제 어디에도 나오면 안 되는 고유어 (회사·제품·사건 이름) — 유명 사례라 알아보기 쉬움 |
| `hidden_terms` | 원인 기술 용어 — 지원자에게 보이는 제목·상황·제출물에만 금지 (승인자용 함정 설명엔 허용) |
| `accepted_fixes` | 정답으로 인정할 조치 — 함정·오답으로 쓰지 않는다. 흔한 처방과 겉이 같아도(예: 풀 크기 확대) 원인 근거가 있으면 정답. 형식은 아래 "accepted_fixes 형식" [제안: 2026-11-04 — 독립 검토 반영, 사례별 내용은 승인자 확정 전] |
| `source_literals` | 원문의 오류 문구·지표 값·고유 설정. 생성 입력에 넣지 않는다 (증상·원인·표면은 관계·일반식으로 요약). 과제에 2개 이상 함께 나오면 복사로 재요청. 흔한 작은 수 단독("50", "3")은 넣지 않고 맥락이 붙은 문자열로 ("backlog 50", "Linux 3.10") |
| `hypotheses` | 지원자가 세우고 자료로 기각해야 할 가설 (선택) |
| `templates` | 기능형 재료를 시험할 수 있는 템플릿 id (`frontend/react-vite-ts`) — 기본 사례가 아닌 추가 사례는 필수 |
| `task_pattern` | 과제 형태가 정해진 경우 (`qa_mutation`: 요구사항+모듈+허술한 테스트, 채점은 심은 결함 검출) |
| `verified` | 원문을 직접 열어 확인했는지. false 는 2차 요약으로만 확인 |
| `feature` | 기능 개발형(1단계 구현 → 2단계 디버깅) 재료 [2026-11-06 사용자 결정] — 아래 "feature 블록". 없으면 그 직군은 기능형 기본값 대상이 아님 |

accepted_fixes 형식 (생성 프롬프트에 `" / "` 로 이어 붙으므로 항목 안에 `" / "` 를 쓰지 않는다)
- `[태그] 조치 — 조건: … — 함정: …` — 조건·함정은 해당할 때만.
- 태그: `[복구]` 문제를 만드는 조건을 없앰 / `[재발 방지]` 다음 발생을 막음 (이것만 낸 답은 지금 장애를 풀지 못함) / `[진단]` 원인을 가르는 확인 절차 (흔한 처방과 겉이 같은 경우).
- `조건:` 정답으로 인정하는 데 필요한 근거·동반 조치. `함정:` 이 조치와 겉이 같지만 오답인 형태(단독·근거 없음 등).
- 흔한 처방(`naive_fix`)은 정답형과 겹치지 않게 "근거 없이 / ~만" 으로 한정한다.

feature 블록 (기능형 재료 — "어떤 기능을 만들 때 흔한 구현이 이 사고를 내는가")
| 필드 | 뜻 |
|---|---|
| `business_need` | 만들 기능과 업무 요구. **사고·증상·원인을 쓰지 않는다** — 1단계 상황은 이것만으로 쓴다 |
| `naive_impl` / `why_naive_breaks` | 공개 요구만 보고 짜는 흔한 구현 / 그 운영 조건에서 깨지는 이유 |
| `hidden_requirement` / `trigger` | 숨은 요구 / 흔한 구현을 깨는 운영 조건 (1단계 자료에서 보여야 함) |
| `discoverable_by` | 1단계에서 조건이 보이는 자료 종류 |
| `accepted_designs` | 설계 단계 정답. `accepted_fixes` 와 같은 형식, 태그 `[설계]`. 숨은 요구마다 2개 이상 |
| `stage2_symptom` / `stage2_evidence` / `stage2_cause_terms` | 배포 뒤 겉 증상(원인 없이) / 원인을 가르는 2단계 자료 종류 — **첫 항목이 핵심 증거**(배포 뒤에만 있는 자료, 1단계 자료에 같은 종류가 나오면 재요청) / 2단계에서 먼저 말할 원인 개념 |
| `leak_terms` | 1단계 지원자 화면·2단계 상황에 나오면 숨은 요구가 새는 말 (바꿔 쓴 표현도 사람이 적어 둔다) |
| `trigger_terms` | 운영 조건(`trigger`)을 드러내는 말과 흔한 바꿔 쓰기. 1단계 제목·상황·공개 요구·공개 수용 기준에 나오면 재요청 — 자료 본문·구체 답에는 써도 된다 (단서 자리). `leak_terms` 와 겹치지 않게, `business_need` 에 나온 말은 넣지 않는다 (공개된 업무 요구라 검사에서 빠짐). 프롬프트에는 들어가지 않는다 (검사 전용) [2026-11-06 사용자] |
| `task_shape` | code / analysis |
| `starter` | 검증된 시작 코드 예제 (`data/feature_starters/<id>`) — 없으면 명세만 |
| `reviewed` | 사람 검토 여부. false 면 명세 review_flags 에 남긴다 |
- 생성(`draft_feature_task` v2)은 숨은 요구·허용 설계·2단계 원인을 블록 그대로 쓰고 LLM 은 겉모습만 쓴다.
- 사례 지문(`incident_ref`)은 feature 를 빼고 계산한다 — 블록을 붙이거나 고쳐도 이슈형 판은 그대로. 기능형 판 키는 `feature_ref`.
- 행마다 조회(`sw.backend.n-plus-one`)는 `contract_needs` 에 `related_entities` 를 둔다 (2026-11-13) — 딸린 정보(고객 이름·상품 수)가 대상 테이블 칸·시드
  값으로 복사되면 그 칸만 읽어도 되어 숨은 요구가 사라진다 (2026-11-12 알파 계약). 응답에 필요한 모양은 계약 `response_shapes`(테이블 아님)에 둔다.

재료 인터페이스 `interfaces/<재료>.yaml` [확정: 2026-11-23 사용자, #256 1단계 — 데이터 재료만]
- 그 재료로 만드는 계약의 명령·입출력 파일·엔티티를 정한다 (`schemas.MaterialInterface`). 계약 계획 입력에 보이고, 코드가 계약에 채우며
  (`starter/interface.fit_interface`), 계약 검사가 그대로인지·밖의 명령·파일·엔티티가 없는지 본다. LLM 은 공개 테스트·숨은 케이스·조절값 근거만 쓴다.
- 데이터 과제는 숨은 요구를 시험하는 자리가 인터페이스 자체(입력 폴더·출력 파티션·실행 한 번의 범위)라 빌드마다 LLM 이 정하면 판정이 뒤집힌다
  (2026-11-18 알파). 손 구현을 이름 바꾸지 않고 돌리려면(#256 3단계) 칸 이름까지 같아야 해서 이름도 재료가 정한다.
- feature 블록(`FeatureSeed`)에 두지 않는다 — `FeatureSeed`·`PublicIncident` 는 인터뷰 프롬프트의 출력 스키마로 렌더돼, 칸을 더하면 그 프롬프트가 바뀐다.
- 값은 재료 `starter` 손 예시에서 옮긴다. 설명 글에 그 재료의 `trigger_terms`·`leak_terms`·`stage2_cause_terms`·`hidden_terms`·`avoid_terms` 를 쓰지 않고
  (공개 계약에 그대로 나간다 — 누설 검사는 고정 부분을 보지 않는다), 실행 한 번이 책임지는 범위를 공개 글로 정하지 않는다 (그 범위가 숨은 요구).
- refs(공개 요구·수용 기준 id)는 명세마다 달라 적지 않는다 — 계약에 채울 때 LLM 답에서 가져온다.
- 인터페이스가 없는 데이터 재료(회사 사례·인터뷰 재료)는 예전처럼 LLM 이 정하고 승인 화면에 "재료 인터페이스 없음" 을 남긴다.

쓰는 규칙
- draft_task 에는 원리·증상·원인·함정·인정할 조치·표면만 넣는다. 조직명·제목·URL·`notes` 는 넣지 않는다 (`notes` 는 큐레이터 메모 — 생성에 필요한 내용은 구조화 필드로 옮긴다).
- 과제가 원 사례의 오류 문구·수치를 그대로 쓰면 재요청한다 (`spec/draft.py` `incident_copied`). 검색 한 번이면 원 사례·정답이 나오기 때문.
- 사례 내용이 바뀌면 사례 지문(`incident_ref`)이 공통 과제 저장 키에 들어가 새 판을 만든다 — 이전 초안을 다시 쓰지 않는다.
- 소재·이름·수치는 공고 업종으로 바꾼다 (context.md §4.4). 원문 수치를 인용하지 않는다 — 생성 입력에 들어가는 필드(증상·원인·처방·단서·원리·표면·가설)에는 원문 수치를 두지 않고 `source_literals` 로 옮긴다.
- 명세 `review_flags` 에 "공개 사례 기반 — 부서 사례 아님" 을 남긴다. 부서 사례가 생기면 그쪽이 우선한다.
- feature 블록의 자료 종류 이름(`discoverable_by`·`stage2_evidence`)에는 그 재료의 `leak_terms`·`stage2_cause_terms` 를 쓰지 않는다 — 생성 모델이 이름을 자료 제목으로
  그대로 써서 늘 재요청에 걸린다 (2026-11-06 v5 비교에서 발견, 테스트 `test_seed_artifact_kinds_have_no_leak_terms`). 1단계 자료 종류 이름은 2단계 핵심 증거
  (`stage2_evidence` 첫 항목)와 낱말이 절반 넘게 겹치지 않게 짓는다 — 겹치면 1단계에 배포 뒤 증거가 섞여도 못 잡는다 (`stage2_kinds_in_stage1`).

검토 대기 [제안] (2026-11-04 독립 검토에서 확신 낮음 — 넣지 않음, 승인자 판단)
- sw.frontend: 탭마다 별도 저장소를 두기 — 저장소마다 작성자가 하나가 됨. 저장 공간·탭 간 일관성 대가를 밝히면 인정?
- sw.embedded: 공유 mutex 대신 메시지 큐로 넘겨 자원 공유 자체를 없애기.
- infra.network: 연결 보호 모드(SYN 보호) 끄기 — 공격 방어를 잃는 대가와 backlog 상향을 함께 밝히면 인정?
- sw.qa: `qa_mutation` 과제의 함정은 "심은 결함"이라 accepted_fixes 가 함정 판정에 거의 쓰이지 않는다 — 필드 의미가 다른 사례와 다름 (형식 정리 [미정]).
- data.ml: `verified: false` — 원문을 확인하면 accepted_fixes(특히 버전 고정)를 다시 본다.
