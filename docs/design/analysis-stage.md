# 기능 개발형 과제 — 문제 분석을 1단계에 합치기 설계 [제안]

> 상태: 설계 초안 (2026-11-13). 이슈 #151.
> 결정 표기는 온톨로지 레포와 같다 — `[확정]` / `[제안]` / `[미정]`.
> 관련: `docs/design/feature-task-backend.md`(기능형 과제, §4.3 두 단계·§10 "AI 없는 첫 단계"), `docs/design/spec-to-code.md`(README·계약),
> `docs/design/task-spec-schema.md`, `src/task_spec/schemas/domain.py`(`Clarification`·`DebugStage`), `src/task_spec/starter/{facilitator,render}.py`.

## 0. 요약

- 기능형 과제 **1단계를 "분석 + 구현"으로 바꾼다**. 지원자는 정해진 요구 사항 대신 **모호한 업무 요청**을 받고, 구현하면서 요청자(진행자)에게
  묻고 자료를 열어 요구를 파악한다. 따로 떼어 낸 분석 단계(0단계)는 두지 않는다 [확정: 2026-11-13 사용자].
- 단계는 지금처럼 둘이다: **1단계 분석·구현 40분 → 2단계 디버깅 20분** (총 60분, `FEATURE_BUILD_MIN, FEATURE_DEBUG_MIN` 그대로).
  분석에 얼마를 쓸지는 지원자가 정한다.
- 공식 요구 사항·공개 수용 기준은 README 에 싣지 않고 **물어야 알 수 있는 요청자 지식**으로 둔다. 계약(API·화면·명령 형식)과 시작 코드는 지금처럼 처음부터 준다.
- 응시 화면의 대화는 **두 채널로 나뉜다** [확정: 2026-11-13 사용자 — 응시 화면 "AI 도우미" 패널]: **AI에게**(코드 설명·수정·테스트 작성 — 코드 생성만)와
  **진행자에게**(요구 사항 질문). **요구는 진행자에게 물을 때만 열린다** — AI 도우미는 요청자 지식을 모른다 (§4.5).
- 생성 순서는 **명세를 먼저 다 만들고 → 그것을 흐려 요청 글을 만든다** (§5). 요청자 답은 **승인된 문장 중에서 고르기만** 한다.
- **질문·자료 요청 횟수 한도를 두지 않는다** — 1·2단계 모두 [확정: 2026-11-13 사용자]. 횟수 대신 무엇을·언제·얼마나 정확히 묻고 열었는지를 채점한다 (§4.4).
- 분석 결과는 1단계 제출물의 **문제 정의 메모**로 낸다 (지금 "설계 메모"를 넓힘). 별도 제출·공개 관문은 없다.

이력: #151 처음 안은 "요구 항목을 감췄다가 질문하면 연다", 다음 안은 "0단계 분석 → 제출하면 공식 요구 공개 → 1단계 구현"이었다.
0단계를 따로 두면 시간을 나눠야 하고(15/35/20 등) 빈 정의서를 내고 넘어가는 길이 생겨, 0·1단계를 합쳤다.

## 1. 왜 필요한가

- 지금 README 에는 제목·상황·**요구 사항·공개 수용 기준**·계약·제출물이 처음부터 다 보인다. 지원자는 "무엇을 만들지"가 정해진 상태에서 시작한다.
  실무 요청은 대개 그렇게 정해져 오지 않는다 — 무엇이 문제인지 묻고 정의하는 것이 경력자를 가르는 지점이다.
- 기능 구현은 코딩 AI 가 가장 잘하는 일이라 AI 대리 풀이 위험이 크다 (`feature-task-backend.md` §0). AI 는 묻지 않고 그럴듯하게 가정해 구현하는 경향이 있어,
  "무엇을 물어야 하는가"를 과제 안에 넣으면 판별력이 생길 수 있다 — 평가로 확인한다 (§9).
- 이슈형(incident)은 원래 "모호한 증상 → 원인 분석"이다. 기능형 1단계에 같은 성격을 넣는 셈이다.

## 2. 범위

| 포함 | 제외 |
|---|---|
| 기능형(`task_kind=feature`) 공통 과제 1단계의 요청 글·요청자 지식·채점 기준 | 이슈형 (이미 분석형) |
| 요청 글 생성 프롬프트·누출 검사·승인 화면 표시 | 확장 슬롯·경험 검증 과제 (지금 그대로) |
| README 템플릿 새 판(요구 절 → 요청 글), 진행자 묶음(`FacilitatorView`) | 대화 진행·제출 수집 (응시 플랫폼 몫) |
| 평가 (AI 단독 풀이로 판별력 확인) | 메모 실제 채점 실행 위치 — §7, [미정] |

## 3. 흐름

```
1단계 분석·구현 (40분)   요청 글 + 계약 + 시작 코드
                         → 요청자에게 질문·자료 요청 (한도 없음, 언제든)
                         → 구현 · 테스트 · 문제 정의 메모 제출
      ↓ reveal_after: stage1_submitted
2단계 디버깅 (20분)      지금 debug_stage 그대로 (자료 한도 없음)
```

| | 1단계 분석·구현 | 2단계 디버깅 |
|---|---|---|
| 보이는 것 | 요청 글, 계약, 시작 코드, 자료 제목 목록, 제출물 | `debug_stage.scenario` 등 (지금 그대로) |
| 진행자에게 물으면 주는 것 | 요청자 지식(§4.2): 공식 요구·공개 수용 기준·추가 요구 · 1단계 자료 | 2단계 자료 |
| AI에게 | 코드 설명·수정·테스트 작성만 — 요구는 모른다 (§4.5) | 같음 |
| 숨긴 것 | 숨은 요구·숨김 수용 기준·허용 설계 | 증상의 원인 |
| 산출물 | 핵심 구현·테스트·**문제 정의 메모** | 진단·수정 |

## 4. 1단계 구조

### 4.1 요청 글 (`request`)

- README 의 "상황·요구 사항·공개 수용 기준" 자리를 대신한다. 요청자(가상 기획자·운영 담당) 말투의 짧은 업무 요청 300자 안팎,
  재료 `business_need` 수준의 "무엇이 필요한가"만 쓴다.
- **쓰지 않는 것**: 공개 수용 기준 문장, 수치(수량·요청량·시간 조건), 운영 조건(`trigger_terms`), 숨은 요구 핵심어(`leak_terms`·`first_mention_of` 개념), 구현 방법.
- 공식 요구(`requirements`) 중 일부만 흐리게 담는다 — 다 담으면 분석할 것이 없고, 하나도 안 담으면 무엇을 물을지 실마리가 없다. 기준은 §5 검사.
- 진행 안내(요청자에게 물을 수 있음, 자료 목록, 제출물)는 코드가 README "진행 방식"에 붙인다 (`process_markdown`).

### 4.2 요청자 지식 (`facts`) — 물으면 주는 답

| 칸 | 내용 |
|---|---|
| `fact_id` | `f1`… |
| `covers` | 이 사실이 드러내는 명세 항목 id — `r#`(공식 요구) · `ac#`(공개 수용 기준) |
| `topic` · `match_terms` · `answer` · `answer_hint` | 지금 `Clarification` 과 같은 두 층 답 규칙 [확정: 2026-11-06 사용자] — 고르기만, 문장 안 바꿈 |

- 공식 요구·공개 수용 기준마다 그것을 덮는 사실이 하나 이상 있어야 한다 — 물어서 알 수 없는 요구로 채점하면 안 된다.
- 추가 요구(`c#`, 함정 단서)는 지금 `clarifications` 그대로 같은 대화에서 쓴다.
- 자료는 지금 1단계 자료(`artifacts`) 그대로, 요청하면 공개.

### 4.3 문제 정의 메모 (1단계 제출물)

지금 기능형 제출물의 "설계 메모(결정·근거·AI 에 맡긴 것)"를 넓힌다. 양식은 고정, 내용은 자유:

1. 해결할 문제 (누구의 무엇)
2. 범위 — 하는 것 / 하지 않는 것
3. 가정 — 확인하지 못해 가정한 것
4. 위험·엣지 케이스
5. 설계 결정과 근거
6. AI 에 맡긴 것과 확인한 방법

따로 먼저 내는 관문은 없다 — 구현과 함께 낸다.

### 4.4 한도 없음 [확정: 2026-11-13 사용자]

질문 횟수(`max_clarifications`·요청자 질문)와 자료 요청 횟수(`max_requests`·`debug_stage.max_requests`)에 **한도를 두지 않는다**. 상한은 제한 시간이다.

- 왜: 재려는 것은 "무엇을 물어야 하는가"다. 횟수를 막으면 아끼는 요령을 재게 된다. 실무에도 질문·자료 열람 횟수 제한은 없다.
- 잃는 것과 대응:

| 한도가 하던 일 | 한도 없이 대신 하는 것 |
|---|---|
| 자료를 골라야 하게 함 — '자료 전부 제공' 과제는 AI 단독 풀이에 풀렸다 (스키마 결정 표 2026-11-03) | 자료 열람 **순서·시각**을 기록해 채점: 단서(key) 자료를 언제 열었는지, 방해(distractor) 자료에 기대 결정했는지, 메모에 연 자료를 근거로 썼는지 |
| 키워드 뿌리기 방지 — 질문을 낱말만 바꿔 계속 보내면 구체 답(`match_terms`)이 다 열림 | **질문 하나에 사실 하나만** 답한다. "무엇을 물을 수 있나"·주제 나열 질문은 답하지 않는다. 같은 사실을 다시 물으면 같은 답 |
| 질문을 고르게 함 | 채점이 **질문 적중률**(사실에 닿은 질문 / 전체), 먼저 물은 것, 반복을 본다 |

- 질문·자료 요청은 **전부 시각과 함께 기록**한다. 관찰 종류는 지금 것(`asks_clarification`·`requests_artifact`·`catches_trap`·`first_mention_of`)에
  요청자 지식 질문 `asks_fact`(f#) 를 더할지, `asks_clarification` 의 값 공간을 넓힐지 [미정].
- 효과는 평가로 확인한다 (§9): "닥치는 대로 묻고 다 여는" AI 전략이 수준 5에 닿으면 한도 없음을 다시 본다.
- 응시 화면의 지금 안내("진행자 질문은 최대 2번", "진행자 질문 2/2")는 한도 없음에 맞춰 바꿔야 한다 — 응시 화면 담당 몫.

### 4.5 두 대화 채널 — AI에게 / 진행자에게 [확정: 2026-11-13 사용자]

응시 화면 "AI 도우미" 패널은 대화 상대를 고르게 되어 있다.

| | AI에게 | 진행자에게 |
|---|---|---|
| 하는 일 | 코드 설명·수정·테스트 작성. 수정한 코드는 에디터에 바로 반영 | 요구 사항 질문에 답 — 요청자 지식(`facts`)·추가 요구(`clarifications`)·자료 |
| 답 만드는 법 | 코딩 모델 생성 | **승인된 문장에서 고르기만** (§4.2, 결정적) |
| 아는 것 | 지원자에게 보이는 것(요청 글·계약·시작 코드·지원자 코드)과 지원자가 대화에 붙여 넣은 것만 | 명세의 진행자 보기(`FacilitatorView`) |
| 모르는 것 | 요청자 지식·추가 요구·열지 않은 자료·숨은 요구 전부 | 숨은 요구·허용 설계·`covers`·`reveals` |
| 한도 | [미정] — 응시 플랫폼 정책 | 없음 (§4.4) |

- **요구는 진행자에게 물을 때만 열린다.** AI 도우미에 요구 칸을 넣지 않는다 — 넣으면 지원자가 AI 에게 "요구 다 알려 줘"로 분석을 건너뛴다.
- 지원자가 AI 에게 요구를 묻거나, 요구가 다 열리지 않은 채로 AI 에게 구현을 맡기면 AI 는 요구를 모른다.
  **AI 는 보통 코딩 AI 처럼 그럴듯하게 가정해 답하고 구현한다 (b)** [확정: 2026-11-13 사용자].
  버린 안 (a) "업무 요구는 진행자에게 확인하세요"로 돌려보냄 — 공정하지만 AI 의 가정을 검증하는지(`ai_axes` verification)를 못 본다.
- 두 채널 기록 모두 시각과 함께 남긴다. AI 채널 기록은 `ai_axes`(delegation·verification) 근거, 진행자 채널 기록은 분석 근거.

#### 요구가 다 열리지 않은 상태에서 AI 가 구현할 때 (b) [제안]

1. **AI 도우미 지시는 중립으로 둔다.** 코딩 도우미 역할과 지원자에게 보이는 것(요청 글·계약·시작 코드·지원자 코드)만 준다.
   "요구를 지어내라"도, "요구를 모르니 경고하라"도 넣지 않는다 — 일부러 틀리게 하지도, 일부러 도와주지도 않는다.
   그러면 AI 는 흔한 코딩 모델처럼 빈 요구를 흔한 가정으로 채운다 (가정을 말할 때도, 말하지 않을 때도 있다 — 그것도 실무와 같다).
2. **모든 지원자가 같은 AI 를 쓴다.** 모델·버전·설정·지시문 판을 공고 과제 판마다 고정하고 기록한다 (provenance). AI 답 자체는 지원자마다 달라질 수 있으므로
   AI 출력이 아니라 **지원자가 그것을 확인했는지**를 채점한다.
3. **AI 출력을 기록한다.** 질문·답·코드 변경(에디터 반영분)을 시각과 함께. 채점 때 "AI 가 가정해 만든 요구"를 찾는 근거.
4. **채점 — 한 증거는 한 곳에서만 깎는다.** AI 가 가정해 구현한 요구를 지원자가 확인 없이 둔 경우:
   - 그 요구는 §7.1 표에서 "묻지 않음" 행으로 센다 (가정이 맞으면 메모에 적었는지에 따라 인정/분석 점수 없음, 틀리면 분석 문제).
   - `ai_axes` verification 은 **확인한 경우의 가점**으로만 쓴다 — AI 가정을 진행자에게 확인했거나, 메모 "AI 에 맡긴 것과 확인한 방법"에 적은 경우.
     같은 누락을 분석과 verification 에서 두 번 깎지 않는다.
5. AI 도우미 지시문은 응시 플랫폼 쪽에 있다. 지시문 판이 바뀌면 같은 공고 지원자 간 비교가 깨지므로, 바꾸는 시점을 공통 과제 판과 맞추는 규칙을 응시 플랫폼과 정한다 [미정].

## 5. 생성 흐름

```
draft_spec (지금 그대로 — 요구·공개 기준·함정·추가 요구·자료)
   → draft_analysis_request   요청 글 + 요청자 지식 (새 프롬프트)
   → 검사 (아래) — 어긋나면 사유 붙여 1회 재요청, 그래도면 review_flags
   → approval (요청 글·요청자 지식도 승인 대상, 불변식 9)
   → 빌드: 계약·시작 코드·README (요청 글 판 템플릿)
```

- 새 과제 `prompts/draft_analysis_request/v1.md` — 시작 코드 생성기가 아니므로 평가 뒤 `CURRENT` (불변식 7). 모델은 `opencode:qwen3.8-flash` 로 시작.
- 입력: 기능형 과제의 공개 칸(제목·상황·요구·공개 수용 기준), 추가 요구, 재료 `business_need`. **숨은 요구·허용 설계는 넣지 않는다**.
- 계산할 수 있는 칸(id 번호·`covers` 대조·진행 안내)은 코드가 채운다 (`draft_feature_task` v4 와 같은 원칙).
- 검사 [제안]:
  - 결정적: 요청 글에 `trigger_terms`·`leak_terms`·`first_mention_of` 개념·숫자 없음 / 공개 수용 기준 문장과 겹침 낮음 /
    모든 `r#`·`ac#` 가 어떤 사실의 `covers` 에 있음 / 사실 답에 숨은 요구 핵심어 없음 (`check_hints` 재사용).
  - 흐림 정도: 요청 글이 직접 말하는 `r#` 비율 — 너무 높으면·0 이면 재요청. 1차 낱말 겹침, 2차 판정 LLM [미정: 기준값].
  - **계약 누출**: 요구를 README 에서 뺐으므로 계약이 요구를 대신 말하면 안 된다 — 응답 상태 값(예: `SOLD_OUT`)·오류 코드·화면 요소 test id·문구·
    배경 요청이 공식 요구나 숨은 요구를 드러내는지 본다. 프론트는 계약이 화면 요소까지 담아 더 크다 (#151 댓글). 처리 방법 [미정]:
    중립적 이름으로 계약에 둠 / 계약에서 드러나는 요구는 처음부터 공개 요구로 둠.
- 공통 과제는 공고 단위로 한 번 만들고 저장소(`CommonRef`)를 재사용하므로, 요청 글도 공통 과제 판의 일부로 같이 저장·재사용된다.

## 6. 스키마·템플릿 초안 [제안]

`TaskItem` 에 다음을 더한다 — 기능형 전용(`FEATURE_FIELDS`), 예전 판·이슈형은 비어 있음 (하위 호환).

```yaml
request: "<요청 글>"                       # 있으면 README 의 상황·요구·공개 수용 기준 자리를 대신함
facts: [{fact_id, covers: [r#|ac#], topic, match_terms, answer, answer_hint}]
# max_clarifications · max_requests · debug_stage.max_requests → None (한도 없음, §4.4)
```

- 지금 `max_clarifications` 는 1~6 필수라 `None` 을 허용하게 바꾼다 (`DebugStage.max_requests`·`FacilitatorView` 의 `max_questions`·`max_requests` 는 이미 `None` 을 받는다).
- README 템플릿은 스택마다 **새 판**(`templates/<stack>/vN+1/README.tpl.md`)으로: "요구 사항"·"공개 수용 기준" 절 대신 "요청" 절. 계약·코드 구조·실행·채점 방법 절은 그대로.
  "진행 방식"(`process_markdown`)에서 한도 문장을 빼고 "요청자에게 물어 요구를 확인한다"를 넣는다. 공개 테스트 목록은 싣지 않는다 (공개 수용 기준을 드러내므로).
- 이 문서가 확정되면 `docs/design/task-spec-schema.md` + `schemas/domain.py` 를 같은 PR 에서 고친다 (스키마 SSOT 규칙).

## 7. 채점 (Evidence model)

### 7.1 요구별 칸 나누기 — 이중 감점 막기

요구를 물어야 알 수 있으므로, 공식 요구마다 "알았나 × 만들었나"로 한 칸에 넣고 **한 번만** 깎는다.

| | 테스트 통과 | 테스트 실패 |
|---|---|---|
| 물어서 앎 (사실 열림) | 정상 | 구현 문제 |
| 묻지 않음, 메모에 가정으로 적음 | 가정이 맞음 — 인정 | 분석 문제 (가정이 틀림) |
| 묻지 않음, 메모에도 없음 | 우연히 맞음 — 분석 점수 없음 | 분석 문제 |

- 질문 한도가 없으므로 모든 요구는 물으면 알 수 있다 — 몰라서 못 만든 것은 분석 문제로 본다.
- 숨은 요구(t#)는 지금 기능형 채점 그대로 (`catches_trap`, 숨김 수용 기준, 허용 설계).

### 7.2 문제 정의 메모

| 본다 | 근거 |
|---|---|
| 공식 요구·공개 수용 기준을 얼마나 짚었나 | `r#`·`ac#` ↔ 메모 문장 |
| 숨은 요구를 위험으로 짚었나 | `t#` ↔ "위험·엣지 케이스" 칸 |
| 가정을 드러냈나, 물어서 확인했나 | "가정" 칸 · 대화 로그 |
| 잘 물었나·잘 골랐나 (한도 없음의 대신) | 질문 적중률·먼저 물은 것·반복, 단서 자료를 연 시점, 방해 자료에 기댄 결정 (§4.4) |
| AI 가정을 확인했나 (§4.5, 가점만) | AI 채널에서 나온 요구 가정 ↔ 진행자에게 확인한 질문 · 메모 "AI 에 맡긴 것과 확인한 방법" 칸 |

수준 기준 예 [제안] (근거 수행준거 id 필수 — 지금 규칙):
- 1: 요청 글만 보고 구현. 질문이 없거나 요청 글에 있는 것만 묻는다.
- 3: 공식 요구 대부분을 물어 확인하고 가정을 적는다. 숨은 요구는 못 짚는다.
- 5: 숨은 요구 하나 이상을 위험으로 짚고, 질문으로 확인하거나 확인 못 했음을 가정으로 남겨 구현에 반영한다.

채점 방식 [제안]: 메모 ↔ 명세 id 대조는 LLM 1차(**id 목록과 인용만** 출력, provenance 기록) + 사람 최종 판단 (고영향 AI).
지원자 메모·질문은 지원자 데이터다 — 외부 LLM 으로 보내기 전 개인정보 거르기 필요 (불변식 2 취지). 채점을 P1 과 응시 플랫폼 중 어디서 돌릴지 [미정].

## 8. 진행자·승인 화면

- `FacilitatorView.stage1` 에 `request`·`facts` 를 더한다 (두 층 답 규칙 그대로 — `ANSWER_RULE`). `covers` 는 진행자에게 주지 않는다
  (지금 `reveals` 를 빼는 것과 같은 원칙). 한도는 `None`, 규칙에 "질문 하나에 사실 하나, 나열 질문은 답하지 않음, 모든 질문·자료 요청을 시각과 함께 기록"을 더한다.
- AI 도우미(코딩 모델)에는 진행자 보기를 넘기지 않는다 — 지원자에게 보이는 것만 (§4.5). 응시 플랫폼과 이 경계를 문서로 맞춘다.
- 판정 방식은 지금 키워드(`match_terms`) 매칭 유지 [제안]. 키워드 + LLM 보조(사실 id 선택만, temperature 0, 판정 근거 기록)는
  응시 플랫폼과 재현성 기준(같은 질문 → 같은 사실 비율)을 정한 뒤 [미정].
- 승인 화면: 기능형 카드에 요청 글 ↔ 공식 요구를 나란히, 요청 글이 직접 말한 `r#` 표시(흐림 정도), 요청자 지식(사실 → `covers`), 계약 누출 검사 결과.
