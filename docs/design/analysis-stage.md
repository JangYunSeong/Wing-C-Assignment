## 0. 요약

- 기능형 과제 **1단계를 "분석 + 구현"으로 바꾼다**. 지원자는 정해진 요구 사항 대신 **모호한 업무 요청**을 받고, 구현하면서 진행자에게
  묻고 자료를 열어 요구를 파악한다. 따로 떼어 낸 분석 단계(0단계)는 두지 않는다 [확정: 2026-11-13 사용자].
- 단계는 지금처럼 둘이다: **1단계 분석·구현 40분 → 2단계 디버깅 20분** (총 60분, `FEATURE_BUILD_MIN, FEATURE_DEBUG_MIN` 그대로).
- 공식 요구 사항·공개 수용 기준은 README 에 싣지 않고 **물어야 알 수 있는 요청자 지식**으로 둔다.
- **계약은 모양만, 규칙은 물어서, 채점은 행동으로** (§5.2, B1) [확정: 2026-11-13 사용자 — 손 시범으로 확인할 설계, 백엔드·데이터만]: 계약에는 경로·필드·상태 이름만,
  업무 규칙 위반은 공통 거절 하나, 공개 테스트는 사유 값이 아니라 행동(거절됐나·그 뒤 조회 결과)을 본다.
- 응시 화면 대화는 **두 채널** [확정: 2026-11-13 사용자]: **AI에게**(코드만, 요구 모름 — 그럴듯하게 가정 (b) [확정])와 **진행자에게**(요구 질문).
  **진행자는 프로그램**이다 [확정: 2026-11-13 사용자] — 정해진 규칙으로 승인된 문장을 고른다 (§4.6).
- **질문·자료 요청 횟수 한도를 두지 않는다** — 1·2단계 모두 [확정: 2026-11-13 사용자]. 횟수 대신 무엇을·언제·얼마나 정확히 묻고 열었는지를 채점한다.
- 생성 순서는 **명세를 먼저 다 만들고 → 흐려 요청 글을 만든다**. 계약 관련 검사는 **빌드 단계**에서 한다 (계약은 명세 승인 뒤에 생긴다).
- **구현 전에 손 시범으로 판별력부터 본다** (§9.1). 시범 판정에 따라 멈추거나 보완한다 (B1 포함).

## 1. 왜 필요한가

- 지금 README 에는 제목·상황·**요구 사항·공개 수용 기준**·계약·제출물이 처음부터 다 보인다. 지원자는 "무엇을 만들지"가 정해진 상태에서 시작한다.
  실무 요청은 대개 그렇게 정해져 오지 않는다 — 무엇이 문제인지 묻고 정의하는 것이 경력자를 가르는 지점이다.
- 기능 구현은 코딩 AI 가 가장 잘하는 일이라 AI 대리 풀이 위험이 크다 (`feature-task-backend.md` §0). AI 는 묻지 않고 그럴듯하게 가정해 구현하는 경향이 있어,
  "무엇을 물어야 하는가"를 과제 안에 넣으면 판별력이 생길 수 있다 — 손 시범(§9.1)으로 먼저 확인한다.
- 이슈형(incident)은 원래 "모호한 증상 → 원인 분석"이다. 기능형 1단계에 같은 성격을 넣는 셈이다.

## 2. 범위

| 포함 | 제외 |
|---|---|
| 기능형(`task_kind=feature`) 공통 과제 1단계의 요청 글·요청자 지식·채점 기준 | 이슈형 (이미 분석형) |
| 요청 글 생성·명세 쪽 검사·명세 승인 화면 | 확장 슬롯·경험 검증 과제 (지금 그대로) |
| 빌드 쪽: 얇은 계약(B1)·행동 판정 공개 테스트·단언 값 검사·테스트를 보지 않는 구현·빌드 승인 표시 | 대화 화면·제출 수집 (응시 플랫폼 몫) |
| README 템플릿 새 판, 진행자 보기·답 규칙, 평가 키트 | 메모 실제 채점 실행 위치 — §7, [미정] |
| 손 시범 → 빌드 알파 → 본 평가 | |

스택: **B1(얇은 계약·행동 판정)은 백엔드·데이터만** [확정: 2026-11-13 사용자]. 프론트는 테스트가 화면 요소를 test id·문구로 찾아야 해서 요소 이름이 계약에 보여야 하므로,
**요소가 필요 없는 규칙(입력 검증·순서·상태)만 묻게** 따로 둔다 (§5.6).

## 3. 흐름

```
1단계 분석·구현 (40분)   요청 글 + 계약(모양) + 시작 코드
                         → 진행자에게 질문·자료 요청 (한도 없음, 언제든)
                         → 구현 · 테스트 · 문제 정의 메모 제출
      ↓ reveal_after: stage1_submitted
2단계 디버깅 (20분)      지금 debug_stage 그대로 (자료 한도 없음)
```

| | 1단계 분석·구현 | 2단계 디버깅 |
|---|---|---|
| 보이는 것 | 요청 글, 계약(모양), 시작 코드, 자료 제목 목록, 제출물 | `debug_stage.scenario` 등 (지금 그대로) |
| 진행자에게 물으면 주는 것 | 요청자 지식(§4.2): 공식 요구·공개 수용 기준·사유 값 · 추가 요구 · 1단계 자료 | 2단계 자료 |
| AI에게 | 코드 설명·수정·테스트 작성만 — 요구는 모른다 (§4.5) | 같음 |
| 숨긴 것 | 숨은 요구·숨김 수용 기준·허용 설계 | 증상의 원인 |
| 산출물 | 핵심 구현·테스트·**문제 정의 메모** | 진단·수정 |

## 4. 1단계 구조

### 4.1 요청 글 (`request`)

- README 의 "상황·요구 사항·공개 수용 기준" 자리를 대신한다. 요청자 말투의 짧은 업무 요청 300자 안팎, 재료 `business_need` 수준의 "무엇이 필요한가"만.
- **쓰지 않는 것**: 공개 수용 기준 문장, 수치, 운영 조건(`trigger_terms`), 숨은 요구 핵심어(`leak_terms`·`first_mention_of` 개념), 구현 방법.
- 공식 요구 중 일부만 흐리게 담는다 — 기준은 §5.1 검사.
- **요청 글이 말한 요구 `request_mentions: [r#]`** 를 같이 둔다 (승인 대상) — 묻지 않아도 아는 요구라 채점에서 "앎"으로 본다 (§7.1).
- 진행 안내(진행자에게 물을 수 있음, 자료 목록, 제출물)는 코드가 README "진행 방식"에 붙인다 (`process_markdown`, `starter/render.py:170`).

### 4.2 요청자 지식 (`facts`) — 물으면 주는 답

| 칸 | 내용 |
|---|---|
| `fact_id` | `f1`… |
| `covers` | 이 사실이 드러내는 명세 항목 id — `r#`(공식 요구) · `p#`(공개 수용 기준, `PublicAcceptance.ac_id` `^p\d{1,2}$`) |
| `topic` · `match_terms` · `answer` · `answer_hint` | 지금 `Clarification` 과 같은 두 층 답 [확정: 2026-11-06 사용자] — 고르기만, 문장 안 바꿈 |

- 공식 요구·공개 수용 기준마다 그것을 덮는 사실이 하나 이상 — 물어서 알 수 없는 요구로 채점하면 안 된다.
- 사실의 매칭 낱말은 넓게 쓴다 — 한 단어도 괜찮다(두 글자 필터는 `c#` 에만). 다만 **계약 칸 이름 하나만으로 된 낱말을 그 칸의 규칙 하나만 담은 사실에
  쓰지 않는다** — `after` 만으로 경계 규칙 사실이 열리면 형식을 묻는 질문도 적중 1로 센다. 칸 이름 + 규칙 낱말("after 포함"·"after 경계")로 쓴다 [#151 검토 4차].
- **사유 값 예외 경로** (B1, §5.2): 사유를 꼭 구별해야 하는 요구(앱이 '소진'과 '이미 받음'을 다르게 보여야 함 등)만 그 칸 이름과 값을(예: `reason` 을 `SOLD_OUT`)
  **명세 단계에서 사실 답에 정한다**. 계약에는 칸 이름·형식(`reason: string`)만, 값 목록은 싣지 않는다. 계약·테스트는 이 값을 따른다 — 어긋나면 빌드 실패 → 명세 새 판
  (`spec-to-code.md` §3.3 "숨은 테스트 수치 = 명세에 보이는 수치"와 같은 규칙). 단계 사이 결합·사람 손이 드는 **비용** 때문에 생성 단계에서 이런 요구를 적게 만들게 이끈다.
- 추가 요구(`c#`, 함정 단서)는 지금 `clarifications` 그대로 같은 대화에서 쓴다. 자료는 지금 1단계 자료 그대로, 요청하면 공개.

### 4.3 문제 정의 메모 (1단계 제출물)

지금 기능형 제출물의 "설계 메모(결정·근거·AI 에 맡긴 것)"를 넓힌다. 양식은 고정, 내용은 자유:

1. 해결할 문제 (누구의 무엇)
2. 범위 — 하는 것 / 하지 않는 것
3. 가정 — 확인하지 못해 가정한 것
4. 위험·엣지 케이스
5. 설계 결정과 근거
6. AI 에 맡긴 것과 확인한 방법

따로 먼저 내는 관문은 없다 — 구현과 함께 낸다.

### 4.4 한도 없음 [확정: 2026-11-13 사용자]

질문 횟수(추가 요구·요청자 지식)와 자료 요청 횟수(1단계 자료·`debug_stage` 자료)에 **한도를 두지 않는다**. 상한은 제한 시간이다.

| 한도가 하던 일 | 한도 없이 대신 하는 것 |
|---|---|
| 자료를 골라야 하게 함 — '자료 전부 제공' 과제는 AI 단독 풀이에 풀렸다 (스키마 결정 표 2026-11-03) | 자료 열람 **순서·시각**을 기록해 채점: 단서 자료를 언제 열었는지, 방해 자료에 기대 결정했는지, 메모에 연 자료를 근거로 썼는지 |
| 키워드 뿌리기 방지 | **§4.6 답 규칙** — 안 열린 항목 둘 이상에 걸린 질문은 "한 가지씩", 질문 하나에 답 하나 |
| 함정 단서(`c#`)를 골라 묻게 함 — 지금은 최대 2개(`MAX_CLARIFICATIONS = 2`, `spec/feature.py:229`·`:267`) | 정확히 짚지 않은 질문엔 모호한 답(볼 곳)만. 그래도 다 열려 §9 (다)가 깨지면 **`c#` 질문 한도만 먼저 되돌린다** [제안] |
| 질문을 고르게 함 | 채점이 질문 적중률(§4.6)·넓은 질문 수·먼저 물은 것·반복을 본다 |

- 질문·자료 요청은 **전부 시각과 함께 기록**한다.
- 관찰 종류(`Observable.kind`, `schemas/domain.py:312`)에 `asks_fact`(f#) 를 더할지 [미정 — 스키마 PR 전].
- 응시 화면 안내("진행자 질문은 최대 2번", "2/2")는 한도 없음에 맞춰 바꿔야 한다 — 응시 화면 담당 몫.

### 4.5 두 대화 채널 — AI에게 / 진행자에게 [확정: 2026-11-13 사용자]

| | AI에게 | 진행자에게 |
|---|---|---|
| 하는 일 | 코드 설명·수정·테스트 작성. 수정한 코드는 에디터에 바로 반영 | 요구 사항 질문에 답 — 요청자 지식·추가 요구·자료 |
| 답 만드는 법 | 코딩 모델 생성 | **프로그램이 승인된 문장에서 고르기만** (§4.6) |
| 아는 것 | 지원자에게 보이는 것(요청 글·계약·시작 코드·지원자 코드)과 붙여 넣은 것만 | 진행자 보기(`FacilitatorView`) |
| 모르는 것 | 요청자 지식·추가 요구·열지 않은 자료·숨은 요구 전부 | 숨은 요구·허용 설계·`covers`·`reveals` |
| 한도 | [미정] — 응시 플랫폼 정책 | 없음 |

- **요구는 진행자에게 물을 때만 열린다.** AI 도우미에 요구 칸을 넣지 않는다.
- 요구가 다 열리지 않은 채 AI 에게 묻거나 구현을 맡기면 **AI 는 보통 코딩 AI 처럼 그럴듯하게 가정해 답·구현한다 (b)** [확정: 2026-11-13 사용자].
  버린 안 (a) "진행자에게 확인하세요"로 돌려보냄 — AI 가정을 검증하는지(`ai_axes` verification)를 못 본다.
- (b) 운영 [제안]:
  1. AI 지시는 중립 — "요구를 지어내라"도 "모르니 경고하라"도 넣지 않는다.
  2. 모델·버전·설정·지시문 판을 공통 과제 판마다 고정·기록 (provenance). AI 출력이 아니라 지원자가 그것을 확인했는지를 채점한다.
  3. AI 출력(질문·답·코드 변경)을 시각과 함께 기록.
  4. 한 증거는 한 곳에서만 깎는다 — AI 가 가정해 만든 요구를 확인 없이 두면 §7.1 "묻지 않음"으로만, `ai_axes` verification 은 확인한 경우의 가점만.
  5. 지시문 판 바꾸는 시점을 공통 과제 판과 맞추는 규칙은 응시 플랫폼과 [미정].

### 4.6 진행자 답 규칙 — 프로그램 [확정: 진행자는 프로그램 / 규칙은 제안]

같은 질문에는 늘 같은 답 (같은 공고 지원자 간 비교, 고영향 AI 재현성). 지금 규칙(`ANSWER_RULE`, `starter/facilitator.py:19`)을 넓힌다.
후보는 요청자 지식(`f#`)과 추가 요구(`c#`).

**상태** (지원자마다, 항목마다): 없음 → 모호(`answer_hint` 를 받음) → 열림(`answer` 를 받음). `answer_hint` 가 없어 `answer` 가 나가면 바로 열림.

**낱말 맞추기** [확정: 2026-11-13 사용자 — #151 검토 4차]: 매칭 낱말 하나는 **그 단어가 질문에 모두 있으면** 걸린다 — 순서·조사·사이에 낀 말과
상관없이 ("limit 기본값" ← "limit 의 기본값이…", "정렬 순서" ← "어떤 순서로 정렬해야…"). 단어 하나는 한글이면 띄어쓰기를 무시한 부분 문자열
(조사가 붙어도 걸림), 영문이면 대소문자 무시·단어 경계. 구절째 맞추던 첫 안은 자연스러운 질문의 절반 가까이를 "정보 없음"으로 돌려보냈다
(재료 두 건, 질문 29개 중 13개). 판 3 의 지금 규칙 모드는 "지금 판"이라 구절째 그대로다 (§9.1).
이것은 손 시범만의 규칙이 아니라 **§4.6 자체**다 — 응시 플랫폼이 같은 함수를 쓰므로 시범이 재는 규칙과 운영 규칙이 갈리면 시범이 무의미하다.
넓히면 실패가 "정보 없음"에서 "한 가지씩"으로 옮겨 간다 — 다른 항목의 낱말이 문맥으로 들어간 질문("after 로 거른 결과도 최신순인가요?")이 규칙 1에 걸린다.
그래서 질문 목록 점검(§9.1)은 정보 없음 · 한 가지씩 · 엉뚱한 항목 열림 셋을 다 센다.

**낱말 다듬기 (i)(ii)(iii)** [확정: 2026-11-13 사용자 — 손 시범 질문 목록 미달: kb005 사실 질문 구체 답 25%, 주제 밖 질문 11개 중 8개가 잘못 열림].
재료 낱말만 고쳐서는 운영과 같아지지 않는 규칙 쪽 원인 둘을 규칙에서 막는다 — 운영 생성기도 "감사 기록에 남길 내용" 같은 주제와 "동시 요청 수" 같은 낱말을 그대로 만든다.
- (i) 여러 단어로 된 매칭 낱말 안의 **한 글자 단어는 무시**한다. 한글 단어는 부분 문자열로 맞추므로 "동시 요청 수"의 "수"가 거의 모든 문장에 걸려,
  락을 묻는 질문에 함정 단서(c1)가 열렸다. 낱말이 한 글자 단어뿐이면 그대로 둔다.
- (ii) 규칙 4 의 주제 낱말에서 **요청 글에 있는 말**은 뺀다 — §5.1 이 매칭 낱말에서 공개 글의 말을 빼는 것과 같은 원칙
  ("감사·기록"이 요청 글에 있어 거의 모든 질문에 걸렸다). 답 규칙 함수는 요청 글을 받는다 (진행자 보기에 이미 있다).
- (iii) 규칙 4 의 주제 낱말에서 **두 항목 이상의 주제에 함께 나오는 말**도 뺀다 — 항목을 가르지 못하고, 동점이면 id 순으로 엉뚱한 항목(f1)이 열렸다.
  항목 목록만 보면 정해지는 결정적 규칙이다.
- (ii)(iii) 은 규칙 4 에만 건다. 판 3 의 지금 규칙 모드는 "지금 판"이라 그대로다.

질문을 정규화한 뒤 **위에서부터 처음 맞는 하나**를 적용한다:

1. 열림이 아닌 항목 **둘 이상**의 `match_terms` 에 걸림 → "한 가지씩 물어봐 주세요", 적중 0 (넓은 질문).
   여러 항목의 낱말을 몰아넣으면 가장 많이 맞은 항목이 열리던 허점(검토 2차 A2)을 막는다. 결정적으로 가릴 수 있는 나열 질문이라, 낱말로 못 가리는 "나열 질문 거절"을 대신한다.
2. 열림이 아닌 항목 **하나**에만 걸림 → 그 항목의 `answer`, 적중 1, 상태 열림.
   열린 항목은 1에서 세지 않으므로 "수량 말고 회원당은요?" 같은 이어 묻기는 여기로 와서 구체 답을 받는다.
3. 열림 항목에만 걸림 → 그 `answer` 를 다시 줌 (여럿이면 맞은 낱말 수 → id 순), 반복으로 셈.
4. 어느 `match_terms` 에도 안 걸리고, 열림이 아닌 항목과 주제(`topic`) 낱말이 겹침 (주제 낱말은 끝 조사를 떼고, 두 글자 이하 일반어(`too_general`)는
   **추가 요구(`c#`)에서만** 뺀다 — 이 필터는 함정 단서가 일반 질문에 새지 않게 정한 것(2026-11-06)이고 요청자 지식(`f#`)은 잘못 열려도 함정이 아니다.
   `f#` 은 한 글자 낱말만 뺀다. 요청 글에 있는 말과 두 항목 이상의 주제에 함께 나오는 말도 뺀다 — 위 (ii)(iii)) →
   겹침이 가장 많은 하나(같으면 id 순, `f` 먼저)의 `answer_hint`(없으면 `answer` — 상태 열림). 적중은 겹친 항목이 하나면 0.5, 둘 이상이면 0 (주제 낱말 몰아넣기 방지).
   이미 모호인 항목이면 반복으로 셈.
5. 그 밖 → "추가로 드릴 정보가 없습니다", 적중 0.

§7.1 의 "물어서 앎"은 **상태 열림**을 뜻한다.

- 생성 검사(§5.1): 항목끼리 `match_terms` 겹침 금지 — 단어 단위로 한쪽 낱말이 다른 쪽을 덮으면(큰 쪽에 걸리는 질문은 둘 다 걸림) 겹침이다.
- 이 규칙은 **작은 순수 함수**로 먼저 만든다 — 손 시범·평가·응시 플랫폼이 같은 구현을 쓴다 (위치 [미정] 7). `FacilitatorView.rule` 에도 글로 적는다.

### 5.1 명세 쪽 검사 [제안]

- 요청 글에 `trigger_terms`·`leak_terms`·`first_mention_of` 개념·숫자 없음 / 공개 수용 기준 문장과 겹침 낮음 / `request_mentions` 가 요청 글과 맞음.
- 모든 `r#`·`p#` 가 어떤 사실의 `covers` 또는 `request_mentions` 에 있음. 사실 답에 숨은 요구 핵심어 없음 (`check_hints` 재사용).
- **공식 요구마다 그 요구를 가리키는 `p#` 가 하나 이상** (`req_ids` 의 역방향). 지금은 `p#` → `r#` 만 강제하므로 `p#` 가 없는 `r#` 는 공개 테스트가 없어
  §7.1 의 "만들었나"를 정할 수 없다.
- 항목(`f#`·`c#`)끼리 `match_terms` 겹침 금지 (단어 단위, §4.6). `prune_match_terms`(`spec/feature.py:435`, 공개 글에 있는 말 지우기 — 지금 `c#` 에만)를 `f#` 에도 —
  다만 `f#` 은 **요청 글에 있는 말만** 빼고 두 글자 일반어는 빼지 않는다 (두 글자 필터는 `c#` 만, §4.6).
  빌드 단계에서는 승인된 사실을 고치지 않는다. 계약·README 설명 글과 겹치는 `match_terms` 는 빌드 승인 화면에 표시만 한다 (B1 이면 설명 글이 일반어라 드물다).
  계약의 칸 이름을 보고 묻는 질문은 바라는 행동이므로 막지 않는다.
- **자료가 공식 요구를 그대로 말하지 않는지** — 자료는 한도 없이 열리므로 자료가 요구를 직접 말하면 "묻는" 일이 사라진다.
- 흐림 정도: 요청 글이 직접 말하는 `r#` 비율 — 너무 높으면·0 이면 재요청 [미정: 기준값].

### 5.2 계약은 모양만 — B1 [확정: 2026-11-13 사용자 — 손 시범으로 확인할 설계, 백엔드·데이터만]

계약의 모든 요소는 공식 요구(`r*`/`p*`) 출처가 필수다(`refs`, `_check_refs` `schemas/build.py:800`; `spec-to-code.md` §3.3 양방향 대응).
README 계약 절(`contract_markdown`, `starter/render.py:55`)에는 이름 말고도 엔드포인트 설명, 응답마다 설명 글(예: "409 이미 발급됨"), 필드 제약, `enum(...)` 값 목록,
상태 전이(`StateRule`)가 나간다 — 요구를 README 에서 빼도 **계약이 구조상 요구를 그대로 옮긴다**. 이름만 중립으로 바꿔서는 못 숨긴다 (검토 2차 A1).

| | 어디에 | 예 (쿠폰) |
|---|---|---|
| 모양 | 계약 — 처음부터 보임 | 경로·메서드, 필드 이름·형식, 상태 값 이름 |
| 규칙 | 진행자에게 물어야 앎 | 회원당 한 번, 수량 한도, 허용 전이 |
| 거절 | 계약엔 **공통 거절 응답 하나** | `409 요청을 처리할 수 없음` — 어느 규칙인지 말하지 않음 |
| 사유 값 (예외) | 진행자 답에만 (§4.2) — 계약엔 칸 이름·형식만 | `reason: string` |

- 공개 테스트는 정확한 사유 코드·문구 대신 **행동**을 본다: 공통 거절이 왔는지 + 그 뒤 조회 결과(발급 수가 늘지 않았는지 등).
  공개 테스트는 응답을 통째로 비교하지 않으므로(gen_public v5 "구현마다 계약 밖 필드를 더할 수 있음") 지원자가 사유 칸을 스스로 더해도 통과한다 —
  오히려 "사유를 구분해야 하나요?"라고 묻는 지원자가 드러나는 자리가 된다.
- 계약 설명 글·응답 설명에 규칙을 쓰지 않는다. 값 목록(`enum(SOLD_OUT|…)`)은 계약에 싣지 않는다 — 새는 것은 이 경우뿐이고 §5.3 검사가 잡는다.
  칸이 있다는 것 자체("사유가 여럿")는 약한 힌트지만 어떤 규칙인지는 드러나지 않는다.
- 업무 규칙 위반을 409 하나와 오류 본문으로 주는 방식은 실무에서도 흔하다 — API 가 덜 자연스러워지는 대가는 작다.
- **B1 이 숨기는 것은 규칙의 내용(얼마나·누구에게·언제)이지 존재가 아니다.** 행동 판정에는 조회 칸(예: `remaining`)이 필요하고, 그 칸 이름이 "수량 제한이 있다"를 드러낸다.
  피할 수 없으니 받아들이고, 손 시범이 이 상태에서 판별력을 잰다.
- 바뀌는 곳: `plan_contract` 새 판(모양·공통 거절 — 시작 코드 빌드 생성기라 같은 변경에서 `CURRENT` + `PROMOTIONS.md`, 불변식 7 예외;
  입력에 예외 경로의 칸·값을 정해진 것으로 주고 계약과 대조한다),
  공개 테스트 생성(행동 판정), 공개 파일 누출 검사 범위. 기존 시작 코드·참조 구현 생성 입력에서 요구 원문(`GenStarterInput` `schemas/build.py:636`, `GenRefInput` :665)을 뺄지 [미정 9].

### 5.3 단언 값 검사 — 공개 테스트·시작 코드 [제안]

- 공개 테스트가 단언하는 문자열·상태 코드가 **보이는 계약이나 진행자 답에 있는지** 정적 검사 (새로).
- 같은 모델이 같은 글로 만든 구현들은 `SOLD_OUT` 같은 같은 이름을 고르기 쉬워, 구현끼리 비교해서는 숨은 값에 기대는 테스트를 못 잡는다.
  "짐작에 기대지 않는다"는 보장은 이 검사만 준다 — §5.4 구현("물어서 풀 수 있다")과 **둘 다** 있어야 한다.
- **시작 코드에도 건다**: 시작 코드 생성기(gen_starter v7~)는 공개 테스트를 보고 쓴다(`public_tests=public_text(public)`, `nodes/starter/generate.py:294`).
  시작 코드는 지원자에게 가므로 테스트의 단언 값이 시작 코드의 상수·enum·주석으로 새지 않는지 본다. 지금 공개 파일 누출 검사(`starter/static_check.py:2419`·`:2469`)는 숨은 요구 낱말만 본다.
- 공개 테스트 생성기는 README 계약 절과 같은 글만 받으므로(`generate.py:317` `contract_markdown`) 계약을 얇게 하면 받지 않은 값을 단언할 길이 대부분 막힌다.
  전이 규칙은 도우미 상수(`NEXT_OK_…`·`NEXT_BAD_…`)로 테스트 안에서만 쓰이고, 공개 테스트는 채점 이미지에만 있다.
- 누출 검사는 같은 낱말만 잡는다 — 바꿔 말한 누출("1인 1매")은 빌드 승인 때 사람이 마지막으로 본다.

### 5.4 테스트를 보지 않는 구현 — "물어서 풀 수 있다" [제안]

- 지금 참조 구현(흔한 구현 gen_naive v6, 허용 구현 gen_accepted v7, 각 1개 — `build_designs` 기본 1, `builder/settings.py:44`)은
  **공개 테스트 소스 전체를 받아 "모두 통과하게"** 쓴다(`generate.py:409`, 2026-11-08 "테스트 먼저"). 입력을 진행자 답으로 바꿔도 테스트에 적힌 단언 값을 베껴 통과하므로
  "물어서 풀 수 있다"가 증명되지 않는다.
- 그래서 **기존 두 구현은 그대로 두고, 공개 테스트를 보지 않는 구현을 하나 더한다**.
  - 입력: **요청 글 + 계약 + 시작 코드 + 공식 요구 사실(`f#`) 구체 답 전부**. 시작 코드는 지원자도 그 위에서 구현하므로 넣는다 (§5.3 검사를 통과한 뒤라 새는 값 없음).
  - **`c#` 와 자료는 넣지 않는다.** 이 구현은 공개 테스트로만 채점하므로 숨은 요구와는 상관이 없다. 넣으면 `f#` 가 `p#` 를 다 덮지 못해도 `c#`·자료가 메워
    사실 답 부족이 드러나지 않는다. 이 구현은 §5.1 의 "모든 `p#` 는 사실이 덮는다"를 확인하는 자리다.
  - 공개 테스트로 채점한다. 통과 = 물어서 알 수 있는 정보만으로 공개 요구를 풀 수 있음. 진행자 답이 모자란 것도 여기서 걸린다.
- 다시 만들게 할 때 **실패 메시지를 넘기지 않는다** — 단언 실패 메시지에 기대 값이 나온다(`expected: "SOLD_OUT"`). 컴파일 오류와 실패한 테스트 이름만 넘긴다.
- 이 구현은 "다 물으면 풀리는가"라는 **상한**을 잰다. 손 시범의 "물을 수 있음" 판(무엇을 물을지 스스로 고름 — 묻는 실력)과는 다르다. 시범의 판 0(§9.1)이 이 구현을 미리 해 보는 것.
- 비용: 호출 하나(몇 센트) + 검증 실행 한 판. 부담되면 알파·평가 때만 돌리고 빌드마다 돌릴지는 나중에 [미정 8].

### 5.5 실패 원인 가르기 [제안]

지금 규칙은 "모든 구현이 같은 단언에서 실패하면 테스트를 의심해 다시 만든다"(`_public_refs`, `starter/repair.py:322`)다. 이대로면 **진행자 답이 모자라서 생긴 실패도
테스트에서 단언을 빼는 쪽으로 고쳐** 테스트가 조용히 약해진다. 테스트를 보지 않는 구현(§5.4)의 실패는 따로 가른다:

1. 테스트 이름만 넘겨 **한 번 다시 만든다** — 테스트를 못 보고 만든 구현은 응답 모양·컴파일 같은 평범한 실수로도 자주 떨어진다. 바로 넘기면 빌드 승인 화면에 표시가 쏟아진다.
2. 다시 만든 뒤에도 같은 테스트에서 실패하면:

| 실패 | 판정 | 할 일 |
|---|---|---|
| 단언한 값이 보이는 계약·진행자 답에 없음 | 테스트 탓 (§5.3 검사가 놓친 경우 — 예: 값을 코드로 조합해 만든 단언) | 공개 테스트를 다시 생성 → 기존 구현·시작 코드를 다시 검증 → 이 구현은 새로 만들지 않고 다시 돌리기만. 기존 재생성 한도 안에서 |
| 값이 진행자 답에 있음 | 구현이 값을 못 맞춤 (답 문장이 모호할 수 있음) | 더 만들지 않음. 빌드 승인 화면에 "답에 있는 값을 못 맞춤: pt# ← f#" 표시 |
| 조건 단언 ("발급 수가 늘지 않음") | 진행자 답 부족 의심 | 더 만들지 않음. "pt#(p#) ← 덮는 사실 f#…" 표시 |

빌드를 실패시키지 않고 review 로 보낸다. 승인자가 승인하거나 명세 새 판을 고른다 (명세는 빌드에서 못 고친다). 이 결과로 빌드를 막을지는 빌드 알파 뒤 [미정 8] 과 함께 정한다.

### 5.6 프론트 [제안]

테스트가 화면 요소를 test id·문구로 찾아야 해서 요소 이름이 계약에 보여야 한다 — 요소에 딸린 요구(재시도 버튼 등)는 숨기기 어렵다.
프론트는 B1 대신 **요소가 필요 없는 규칙(입력 검증·순서·상태)만 묻게** 한다 (#151 첫 댓글 (3)안). 첫 대상은 백엔드. 데이터 과제는 계산 결과가 곧 행동이라 B1 에 잘 맞는다.

## 7. 채점 (Evidence model)

### 7.1 요구별 칸 나누기 — 이중 감점 막기

공식 요구(`r#`)마다 "알았나 × 만들었나"로 한 칸에 넣고 **한 번만** 깎는다. "만들었나" = 그 요구에 걸린 `p#`(`req_ids`)의 공개 테스트(행동 판정).

| | 테스트 통과 | 테스트 실패 |
|---|---|---|
| **보이는 것으로 앎** (`request_mentions`) | 정상 | 구현 문제 |
| 물어서 앎 (사실 상태 열림, §4.6) | 정상 | 구현 문제 |
| 묻지 않음(또는 모호한 답만), 메모에 가정으로 적음 | 가정이 맞음 — 인정 | 분석 문제 (가정이 틀림) |
| 묻지 않음, 메모에도 없음 | 우연히 맞음 — 분석 점수 없음 | 분석 문제 |

- 자료로 아는 길은 두지 않는다. §5.1 이 자료가 요구를 그대로 말하지 않게 검사하고, 검사를 빠져나간 경우는 명세 승인 때 사람이 본다.
- 질문 한도가 없으므로 모든 요구는 물으면 알 수 있다 — 몰라서 못 만든 것은 분석 문제.
- 숨은 요구(t#)는 지금 기능형 채점 그대로 (`catches_trap`, 숨김 수용 기준, 허용 설계).

### 7.2 문제 정의 메모

| 본다 | 근거 |
|---|---|
| 공식 요구·공개 수용 기준을 얼마나 짚었나 | `r#`·`p#` ↔ 메모 문장 |
| 숨은 요구를 위험으로 짚었나 | `t#` ↔ "위험·엣지 케이스" 칸 |
| 가정을 드러냈나, 물어서 확인했나 | "가정" 칸 · 대화 로그 |
| 잘 물었나·잘 골랐나 | 질문 적중률(§4.6)·넓은 질문 수·먼저 물은 것·반복, 단서 자료를 연 시점, 방해 자료에 기댄 결정 |
| AI 가정을 확인했나 (가점만) | AI 채널의 요구 가정 ↔ 진행자 확인 질문 · 메모 "AI 에 맡긴 것과 확인한 방법" |

수준 기준 예 [제안] (근거 수행준거 id 필수):
- 1: 요청 글만 보고 구현. 질문이 없거나 요청 글에 있는 것만 묻는다.
- 3: 공식 요구 대부분을 물어 확인하고 가정을 적는다. 숨은 요구는 못 짚는다.
- 5: 숨은 요구 하나 이상을 위험으로 짚고, 확인하거나 가정으로 남겨 구현에 반영한다 (그 숨은 요구의 숨은 테스트 통과가 근거).
  질문 적중률(§4.6)이 기준값 미만이면 수준 5 를 주지 않는다 — 기준값은 손 시범 결과로 [제안]을 정하고 §9.3 에서 확정 (시범에서는 이 조건 없이 매긴다).
- 숨은 요구를 짚었지만 구현하지 못하면 수준 4 — 깎는 것이 아니라 최고 등급의 조건을 못 채운 것.

**최종 판정은 사람이 행동 기준의 수준과 AI 활용 축(`ai_axes`)으로 한 번 내린다. §7.1 표와 테스트 결과는 그 근거이고 점수로 따로 더하지 않는다** [제안].

채점 방식 [제안]: 메모 ↔ 명세 id 대조는 LLM 1차(id 목록과 인용만, provenance) + 사람 최종 (고영향 AI). 지원자 메모·질문은 외부 LLM 전 개인정보 거르기 (불변식 2 취지).
실행 위치(P1 / 응시 플랫폼) [미정].

#### 재료별 조건, 평균하는 효과

**과제마다 생기는 조건은 재료별로 정하고, 효과의 크기만 재료별로 구해 같은 무게로 평균한다.** 한 재료 안의 메서드들은 같은 구현을 확인하므로 서로 독립이 아니다 —
메서드 수로 합치면 표본이 커 보이기만 하고 메서드가 많은 재료가 결과를 정한다. 조건(바닥 효과 등)은 과제마다 생기므로 평균하면 한 재료의 문제를 가린다.

- 재료별로 정하는 것: (라), 관문, (나) 자격, (바) 기준점.
  - **(나) 자격**: 그 재료에서 정보의 값(판 0 ② − 판 2 ②) > 0 인 모델.
  - **(바) 기준점**: 그 재료의 판 0 ② 천장이 ⅔ 이상인 모델 가운데 가장 약한 모델 (판 1·3 전에 정한다). 재료마다 달라도 된다 — (바)는 한 재료 안에서 판 1 과 판 3 을 비교한다.
- 평균하는 것: (나)의 판 1 − 판 2, (바)의 "판 1 차이 − 판 3 차이", (다)의 포착 수 차이.
- 적중률은 질문 단위 지표라 재료를 합쳐 질문 수로 계산한다.

1. **막힘** — 진행자 쪽 고치기 (한 번):
   - 돌리기 전에 고정한 절차로 만든 동의어·표기·약어 목록 안에서만 `match_terms` 를 고친다. 목록은 운영에서도 재현할 수 있는 절차(예: 고정한 프롬프트로 `match_terms` 마다 동의어 생성)로 만들고,
     §5.1 정리(일반어 빼기, 공개 글에 있는 낱말 빼기, 항목끼리 겹침 금지)를 똑같이 건다. 판 1 이 쓴 표현을 그대로 넣지 않는다.
   - 이 고치기는 **생성기에 동의어 확장 단계를 더하는 시뮬레이션**으로 기록한다 (미정 11 의 근거). 고치기 전후의 "한 가지씩" 비율을 함께 기록한다.
   - 목록 밖 표현으로 막혔다면 고치지 않고 "§4.6 낱말 매칭의 한계"로 기록한다 — 그 기록 자체가 결과다.
   - 다시 풀 것은 진행자를 거치는 판 1·4 뿐. 두 번째에도 막히면 두 번째 결과로 판정하고 **§4.6 판정 방식 재검토**(미정 10)로 보낸다 — 낱말 매칭의 한계일 뿐 아이디어 전체의 실패가 아니다.
2. **흔들림** — **그 재료의 자격 모델 전부**로 판 1·2 를 한 번씩 더 풀고 세 번의 평균으로 다시 판정한다 (흔들림이 나온 모델만 다시 풀거나 좋은 결과만 고르지 않는다).
3. **묻지 않음·늦게 받음** — 보류 → 사람 시범 응시 (아래). 보류는 멈춤도 다시도 아니므로 뒤 기준은 계속 보되, 빌드 알파는 사람 시범 응시 뒤.

원인 단계를 다 거친 뒤의 (나): **실패면 멈춤**. **결론 없음이면 재료 2건을 더해 한 번만 다시** — (바)의 "표본 작음"과 같은 갈래로, 둘 다 해당해도 한 번만 추가한다.
보류("묻지 않음·늦게 받음")로 간 경우는 이 갈래가 아니라 사람 시범 응시로 간다.

(마) 실패로 §4.6·"한도 없음"을 바꾸는 것은 낱말 고치기가 아니라 **설계 변경**이다 — §4.4·§4.6 에 반영하고 시범을 새 판으로 기록한다.

**(다) 원인** — 판 1 기록에 판 3 의 한도를 다시 적용한다: 진행자 질문은 `f#` 로 답한 것을 뺀 처음 2개(빗나감·"한 가지씩"도 한 번으로 셈), 자료 요청은 판 3 한도 개수만.
그 함정의 단서(그 함정을 `reveals` 에 가진 `c#`, 역할이 key 인 자료)가:

| 단서가 | 판정 | 조치 |
|---|---|---|
| 남아 있음 | 한도 문제 아님 (메모 양식·요청 글 구조·분석의 효과) | 진행하되 기록하고 §9.3 에서 (다)를 다시 본다 |
| 질문 쪽에서 잘림 | `c#` 질문 한도 문제 | `c#` 한도를 되돌리고 그 조건으로 판 1 을 다시 풀어 (나)·(바)를 다시 본다 |
| 자료 쪽에서 잘림 | 자료 한도 문제 | 자료 한도를 되돌리고 그 조건으로 판 1 을 다시 풀어 (나)·(바)를 다시 본다 |

판 1 은 한도 없이 풀어 질문·자료를 아끼지 않았으므로 이 재적용은 "잘림"이 실제보다 많이 나와 **한도 문제 쪽으로 기운다** — 안전한 방향이지만 그 기울기를 알고 읽는다.

**요구별 표**: 요구마다 예측(짐작 가능/어려움) · 판 2 결과 · 판 1 결과 · 판 1 이 그 요구의 사실을 열었나 · 원인. 판정에는 쓰지 않는다
(판 2 가 못 맞힌 요구만 골라 판 1 과 비교하는 것은 결과를 보고 고른 부분집합이라 판 1 쪽으로 치우친다). 라벨이 얼마나 맞는지·생성기 보완의 근거로 본다.

#### 사람 시범 응시 — (나) 보류일 때

  (사람과 opus 는 구현 실력이 달라 그 비교는 묻기의 이득이 아니라 구현 실력을 잰다).

  (응시자가 평소 쓰는 AI 를 허용하면 AI 가 무엇을 짐작해 주는지가 사람마다 달라 "물어서 얻은 정보를 썼는가"를 가를 수 없다).

#### 고정 — 첫 풀이(판 2 opus)를 돌리기 전에 한 번

**첫 풀이(판 2 opus, 관문 먼저 — 위 "순서")를 돌린 뒤에는 아래 목록 전체를 바꾸지 않는다** — 아직 돌리지 않은 판의 항목(판 1·4 지시문 등)도 마찬가지다.
판 2·0 을 먼저 돌리고 판 1·3·4 를 나중에 돌리므로, "돌리기 전에만"으로 두면 판 2 결과를 본 뒤 판 1·4 항목을 고치는 길이 열린다.

고정할 것:
- 재료 고르는 규칙과 고른 재료
- 재료마다 손으로 쓴 요청 글·`request_mentions`·사실 파일(두 층)·요구별 예측·`method_req`, ①용·②용 테스트 묶음, 얇은 README·`starter-thin/`,
  돌연변이(`mutants.json`·`mutants/`)와 유효성 결과(`validity.json`), 질문 목록 둘과 결과(`questions/`), 사실의 정보 값 0 표시(`info_zero`)
- 판 1·2 지시문(판 1 은 "진행자에게 요구를 물을 수 있다"는 사실만 알리는 중립 문장 — 응시 화면 안내와 같게, 판 2 는 그 문장만 뺌), **묻는 도구의 설명 문구**, 판 4 지시문
- 판마다 같은 풀이 예산, 판 3 진행자 모드(지금 규칙·질문 2·자료 핵심 + 1)
- 동의어 목록을 만드는 절차와 그 결과 목록
- 사람 시범 응시의 AI 도우미 모델·지시문, 진행자 CLI
- 숫자: 예산 2배, (바) 기준점 하한 ⅔, (마) 배수 0.5, ② 채점의 "4xx 인가", 묻지 않고는 모르는 측정 요구 하한 2, 확인용 질문 목록 기준(구체 답 ≥ 80%·한 가지씩 ≤ 10%)
- 돌리는 순서 (관문 먼저 — 판 2 opus → 관문 → 판 0 → (라) → 판 2 나머지 → 판 1·3·4)

첫 풀이 뒤에 움직일 수 있는 것 — **미리 정한 절차뿐**:
- 정해진 절차로 만든 동의어 목록 안에서 하는 진행자 고치기
- 미리 정한 규칙에 따른 재료 교체·추가 — 새 재료는 그 재료의 첫 풀이 전에 다시 고정한다 (해시 목록 새로)
- 판정표에 정해진 다시 풀기
- (라) 실패 뒤 사실 답 고치기 — **판 0 기록에서 정보 부족으로 드러난 요구의 사실만, 판 1 전에**. 판 2 결과는 근거로 쓰지 않는다.
  고친 뒤 해시 목록에 새 해시와 이유를 덧붙인다
- 관문 뒤 생성기 보완 — 고치기가 아니라 **새 재료**로 다룬다 (새로 고정, 기록을 따로)

확인할 수 있게 남긴다:
- 첫 풀이 전에 `data/eval/<시범>/` (git 밖)에 고정한 파일마다 해시를 적은 목록을 남긴다 (돌리는 순서도 함께). 목록에는 **설계 문서 커밋 sha** 와
  **진행자 함수·채점 스크립트·②용 테스트 묶음의 커밋 sha** 도 적는다 — 코드도 판정에 영향을 준다.
- 판정 규칙(기준·숫자)은 이 설계 문서 PR 로만 고친다. **첫 풀이 뒤에 판정 규칙을 고치면 시범 새 판**으로 기록하고, 이미 나온 결과는 고치기 전 규칙으로 판정해 보고한다.

### 9.2 빌드 알파 (실현성) — 손 시범 통과 뒤 1~2건

스키마 전에 `eval/starter/run_alpha.py` 로 돌린다. 이전 알파 명세를 다시 쓰는 `--task-json` 에 손 시범의 요청 글·`request_mentions`·사실 파일을 받는 옵션을 더한다.
사실 파일은 **기본 층만** 넣는다 (§9.1) — 시범 전용 층의 예전 값을 넣으면 테스트를 보지 않는 구현이 예전 방식대로 구현해 공통 거절을 보는 새 공개 테스트에서 떨어지고,
답이 부족하지 않은데도 "진행자 답 부족 의심"이 뜬다. 결과는 `data/eval/build/<날짜>-alpha-<tag>/` (git 밖).
스키마를 앞으로 당기지 않는 이유: 알파 결과를 보기 전에 칸 이름부터 굳히지 않기 위해 (예외 경로의 칸 같은 것이 알파 결과로 바뀔 수 있다).

`plan_contract` 새 판이 첫 답에 얇은 계약을 내는 비율 · 단언 값 검사·계약 누출 검사 통과율 · 테스트를 보지 않는 구현의 공개 테스트 통과율 · "진행자 답 부족 의심" 빈도.

## 부록 — 가상 예시 (형식 설명용, 실제 생성물 아님)

`feature-task-backend.md` 부록의 "이벤트 쿠폰 발급 API" 과제를 요청 글 판으로 바꾸면:

- request: "이번 주말 이벤트 때 선착순 쿠폰을 뿌리려고 해요. 기존 쿠폰 서비스에 발급 기능을 붙여 주실 수 있을까요? 다음 주에 오픈이에요."
  request_mentions: [] (수량·회원당 횟수·응답 종류를 말하지 않음)
- acceptance_public: p1 "수량이 0이 되면 더 발급하지 않는다" (req_ids [r2]) · p2 "같은 회원은 두 번 받지 못한다" (req_ids [r1]) …
- 계약 (B1, 모양만): `POST /events/{id}/coupons` → `201 {couponId}` / `409 요청을 처리할 수 없음 {reason: string}` · `GET /events/{id}` → `{remaining}`.
  값 목록·"이미 발급됨"·"소진" 같은 설명은 계약에 없다.
- 공개 테스트 (행동): 같은 회원이 두 번 요청 → 두 번째는 409 + `remaining` 이 한 번만 줄었음. 수량이 0 이면 409 + 발급 수 그대로.
- facts:
  - f1 covers [r1, p2] "한 사람이 여러 번 받을 수 있나요?" → "회원당 한 번이에요."
  - f2 covers [r2, p1] "수량은 어떻게 정하나요?" → "이벤트마다 정해 둔 수량만큼이요." / 모호: "이벤트 설정에 따라 달라요."
  - f3 covers [r3] "실패하면 앱에서 이유를 구분해야 하나요?" → "네, 다 떨어진 경우는 `reason` 을 `SOLD_OUT` 으로 주세요." (사유 값 예외 경로 — 명세에서 값을 정함)
- clarifications (그대로): c1 요청량(t1 단서) · c2 앱 재시도(t2 단서).
- 진행자 답 (§4.6): "수량이랑 회원당 제한이 있나요?" → f1·f2 둘 다 안 열렸고 둘 다 걸림 → "한 가지씩 물어봐 주세요" (적중 0).
  f2 를 연 뒤 "수량 말고 회원당 제한은요?" → 안 열린 f1 하나만 셈 → f1 구체 답. c1 은 c1 을 짚는 질문을 따로 해야 열린다.
- 수준 5 메모 예: 위험 칸에 "오픈 직후 요청이 몰리면 남은 수량을 넘겨 발급될 수 있음 — 요청량 확인함(c1)",
  "응답이 늦으면 앱이 다시 보낼 수 있음 — 확인 못 해 중복 발급 방지를 가정으로 두고 구현함".
