# 기능 개발형 과제 — 문제 분석 단계(0단계) 설계 [제안]

> 상태: 설계 초안 (2026-11-13). 이슈 #151.
> 결정 표기는 온톨로지 레포와 같다 — `[확정]` / `[제안]` / `[미정]`.
> 관련: `docs/design/feature-task-backend.md`(기능형 과제, §4.3 두 단계·§10 "AI 없는 첫 단계"), `docs/design/spec-to-code.md`(README·계약),
> `docs/design/task-spec-schema.md`, `src/task_spec/schemas/domain.py`(`Clarification`·`DebugStage`), `src/task_spec/starter/{facilitator,render}.py`.

## 0. 요약

- 기능형 과제 앞에 **0단계 문제 분석**을 둔다: 지원자는 README 대신 **모호한 업무 요청** 하나를 받고, 요청자(진행자)와 대화·자료 요청으로 파악한 뒤 **문제 정의서**를 낸다.
- 0단계를 내면 **공식 요구 사항(지금 README)을 모두에게 같게 공개**하고 1단계 구현 → 2단계 디버깅은 지금 그대로 간다 [제안].
  분석은 0단계 점수, 구현은 1단계 점수로 따로 본다 — 분석을 못 해도 구현은 같은 출발선이고, 숨은 테스트·비교 가능성(불변식 3)이 유지된다.
- 생성 순서는 **명세를 먼저 다 만들고 → 그것을 흐려 요청 글을 만든다** (§5). 정답 범위·요청자 답이 먼저 있어야 채점과 요청 글이 어긋나지 않는다.
- 요청자 답은 지금 추가 요구(`clarifications`)처럼 **승인된 문장 중에서 고르기만** 한다 — 생성하지 않는다.
- 0단계를 쓰는 과제는 **질문 횟수·자료 요청 횟수 한도를 두지 않는다** [확정: 2026-11-13 사용자]. 상한은 제한 시간이고,
  횟수 대신 **무엇을·어떤 순서로·얼마나 정확히** 묻고 열었는지를 채점한다 (§4.5).
- 처음 안(#151 첫 본문)은 "요구 항목을 감췄다가 질문하면 연다"였다. 측정 대상은 정보를 여는 행위가 아니라 **모호한 문제를 분석하는 과정**이므로
  감추기·열기는 0단계 대화의 한 수단으로 내렸다.

## 1. 왜 필요한가

- 지금 README 에는 제목·상황·**요구 사항·공개 수용 기준**·계약·제출물이 처음부터 다 보인다. 지원자는 "무엇을 만들지"가 정해진 상태에서 시작한다.
  실무 요청은 대개 그렇게 정해져 오지 않는다 — 무엇이 문제인지 묻고 정의하는 것이 경력자를 가르는 지점이다.
- 기능 구현은 코딩 AI 가 가장 잘하는 일이라 AI 대리 풀이 위험이 크다 (`feature-task-backend.md` §0). AI 는 묻지 않고 그럴듯하게 가정해 구현하는 경향이 있어,
  "무엇을 물어야 하는가"를 독립 단계로 재면 판별력이 생길 수 있다 — 평가로 확인한다 (§10).
- `feature-task-backend.md` §10 의 [미정] "AI 없는 첫 단계(구현 전 설계 메모 먼저 제출)" 자리를 이 단계가 채운다.
- 이슈형(incident)은 원래 "모호한 증상 → 원인 분석"이다. 기능형에 같은 성격의 앞 단계를 붙이는 셈이다.

## 2. 범위

| 포함 | 제외 |
|---|---|
| 기능형(`task_kind=feature`) 공통 과제의 0단계 명세 — 요청 글·요청자 지식·정의서 채점 기준 | 이슈형 (이미 분석형 — 필요하면 나중에) |
| 0단계 생성 프롬프트·누출 검사·승인 화면 표시 | 확장 슬롯·경험 검증 과제 (지금 그대로) |
| 진행자 묶음(`FacilitatorView`)에 0단계 추가 | 대화 진행·단계 전환·제출 수집 (응시 플랫폼 몫) |
| 평가 (AI 단독 0단계 풀이로 판별력 확인) | 지원자 정의서 실제 채점 실행 위치 — §8, [미정] |

README 틀은 스택(백엔드·프론트·데이터)마다 같고 계약 절만 다르다. 0단계에는 계약이 없으므로 **스택과 무관하게 한 번 만들면 된다**.
#151 댓글의 프론트 계약 누출 문제(test id·배경 요청이 숨긴 요구를 드러냄)도 0단계에서는 생기지 않는다.

## 3. 흐름

```
0단계 문제 분석   요청 글 → 요청자와 대화·자료 요청 → 문제 정의서 제출
      ↓ reveal_after: stage0_submitted — 공식 요구 사항·계약 공개 (모두 같음)
1단계 구현        지금 기능형 1단계 (README)
      ↓ reveal_after: stage1_submitted
2단계 디버깅      지금 debug_stage
```

| | 0단계 분석 (새) | 1단계 구현 | 2단계 디버깅 |
|---|---|---|---|
| 보이는 것 | 요청 글, 자료 제목 목록 (한도 없음) | README (지금 그대로, 한도 안내 없음) | `debug_stage.scenario` 등 (지금 그대로, 자료 한도 없음) |
| 물으면 주는 것 | 요청자 지식(§4.2) · 1단계 자료 | 추가 요구(`clarifications`) · 1단계 자료 | 2단계 자료 |
| 숨긴 것 | 공식 요구·공개 수용 기준·숨은 요구 | 숨은 요구·숨김 수용 기준·허용 설계 | 증상의 원인 |
| 산출물 | 문제 정의서 (§4.3) | 핵심 구현·테스트·설계 메모 | 진단·수정 |

시간 [미정]: 지금 기능형은 60분 = 1단계 40 + 2단계 20 (`spec/common.py FEATURE_BUILD_MIN, FEATURE_DEBUG_MIN`).
- 안 A — 총 60분 유지: 0단계 10 + 1단계 30 + 2단계 20. 구현 시간이 줄어 1단계 범위(공개 요구 ≤6)를 줄여야 할 수 있다.
- 안 B — 총 70분: 0단계 15 + 1단계 35 + 2단계 20. (#151 본문의 "15/35/20" 은 이 안 — 총 시간이 늘어난다.)

## 4. 0단계 구조

### 4.1 요청 글 (`request`)

- 요청자(가상 기획자·운영 담당) 말투의 짧은 업무 요청 300자 안팎. 재료 `business_need` 수준의 "무엇이 필요한가"만 쓴다.
- **쓰지 않는 것**: 공개 수용 기준 문장, 수치(수량·요청량·시간 조건), 운영 조건(`trigger_terms`), 숨은 요구 핵심어(`leak_terms`·`first_mention_of` 개념), 구현 방법.
- 공식 요구(`requirements`) 중 일부만 흐리게 담는다 — 다 담으면 분석할 것이 없고, 하나도 안 담으면 무엇을 물을지 실마리가 없다. 기준은 §5 검사.
- 끝에 진행 안내(질문·자료 한도, 제출물)는 코드가 붙인다 (지금 `process_markdown` 과 같은 방식).

### 4.2 요청자 지식 (`facts`) — 물으면 주는 답

요청자가 아는 사실 목록. 공식 요구·공개 수용 기준·추가 요구에서 만든다.

| 칸 | 내용 |
|---|---|
| `fact_id` | `f1`… |
| `covers` | 이 사실이 드러내는 명세 항목 id — `r#`(공개 요구) · `ac#`(공개 수용 기준) · `c#`(추가 요구) |
| `topic` · `match_terms` · `answer` · `answer_hint` | 지금 `Clarification` 과 같은 두 층 답 규칙 [확정: 2026-11-06 사용자] — 고르기만, 문장 안 바꿈 |

- 공개 요구·공개 수용 기준마다 그것을 덮는 사실이 하나 이상 있어야 한다 — 물어서 알 수 없는 요구로 0단계를 채점하면 안 된다.
- 추가 요구(`c#`, 함정 단서)는 따로 사실을 만들지 않고 `clarifications` 를 그대로 0단계에서도 쓴다 [제안]. 질문 한도는 없다 (§4.5).
- 0단계에서 받은 답은 1단계에도 유효하다 (지원자가 이미 안 것).
- 자료는 1단계 자료(`artifacts`)를 0단계에서도 요청할 수 있다 [제안], 한도 없음 (§4.5). 2단계 자료는 지금처럼 1단계 제출 뒤.

### 4.3 문제 정의서 (제출물)

지원자가 쓰는 칸 — 양식은 고정, 내용은 자유:

1. 해결할 문제 (누구의 무엇)
2. 범위 — 하는 것 / 하지 않는 것
3. 가정 — 확인하지 못해 가정한 것
4. 위험·엣지 케이스
5. 내가 정한 수용 기준
6. 남은 질문

### 4.4 관찰 행동 (`observables`)

지금 종류를 그대로 쓴다: `asks_clarification`(c#) · `requests_artifact` · `catches_trap`(정의서 위험 칸에서 숨은 요구를 짚음) · `first_mention_of`.
요청자 지식 질문은 새 종류 `asks_fact`(f#) 를 더할지, `asks_clarification` 의 값 공간을 넓힐지 [미정].
가장 강한 신호는 **0단계에서 숨은 요구(t#)를 위험으로 짚었는지**다 — 공식 요구 공개 전이라 1단계 `catches_trap` 보다 단서가 적다.
한도가 없으므로 질문·자료 요청은 **전부 시각과 함께 기록**하고, 횟수가 아니라 순서·적중으로 본다 (§4.5).

### 4.5 한도 없음 [확정: 2026-11-13 사용자]

0단계를 쓰는 과제는 질문 횟수(`max_clarifications`·0단계 질문)와 자료 요청 횟수(`max_requests`)에 **한도를 두지 않는다**.
0단계에서 1단계 자료·추가 요구를 함께 쓰므로 0·1단계 모두 한도가 없고, 2단계 자료 한도(`debug_stage.max_requests`)도 없앤다 [확정: 2026-11-13 사용자].
2단계도 같은 대응(열람 순서·시각 기록, 단서 자료를 연 시점, 방해 자료에 기댄 진단)으로 채점한다.

- 왜: 0단계가 재는 것은 "무엇을 물어야 하는가"다. 횟수를 막으면 아끼는 요령을 재게 된다. 실무에도 질문·자료 열람 횟수 제한은 없다. 상한은 제한 시간이다.
- 잃는 것과 대응:

| 한도가 하던 일 | 한도 없이 대신 하는 것 |
|---|---|
| 자료를 골라야 하게 함 — '자료 전부 제공' 과제는 AI 단독 풀이에 풀렸다 (스키마 결정 표 2026-11-03) | 자료 열람 **순서·시각**을 기록해 채점: 단서(key) 자료를 언제 열었는지, 방해(distractor) 자료에 근거해 결론을 냈는지, 정의서에 연 자료를 근거로 썼는지. 다 열 수 있어도 무엇이 중요한지는 지원자가 가려야 한다 |
| 키워드 뿌리기 방지 — 질문을 낱말만 바꿔 계속 보내면 구체 답(`match_terms`)이 다 열림 | **질문 하나에 사실 하나만** 답한다 (낱말 여러 개를 몰아 넣어도 하나). "무엇을 물을 수 있나"·주제 나열 질문은 답하지 않는다. 같은 사실을 다시 물으면 같은 답(새 정보 없음) |
| 질문을 고르게 함 | 채점이 **질문 적중률**(사실에 닿은 질문 / 전체), 먼저 물은 것, 반복을 본다 — 많이 묻는 것이 아니라 잘 묻는 것이 점수 |

- 효과는 평가로 확인한다 (§10): "닥치는 대로 묻고 다 여는" AI 전략이 수준 5에 닿으면 한도 없음을 다시 본다.

## 5. 생성 흐름

```
draft_spec (지금 그대로 — 요구·공개 기준·함정·추가 요구·자료)
   → draft_analysis_request   요청 글 + 요청자 지식 (새 프롬프트)
   → 검사 (아래) — 어긋나면 사유 붙여 1회 재요청, 그래도면 review_flags
   → approval (요청 글·요청자 지식도 승인 대상, 불변식 9)
```

- 새 과제 `prompts/draft_analysis_request/v1.md` — 시작 코드 생성기가 아니므로 평가 뒤 `CURRENT` (불변식 7). 모델은 `opencode:qwen3.8-flash` 로 시작.
- 입력: 승인 전 기능형 과제의 공개 칸(제목·상황·요구·공개 수용 기준), 추가 요구, 재료 `business_need`. **숨은 요구·허용 설계는 넣지 않는다** — 요청 글에 샐 길을 원천에서 막는다.
- 계산할 수 있는 칸(id 번호·`covers` 대조·진행 안내)은 코드가 채운다 (`draft_feature_task` v4 와 같은 원칙).
- 검사 [제안]:
  - 결정적: 요청 글에 `trigger_terms`·`leak_terms`·`first_mention_of` 개념·숫자 없음 / 공개 수용 기준 문장과 겹침 낮음 /
    모든 `r#`·`ac#` 가 어떤 사실의 `covers` 에 있음 / 사실 답에 숨은 요구 핵심어 없음 (`check_hints` 재사용).
  - 흐림 정도: 요청 글이 직접 말하는 `r#` 비율 — 너무 높으면(분석할 것 없음)·0 이면(실마리 없음) 재요청. 1차는 낱말 겹침, 2차는 판정 LLM [미정: 기준값].
- 공통 과제는 공고 단위로 한 번 만들고 저장소(`CommonRef`)를 재사용하므로, 0단계도 공통 과제 판의 일부로 같이 저장·재사용된다.

## 6. 스키마 초안 [제안]

`TaskItem` 에 `analysis_stage: AnalysisStage | None = None` 을 더한다 — 예전 판·이슈형은 `None` (하위 호환). 기능형 전용 칸(`FEATURE_FIELDS`)에 넣는다.

```yaml
analysis_stage:
  time_limit_min: 5~30
  request: "<요청 글>"                       # 지원자에게 처음 보이는 글
  facts: [{fact_id, covers: [r#|ac#|c#], topic, match_terms, answer, answer_hint}]
  deliverables: ["문제 정의서"]                # 질문·자료 한도 칸 없음 (§4.5)
  observables: [...]
  rubric:                                     # 정의서 채점 기준 (§7)
    coverage_targets: [r#, ac#, t#]
    anchors: {level_1, level_3, level_5}      # 각 기준에 근거 수행준거 id (지금 규칙)
```

- 0단계가 있는 과제는 `max_clarifications`·`max_requests`·`debug_stage.max_requests` 를 `None`(한도 없음)으로 둔다 — 지금 `max_clarifications` 는 1~6 필수라 `None` 을 허용하게 바꾼다
  (`DebugStage.max_requests`·`FacilitatorView` 의 `max_questions`·`max_requests` 는 이미 `None` 을 받는다). README "진행 방식"(`process_markdown`)과
  요청 글 끝 안내에서 한도 문장을 뺀다.
- 1단계 README 공개 시점이 생기므로 `reveal_after` 를 0단계 쪽에 둘지(`stage0_submitted`), 1단계 쪽에 새로 둘지 정한다.
- 이 문서가 확정되면 `docs/design/task-spec-schema.md` + `schemas/domain.py` 를 같은 PR 에서 고친다 (스키마 SSOT 규칙).

## 7. 문제 정의서 채점 (Evidence model)

| 본다 | 근거 |
|---|---|
| 공식 요구·공개 수용 기준을 얼마나 짚었나 | `coverage_targets` 의 `r#`·`ac#` ↔ 정의서 문장 |
| 숨은 요구를 위험으로 짚었나 | `t#` ↔ 정의서 "위험·엣지 케이스" 칸 |
| 가정을 드러냈나, 물어서 확인했나 | 정의서 "가정" 칸 · 대화 로그(`asks_*`) |
| 범위를 정했나 | "하지 않는 것" 칸 |
| 잘 물었나·잘 골랐나 (한도 없음의 대신) | 질문 적중률·먼저 물은 것·반복, 단서 자료를 연 시점, 방해 자료에 기댄 결론 (§4.5) |

수준 기준 예 [제안]:
- 1: 요청 글을 다시 쓴 수준. 질문이 없거나 요청 글에 있는 것만 묻는다.
- 3: 공개 요구 대부분을 짚고 가정을 적는다. 숨은 요구는 못 짚는다.
- 5: 숨은 요구 하나 이상을 위험으로 짚고, 질문으로 확인하거나 확인 못 했음을 가정으로 남긴다.

채점 방식 [제안]: LLM 1차 대조(정의서 문장 ↔ 명세 id, **id 목록과 인용만** 출력, provenance 기록) + 사람 최종 판단 (고영향 AI).
지원자 정의서는 지원자 데이터다 — 외부 LLM 으로 보내기 전 개인정보 거르기 필요 (불변식 2 취지). 채점을 P1 과 응시 플랫폼 중 어디서 돌릴지 [미정].

## 8. 진행자·전달

- `FacilitatorView` 에 `stage0` 을 더한다: `time_limit_min`, `request`, `facts`(두 층 답 규칙 그대로 — `ANSWER_RULE`). 한도는 없고(`None`),
  규칙에 "질문 하나에 사실 하나, 나열 질문은 답하지 않음, 모든 질문·자료 요청을 시각과 함께 기록"을 더한다 (§4.5).
  `covers` 는 진행자에게 주지 않는다 (지금 `reveals` 를 빼는 것과 같은 원칙 — 응답 모델에 없으면 새지 않는다).
- 응시용 묶음: 0단계에서는 1단계 README·계약이 보이면 안 된다. 응시용 이미지에 README 가 들어 있으므로
  (a) 0단계 요청 글을 따로 주고 이미지는 0단계 제출 뒤 내준다 / (b) 이미지는 주되 README 를 진행자가 나중에 준다 — 응시 플랫폼과 정한다 [미정].
- 판정 방식은 지금 키워드(`match_terms`) 매칭 유지 [제안]. 키워드 + LLM 보조(사실 id 선택만, temperature 0, 판정 근거 기록, 질문당 하나·열거 질문 차단)는
  응시 플랫폼과 재현성 기준(같은 질문 → 같은 사실 비율)을 정한 뒤 [미정].
