## 0. 요약

- 기능형 과제 **1단계를 "분석 + 구현"으로 바꾼다**. 지원자는 정해진 요구 사항 대신 **모호한 업무 요청**을 받고, 구현하면서 진행자에게
  묻고 자료를 열어 요구를 파악한다. 따로 떼어 낸 분석 단계(0단계)는 두지 않는다 [확정: 2026-11-13 사용자].
- 단계는 지금처럼 둘이다: **1단계 분석·구현 40분 → 2단계 디버깅 20분** (총 60분, `FEATURE_BUILD_MIN, FEATURE_DEBUG_MIN` 그대로).
  분석에 얼마를 쓸지는 지원자가 정한다.
- 공식 요구 사항·공개 수용 기준은 README 에 싣지 않고 **물어야 알 수 있는 요청자 지식**으로 둔다. 계약(API·화면·명령 형식)과 시작 코드는 지금처럼 처음부터 준다.
- 응시 화면의 대화는 **두 채널로 나뉜다** [확정: 2026-11-13 사용자 — 응시 화면 "AI 도우미" 패널]: **AI에게**(코드 설명·수정·테스트 작성 — 코드 생성만)와
  **진행자에게**(요구 사항 질문). **요구는 진행자에게 물을 때만 열린다** — AI 도우미는 요청자 지식을 모른다 (§4.5).
- **진행자는 프로그램이다** [확정: 2026-11-13 사용자] — 사람·LLM 이 아니라 정해진 규칙으로 승인된 문장을 고른다 (§4.6).
- 생성 순서는 **명세를 먼저 다 만들고 → 그것을 흐려 요청 글을 만든다** (§5). **계약 누출 검사는 빌드 단계**에서 한다 — 계약은 명세 승인 뒤에 생긴다 (§5.2).
- **질문·자료 요청 횟수 한도를 두지 않는다** — 1·2단계 모두 [확정: 2026-11-13 사용자]. 횟수 대신 무엇을·언제·얼마나 정확히 묻고 열었는지를 채점한다 (§4.4).
- 분석 결과는 1단계 제출물의 **문제 정의 메모**로 낸다 (지금 "설계 메모"를 넓힘). 별도 제출·공개 관문은 없다.

이력: #151 처음 안은 "요구 항목을 감췄다가 질문하면 연다", 다음 안은 "0단계 분석 → 제출하면 공식 요구 공개 → 1단계 구현"이었다.
0단계를 따로 두면 시간을 나눠야 하고(15/35/20 등) 빈 정의서를 내고 넘어가는 길이 생겨, 0·1단계를 합쳤다.
#151 검토 댓글(2026-11-13)로 계약 누출 검사 위치·요구↔테스트 연결·`c#` 대비책·진행자 규칙·40분 가능성 평가를 고쳤다.

## 1. 왜 필요한가

- 지금 README 에는 제목·상황·**요구 사항·공개 수용 기준**·계약·제출물이 처음부터 다 보인다. 지원자는 "무엇을 만들지"가 정해진 상태에서 시작한다.
  실무 요청은 대개 그렇게 정해져 오지 않는다 — 무엇이 문제인지 묻고 정의하는 것이 경력자를 가르는 지점이다.
- 기능 구현은 코딩 AI 가 가장 잘하는 일이라 AI 대리 풀이 위험이 크다 (`feature-task-backend.md` §0). AI 는 묻지 않고 그럴듯하게 가정해 구현하는 경향이 있어,
  "무엇을 물어야 하는가"를 과제 안에 넣으면 판별력이 생길 수 있다 — 평가로 확인한다 (§9).
- 이슈형(incident)은 원래 "모호한 증상 → 원인 분석"이다. 기능형 1단계에 같은 성격을 넣는 셈이다.

## 2. 범위

| 포함 | 제외 |
|---|---|
| 기능형(`task_kind=feature`) 공통 과제 1단계의 요청 글·요청자 지식·채점 기준 | 이슈형 (이미 분석형) |
| 요청 글 생성 프롬프트·명세 쪽 검사·명세 승인 화면 표시 | 확장 슬롯·경험 검증 과제 (지금 그대로) |
| 빌드 쪽 계약 누출 검사·빌드 승인 화면 표시 | 대화 화면·제출 수집 (응시 플랫폼 몫) |
| README 템플릿 새 판(요구 절 → 요청 글), 진행자 보기·답 규칙(`FacilitatorView`) | 메모 실제 채점 실행 위치 — §7, [미정] |
| 평가 (AI 단독 풀이로 판별력·40분 가능성 확인) | |

## 3. 흐름

```
1단계 분석·구현 (40분)   요청 글 + 계약 + 시작 코드
                         → 진행자에게 질문·자료 요청 (한도 없음, 언제든)
                         → 구현 · 테스트 · 문제 정의 메모 제출
      ↓ reveal_after: stage1_submitted
2단계 디버깅 (20분)      지금 debug_stage 그대로 (자료 한도 없음)
```

| | 1단계 분석·구현 | 2단계 디버깅 |
|---|---|---|
| 보이는 것 | 요청 글, 계약, 시작 코드, 자료 제목 목록, 제출물 | `debug_stage.scenario` 등 (지금 그대로) |
| 진행자에게 물으면 주는 것 | 요청자 지식(§4.2): 공식 요구·공개 수용 기준 · 추가 요구 · 1단계 자료 | 2단계 자료 |
| AI에게 | 코드 설명·수정·테스트 작성만 — 요구는 모른다 (§4.5) | 같음 |
| 숨긴 것 | 숨은 요구·숨김 수용 기준·허용 설계 | 증상의 원인 |
| 산출물 | 핵심 구현·테스트·**문제 정의 메모** | 진단·수정 |

## 4. 1단계 구조

### 4.1 요청 글 (`request`)

- README 의 "상황·요구 사항·공개 수용 기준" 자리를 대신한다. 요청자(가상 기획자·운영 담당) 말투의 짧은 업무 요청 300자 안팎,
  재료 `business_need` 수준의 "무엇이 필요한가"만 쓴다.
- **쓰지 않는 것**: 공개 수용 기준 문장, 수치(수량·요청량·시간 조건), 운영 조건(`trigger_terms`), 숨은 요구 핵심어(`leak_terms`·`first_mention_of` 개념), 구현 방법.
- 공식 요구(`requirements`) 중 일부만 흐리게 담는다 — 다 담으면 분석할 것이 없고, 하나도 안 담으면 무엇을 물을지 실마리가 없다. 기준은 §5.1 검사.
- 진행 안내(진행자에게 물을 수 있음, 자료 목록, 제출물)는 코드가 README "진행 방식"에 붙인다 (`process_markdown`).

### 4.2 요청자 지식 (`facts`) — 물으면 주는 답

| 칸 | 내용 |
|---|---|
| `fact_id` | `f1`… |
| `covers` | 이 사실이 드러내는 명세 항목 id — `r#`(공식 요구) · `p#`(공개 수용 기준, `PublicAcceptance.ac_id` `^p\d{1,2}$`) |
| `topic` · `match_terms` · `answer` · `answer_hint` | 지금 `Clarification` 과 같은 두 층 답 [확정: 2026-11-06 사용자] — 고르기만, 문장 안 바꿈 |

- 공식 요구·공개 수용 기준마다 그것을 덮는 사실이 하나 이상 있어야 한다 — 물어서 알 수 없는 요구로 채점하면 안 된다.
- 추가 요구(`c#`, 함정 단서)는 지금 `clarifications` 그대로 같은 대화에서 쓴다.
- 자료는 지금 1단계 자료(`artifacts`) 그대로, 요청하면 공개.

### 4.3 문제 정의 메모 (1단계 제출물)

지금 기능형 제출물의 "설계 메모(결정·근거·AI 에 맡긴 것)"를 넓힌다. 양식은 고정, 내용은 자유:

1. 해결할 문제 (누구의 무엇)
2. 범위 — 하는 것 / 하지 않는 것
3. 가정 — 확인하지 못해 가정한 것
4. 위험·엣지 케이스
5. 설계 결정과 근거
6. AI 에 맡긴 것과 확인한 방법

따로 먼저 내는 관문은 없다 — 구현과 함께 낸다.

### 4.4 한도 없음 [확정: 2026-11-13 사용자]

질문 횟수(추가 요구·요청자 지식)와 자료 요청 횟수(1단계 자료·`debug_stage` 자료)에 **한도를 두지 않는다**. 상한은 제한 시간이다.

- 왜: 재려는 것은 "무엇을 물어야 하는가"다. 횟수를 막으면 아끼는 요령을 재게 된다. 실무에도 질문·자료 열람 횟수 제한은 없다.
- 잃는 것과 대응:

| 한도가 하던 일 | 한도 없이 대신 하는 것 |
|---|---|
| 자료를 골라야 하게 함 — '자료 전부 제공' 과제는 AI 단독 풀이에 풀렸다 (스키마 결정 표 2026-11-03) | 자료 열람 **순서·시각**을 기록해 채점: 단서(key) 자료를 언제 열었는지, 방해(distractor) 자료에 기대 결정했는지, 메모에 연 자료를 근거로 썼는지 |
| 키워드 뿌리기 방지 — 질문을 낱말만 바꿔 계속 보내면 구체 답(`match_terms`)이 다 열림 | **질문 하나에 답 하나** (§4.6 순서). 같은 항목을 다시 물으면 같은 답 — 새 정보 없음 |
| 함정 단서(`c#`)를 골라 묻게 함 — 지금은 추가 요구 2~5개 중 최대 2개(`MAX_CLARIFICATIONS = 2`, `spec/feature.py:229`·`:267`) | 정확히 짚지 않은 질문엔 모호한 답(`answer_hint` = 볼 곳)만 나간다. 그래도 공식 요구를 묻는 김에 `c#` 단서가 다 열릴 수 있다 — **§9 ③이 깨지면 `c#` 질문 한도만 먼저 되돌린다** [제안] |
| 질문을 고르게 함 | 채점이 **질문 적중률**(§4.6 정의), 먼저 물은 것, 반복을 본다 |

- 질문·자료 요청은 **전부 시각과 함께 기록**한다.
- 관찰 종류(`Observable.kind`, `schemas/domain.py:312`)에 요청자 지식 질문 `asks_fact`(f#) 를 더할지, `asks_clarification` 의 값 공간을 넓힐지 [미정 — 스키마 PR 전에 정한다].
- 효과는 평가로 확인한다 (§9): "닥치는 대로 묻고 다 여는" AI 전략이 수준 5에 닿으면 한도 없음을 다시 본다.
- 응시 화면의 지금 안내("진행자 질문은 최대 2번", "진행자 질문 2/2")는 한도 없음에 맞춰 바꿔야 한다 — 응시 화면 담당 몫.

### 4.5 두 대화 채널 — AI에게 / 진행자에게 [확정: 2026-11-13 사용자]

응시 화면 "AI 도우미" 패널은 대화 상대를 고르게 되어 있다.

| | AI에게 | 진행자에게 |
|---|---|---|
| 하는 일 | 코드 설명·수정·테스트 작성. 수정한 코드는 에디터에 바로 반영 | 요구 사항 질문에 답 — 요청자 지식(`facts`)·추가 요구(`clarifications`)·자료 |
| 답 만드는 법 | 코딩 모델 생성 | **프로그램이 승인된 문장에서 고르기만** (§4.6, 결정적) |
| 아는 것 | 지원자에게 보이는 것(요청 글·계약·시작 코드·지원자 코드)과 지원자가 대화에 붙여 넣은 것만 | 명세의 진행자 보기(`FacilitatorView`) |
| 모르는 것 | 요청자 지식·추가 요구·열지 않은 자료·숨은 요구 전부 | 숨은 요구·허용 설계·`covers`·`reveals` |
| 한도 | [미정] — 응시 플랫폼 정책 | 없음 (§4.4) |

- **요구는 진행자에게 물을 때만 열린다.** AI 도우미에 요구 칸을 넣지 않는다 — 넣으면 지원자가 AI 에게 "요구 다 알려 줘"로 분석을 건너뛴다.
- 지원자가 AI 에게 요구를 묻거나, 요구가 다 열리지 않은 채로 AI 에게 구현을 맡기면 AI 는 요구를 모른다.
  **AI 는 보통 코딩 AI 처럼 그럴듯하게 가정해 답하고 구현한다 (b)** [확정: 2026-11-13 사용자].
  버린 안 (a) "업무 요구는 진행자에게 확인하세요"로 돌려보냄 — 공정하지만 AI 의 가정을 검증하는지(`ai_axes` verification)를 못 본다.
- 두 채널 기록 모두 시각과 함께 남긴다. AI 채널 기록은 `ai_axes`(delegation·verification) 근거, 진행자 채널 기록은 분석 근거.

#### 요구가 다 열리지 않은 상태에서 AI 가 구현할 때 (b) [제안]

1. **AI 도우미 지시는 중립으로 둔다.** 코딩 도우미 역할과 지원자에게 보이는 것(요청 글·계약·시작 코드·지원자 코드)만 준다.
   "요구를 지어내라"도, "요구를 모르니 경고하라"도 넣지 않는다 — 일부러 틀리게 하지도, 일부러 도와주지도 않는다.
   그러면 AI 는 흔한 코딩 모델처럼 빈 요구를 흔한 가정으로 채운다 (가정을 말할 때도, 말하지 않을 때도 있다 — 그것도 실무와 같다).
2. **모든 지원자가 같은 AI 를 쓴다.** 모델·버전·설정·지시문 판을 공고 과제 판마다 고정하고 기록한다 (provenance). AI 답 자체는 지원자마다 달라질 수 있으므로
   AI 출력이 아니라 **지원자가 그것을 확인했는지**를 채점한다.
3. **AI 출력을 기록한다.** 질문·답·코드 변경(에디터 반영분)을 시각과 함께. 채점 때 "AI 가 가정해 만든 요구"를 찾는 근거.
4. **채점 — 한 증거는 한 곳에서만 깎는다.** AI 가 가정해 구현한 요구를 지원자가 확인 없이 둔 경우:
   - 그 요구는 §7.1 표에서 "묻지 않음" 행으로 센다 (가정이 맞으면 메모에 적었는지에 따라 인정/분석 점수 없음, 틀리면 분석 문제).
   - `ai_axes` verification 은 **확인한 경우의 가점**으로만 쓴다 — AI 가정을 진행자에게 확인했거나, 메모 "AI 에 맡긴 것과 확인한 방법"에 적은 경우.
     같은 누락을 분석과 verification 에서 두 번 깎지 않는다.
5. AI 도우미 지시문은 응시 플랫폼 쪽에 있다. 지시문 판이 바뀌면 같은 공고 지원자 간 비교가 깨지므로, 바꾸는 시점을 공통 과제 판과 맞추는 규칙을 응시 플랫폼과 정한다 [미정].

### 4.6 진행자 답 규칙 — 프로그램 [확정: 2026-11-13 사용자 — 진행자는 프로그램]

진행자는 사람·LLM 이 아니라 프로그램이다. 같은 질문에는 늘 같은 답이 나가야 한다 (같은 공고 지원자 간 비교, 고영향 AI 재현성).
지금 규칙(`ANSWER_RULE`, `starter/facilitator.py:19`)은 "주제가 맞으면 `match_terms` 로 구체·모호한 답을 고른다"뿐이라,
한 질문이 여러 항목에 걸릴 때의 순서가 없다. 다음으로 넓힌다 [제안]:

1. 후보 = 요청자 지식(`f#`)과 추가 요구(`c#`) 전부. 질문을 정규화(공백·대소문자·조사 떼기 — 지금 `match_terms` 정리 규칙과 같게)한 뒤
   각 후보의 **맞은 `match_terms` 수**와 **주제(`topic`) 낱말 겹침 수**를 센다.
2. 맞은 `match_terms` 가 있는 후보가 있으면 → 맞은 수가 가장 많은 것, 같으면 **항목 id 순**(`f` 먼저, 그다음 `c`, 번호 순) 하나에 **구체 답**(`answer`).
3. 없고 주제 낱말이 겹치는 후보가 있으면 → 겹침이 가장 많은 것(같으면 id 순) 하나에 **모호한 답**(`answer_hint`, 없으면 `answer`).
4. 어느 것에도 걸리지 않으면 → "추가로 드릴 정보가 없습니다" (지금 규칙과 같음).
5. 한 질문에 답은 **하나만**. 같은 항목·같은 층을 다시 고르면 같은 문장을 다시 준다.

- **나열 질문 거절은 두지 않는다** [제안] — "무엇을 물을 수 있나"는 낱말 매칭으로 가릴 수 없다. 대신 질문 하나에 답 하나(5)와 적중률 채점이 뿌리기를 손해로 만든다.
- **질문 적중률 정의** [제안]: 구체 답(2) = 적중 1, 모호한 답(3) = 부분 0.5, 걸리지 않음(4) = 0. 이미 받은 답을 다시 받은 질문은 반복으로 따로 센다 (적중에 넣지 않음).
- 이 규칙은 진행자 보기(`FacilitatorView.rule`)에 글로 적고, 같은 규칙을 코드로도 둔다 — 평가의 요청자 흉내(§9)와 응시 플랫폼이 같은 구현을 쓰게 한다 (위치는 응시 플랫폼과 합의).

- 입력: 기능형 과제의 공개 칸(제목·상황·요구·공개 수용 기준), 추가 요구, 재료 `business_need`. **숨은 요구·허용 설계는 넣지 않는다**.
- 계산할 수 있는 칸(id 번호·`covers` 대조·진행 안내)은 코드가 채운다 (`draft_feature_task` v4 와 같은 원칙).
- 공통 과제는 공고 단위로 한 번 만들고 저장소(`CommonRef`)를 재사용하므로, 요청 글도 공통 과제 판의 일부로 같이 저장·재사용된다.

### 5.1 명세 쪽 검사 (계약 없음) [제안]

- 결정적: 요청 글에 `trigger_terms`·`leak_terms`·`first_mention_of` 개념·숫자 없음 / 공개 수용 기준 문장과 겹침 낮음 /
  모든 `r#`·`p#` 가 어떤 사실의 `covers` 에 있음 / 사실 답에 숨은 요구 핵심어 없음 (`check_hints` 재사용).
- 흐림 정도: 요청 글이 직접 말하는 `r#` 비율 — 너무 높으면·0 이면 재요청. 1차 낱말 겹침, 2차 판정 LLM [미정: 기준값].

### 5.2 계약 누출 검사 — 빌드 단계 [제안]

계약은 명세 승인 **뒤** 빌드의 `plan_contract` 가 만든다 — 명세 그래프에는 계약이 없어 명세 단계에서는 검사할 수 없다.

- 요구를 README 에서 뺐으므로 계약이 요구를 대신 말하면 안 된다. **백엔드도 작지 않다**: 응답 결과 값 목록·오류 코드만으로 요구가 드러난다
  (부록: 결과 값 성공·소진·이미 발급 → r1 회원당 한 번·r3 소진 안내). 프론트는 화면 요소 test id·문구·배경 요청까지 더해 더 크다 (#151 첫 댓글).
- 처리 방식 [제안]: **`plan_contract` 가 숨긴 공식 요구를 알고 계약을 짓는다** — 입력에 "README 에 싣지 않는 요구"를 표시해 주고,
  그 요구에 딸린 계약 요소(응답 값·오류 코드·test id·문구)는 **중립 이름**(예: 결과 값 `result: OK|REJECTED` + 사유 코드는 요구를 말하지 않는 일반어)으로 짓게 한다.
  - 버린 안 "계약에서 드러나는 요구는 처음부터 공개 요구로 둠" — 빌드가 끝난 뒤 요청 글을 고치는 일이라 명세 새 판·재승인으로 이어진다.
- 검사: `starter/contract.py` 의 숨은 요구·운영 조건 낱말 검사(`hidden_terms` :847, `_leaks` :857)와 공개 요구 → 계약 요소 대응(`TaskContract.covers`, `schemas/build.py:462`)에
  "숨긴 공식 요구를 드러내는 계약 요소" 검사를 더한다 — 숨긴 요구의 `covers` 에 걸린 요소 이름·값에 그 요구·공개 수용 기준의 핵심어가 있는지. 결과는 빌드 승인 화면(#130).
- `plan_contract` 는 시작 코드 빌드 생성기라, 새 vN 을 만들면 같은 변경에서 `CURRENT` 를 올리고 `PROMOTIONS.md` 에 근거와 첫 평가를 적는다 (불변식 7 예외).

## 6. 스키마·템플릿 초안 [제안]

`TaskItem` 에 다음을 더한다 — 기능형 전용(`FEATURE_FIELDS`), 예전 판·이슈형은 비어 있음 (하위 호환).

```yaml
request: "<요청 글>"                       # 있으면 README 의 상황·요구·공개 수용 기준 자리를 대신함
facts: [{fact_id, covers: [r#|p#], topic, match_terms, answer, answer_hint}]
acceptance_public: [{ac_id: p#, text, req_ids: [r#]}]   # 새 칸 req_ids — 공개 수용 기준 → 공식 요구 (§7.1)
# max_clarifications · max_requests · debug_stage.max_requests → None (한도 없음, §4.4)
```

- **공개 수용 기준 → 공식 요구 연결** (`PublicAcceptance.req_ids`): 지금 공개 테스트는 공개 수용 기준에만 묶이고(`PublicTest.ac_id`, `schemas/build.py:440`),
  `PublicAcceptance` 에는 요구 링크가 없다. 요구별 채점표(§7.1)가 테스트 결과를 요구로 모으려면 이 칸이 필요하다. 공개 수용 기준마다 하나 이상 [제안].
- **한도 `None`**: 명세 칸(`TaskItem`)·평가 키트·진행자 보기는 이미 `None` 을 받고, README 진행 방식(`render.process_markdown` :156)도 `None` 이면 숫자를 뺀다.
  한도를 숫자로 다루는 곳은 **생성 쪽**이라 그쪽을 바꾼다:
  - 출력 모델 `DraftFeatureOutput`(`schemas/draft.py:112, 114` — `max_requests`·`max_clarifications` 1~4 필수)과 그 검사(`spec/feature.py:655`)·수리(`:857`).
  - 한도를 정하는 코드(`MAX_CLARIFICATIONS` :229, `_limit` :232, :267)와 **상황 글·2단계 증상 글에 한도 문장을 붙이는 코드**(:286–295,
    "아래 자료 중 최대 N개를 요청해 볼 수 있고, 질문은 최대 M개까지") — 승인 대상 글에 한도가 들어가므로 이 문장도 함께 바꾼다.
- README 템플릿은 스택마다 **새 판**(`templates/<stack>/vN+1/README.tpl.md`)으로: "요구 사항"·"공개 수용 기준" 절 대신 "요청" 절. 계약·코드 구조·실행·채점 방법 절은 그대로.
  "진행 방식"에 "진행자에게 물어 요구를 확인한다"를 넣는다. 공개 테스트 목록은 싣지 않는다 (공개 수용 기준을 드러내므로).
- 관찰 종류 `asks_fact` 를 더하면 `Observable.kind`(`schemas/domain.py:312`)도 이 PR 에서 (§4.4 [미정] 먼저 결정).
- `docs/design/task-spec-schema.md` + `schemas/domain.py` 를 같은 PR 에서 고친다 (스키마 SSOT 규칙).

## 7. 채점 (Evidence model)

### 7.1 요구별 칸 나누기 — 이중 감점 막기

요구를 물어야 알 수 있으므로, 공식 요구(`r#`)마다 "알았나 × 만들었나"로 한 칸에 넣고 **한 번만** 깎는다.
"만들었나"는 그 요구에 걸린 공개 수용 기준(`p#`, `req_ids` 로 연결)의 테스트 결과로 본다.
"알았나"는 그 요구를 `covers` 에 가진 사실(또는 그 요구에 걸린 `p#` 를 덮는 사실)을 구체 답으로 받았는지로 본다.

| | 테스트 통과 | 테스트 실패 |
|---|---|---|
| 물어서 앎 (사실 구체 답) | 정상 | 구현 문제 |
| 묻지 않음, 메모에 가정으로 적음 | 가정이 맞음 — 인정 | 분석 문제 (가정이 틀림) |
| 묻지 않음, 메모에도 없음 | 우연히 맞음 — 분석 점수 없음 | 분석 문제 |

- 질문 한도가 없으므로 모든 요구는 물으면 알 수 있다 — 몰라서 못 만든 것은 분석 문제로 본다.
- 모호한 답만 받은 요구는 "묻지 않음"과 "물어서 앎" 사이 — 메모에 가정으로 적었는지로 가른다 [제안].
- 숨은 요구(t#)는 지금 기능형 채점 그대로 (`catches_trap`, 숨김 수용 기준, 허용 설계).

### 7.2 문제 정의 메모

| 본다 | 근거 |
|---|---|
| 공식 요구·공개 수용 기준을 얼마나 짚었나 | `r#`·`p#` ↔ 메모 문장 |
| 숨은 요구를 위험으로 짚었나 | `t#` ↔ "위험·엣지 케이스" 칸 |
| 가정을 드러냈나, 물어서 확인했나 | "가정" 칸 · 대화 로그 |
| 잘 물었나·잘 골랐나 (한도 없음의 대신) | 질문 적중률(§4.6)·먼저 물은 것·반복, 단서 자료를 연 시점, 방해 자료에 기댄 결정 (§4.4) |
| AI 가정을 확인했나 (§4.5, 가점만) | AI 채널에서 나온 요구 가정 ↔ 진행자에게 확인한 질문 · 메모 "AI 에 맡긴 것과 확인한 방법" 칸 |

수준 기준 예 [제안] (근거 수행준거 id 필수 — 지금 규칙):
- 1: 요청 글만 보고 구현. 질문이 없거나 요청 글에 있는 것만 묻는다.
- 3: 공식 요구 대부분을 물어 확인하고 가정을 적는다. 숨은 요구는 못 짚는다.
- 5: 숨은 요구 하나 이상을 위험으로 짚고, 질문으로 확인하거나 확인 못 했음을 가정으로 남겨 구현에 반영한다.

채점 방식 [제안]: 메모 ↔ 명세 id 대조는 LLM 1차(**id 목록과 인용만** 출력, provenance 기록) + 사람 최종 판단 (고영향 AI).
지원자 메모·질문은 지원자 데이터다 — 외부 LLM 으로 보내기 전 개인정보 거르기 필요 (불변식 2 취지). 채점을 P1 과 응시 플랫폼 중 어디서 돌릴지 [미정].

| AI 단독 풀이 | 코딩 모델에 요청 글·계약·시작 코드만 주고 요청자 흉내(§4.6 규칙 코드)와 대화하며 구현 → §7 로 채점. 진행자에게 묻지 않고 AI 가정만으로 구현한 경우를 따로 돌려 (b)의 함정 효과를 본다 | ① 모델 실력 순서대로 수준이 벌어짐 ② 묻지 않고 구현한 경우와 물은 경우의 차이가 보임 ③ 최상위 모델의 숨은 요구 포착률이 지금 기능형보다 높지 않음 — **③이 깨지면 `c#` 질문 한도만 먼저 되돌린다** (§4.4) |
| 한도 없음 점검 | "닥치는 대로 묻고 자료를 다 여는" 전략을 따로 돌림 | 그 전략이 수준 5에 닿지 않음 — 닿으면 한도 없음(§4.4)을 다시 본다 |
| 지금 기능형과 비교 | 같은 과제를 요청 글 판 / 지금 README 판으로 AI 단독 풀이 | 요청 글 판이 판별력을 올리는지 — 안 올리면 기본값으로 켜지 않는다 |

## 11. 불변식 점검

## 부록 — 가상 예시 (형식 설명용, 실제 생성물 아님)

`feature-task-backend.md` 부록의 "이벤트 쿠폰 발급 API" 과제를 요청 글 판으로 바꾸면:

- request: "이번 주말 이벤트 때 선착순 쿠폰을 뿌리려고 해요. 기존 쿠폰 서비스에 발급 기능을 붙여 주실 수 있을까요? 다음 주에 오픈이에요."
  (수량·회원당 횟수·응답 종류를 말하지 않음 — r1·r2·r3·p# 는 물어야 알 수 있음)
- acceptance_public: p1 "수량이 0이 되면 '소진'을 응답한다" (req_ids [r2, r3]) …
- 계약 (빌드): `POST /events/{id}/coupons` 응답 `{result: ...}` — 결과 값을 `ISSUED|SOLD_OUT|ALREADY_ISSUED` 로 지으면 r1·r3 이 드러난다 →
  §5.2 중립 이름 예: `result: OK|REJECTED` + `reason` 은 계약에 값 목록을 싣지 않거나 일반 코드로.
- facts:
  - f1 covers [r1] "한 사람이 여러 번 받을 수 있나요?" → "회원당 한 번이에요."
  - f2 covers [r2] "수량은 어떻게 정하나요?" → "이벤트마다 정해 둔 수량만큼이요." / 모호: "이벤트 설정에 따라 달라요."
  - f3 covers [r3, p1] "다 떨어지면 어떻게 보여 주나요?" → "'소진'이라고 알려 줘야 해요."
- clarifications (그대로): c1 요청량(t1 단서) · c2 앱 재시도(t2 단서).
- 진행자 답 (§4.6): "수량이랑 요청량이 어떻게 되나요?" → f2·c1 둘 다 낱말이 맞으면 맞은 수가 많은 쪽, 같으면 f2 — 답은 하나. c1 은 다시 물어야 열린다.
- 수준 5 메모 예: 위험 칸에 "오픈 직후 요청이 몰리면 남은 수량을 넘겨 발급될 수 있음 — 요청량 확인함(c1)",
  "응답이 늦으면 앱이 다시 보낼 수 있음 — 확인 못 해 중복 발급 방지를 가정으로 두고 구현함".
