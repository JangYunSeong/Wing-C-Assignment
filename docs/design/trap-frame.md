## 2. 위치와 흐름 [제안]

```
⑥ 사례 확인 → ⑦ 역량 → ⑧ seed: 기능형 재료(interview_feature_seed) → 재료 분석(analyze_material) → [함정 틀 → 틀 적용 재료]
   → 명세 초안(draft_feature_task) → … → ⑨ 승인(틀 적용 재료 저장, §3.2) → 빌드: 계약(plan_contract) → 생성기 → 관문
```

- 별도 층을 만들지 않는다. 틀은 ⑧ seed 단계의 재료 분석 옆에 둔다. 같은 입력(가명화 재료 블록 — `material_block` 이 만들어 `material` 칸으로, 템플릿 정보 `template_json`)을 쓰기 때문이다.
- **틀이 명세 초안 입력만 바꾸면 원인 1(a)를 못 막는다.** '공개 쪽 금지'는 계약 단계로도 가야 한다. 계약 생성 입력(`plan_contract` 의 `needs_text`·`forbidden_text` 자리)과 계약 검사(`contract._needs`·검사 4)에도 넣는다.
- **계약 단계는 생성 표시를 보지 않는다.** 생성 표시(`InterviewGeneration`)는 생성 중에만 있고 과제를 저장하면 비운다. 빌더는 명세의 `source_incident` 로 재료를 다시 읽는다 — 공개 사례는 파일, 회사 사례는 DB 이고 등록한 뒤 내용이 바뀌지 않는다 (`builder/steps.py` `incident_for`, `spec/company_incidents.py`). 그래서 틀은 생성 표시를 타고 명세 초안까지만 간다. 계약 단계에 닿으려면 저장할 자리가 따로 있어야 한다 (§3.2).
- **범위 [제안]**: 사례 출처 셋(`known_problem` 인터뷰·`company` 회사·`public_fixed` 공개) 가운데 인터뷰·회사 사례에만 틀을 만든다. 공개 재료(인터뷰의 `public_fixed`, 일반 파이프라인 `spec/feature.py`)는 #301 결정대로 평가로만 본다. #308 본문은 검사 4 를 '공개 재료에도 쓰는 일반 규칙'으로 두었지만, 검사 4 는 틀의 `public_forbidden` 으로 재므로 틀이 없는 공개 재료에서는 돌지 않는다.
- 회사 사례(co:)의 틀을 쓸 때마다 만들지는 [미정]이다 (§10, 저장 자리와 함께 정한다). 재료 분석은 템플릿 판에 따라 결과가 달라져 쓸 때마다 돈다(#316).

## 3. 스키마 [제안]

### 3.1 틀

재료는 '무슨 사고인가'를 담고, 틀은 '이 공고에서 무엇을 숨기고 무엇을 공개하나'를 담는다.

| 칸 | B 동작 함정 | A 설계 함정 |
|---|---|---|
| `kind` | `behavior` | `design` |
| `hidden_requirement` | 관찰 가능한 동작 (예: DB 조회 실패를 만료 401 로 처리하지 않는다) | 재료의 숨은 요구 그대로 + 저장 방식을 막았을 때만 설계 조건 한 문장 (예: 세션 검증 경로가 DB 커넥션을 쓰지 않는다). 2단계 평가에서 다시 쓰게 했더니 재료 조건이 빠졌다 |
| `public_rules` | 오류 응답 규칙 — **특정 코드**(예: 의존 실패는 503). '401 아님' 같은 부정형은 쓰지 않는다 | 운영 조건 (풀 크기·DB 지연 가능성·피크 동시 요청) — 공개 글이나 facts 로 |
| `public_forbidden` | 흔한 구현의 기전을 드러내는 말 | 흔한 구현의 저장 방식 (예: Session 을 DB 엔티티로) — 엔티티 단위, 낱말은 따로 |
| `design_matrix` | 허용 설계 × 공개 요구 대조 (`holds`: yes·no·partial, 이유). 사람이 뺀 설계는 틀 적용 재료에서 빠진다 | 같음 |
| `reason` · `evidence` | 실패 사유(템플릿 `failure_reasons` code)와 그 사유의 **필수 근거**(기전). 수치는 넣지 않는다 | 같음 |
| `gaps` | 근거 빈칸 → 보강 질문 재료 | 같음 |

B 는 운영 조건과 흔한 구현이 깨지는 이유도 재료와 달라진다. 그래서 B 틀은 그 둘(재료 `trigger`·`why_naive_breaks` 자리)도 낸다.

provenance 는 다른 LLM 산출물과 같다 (`prompt_id@version+hash`, 모델·설정, `ontology_version`).

### 3.2 틀 적용 재료와 저장 [제안 · 저장 자리는 미정]

등록 재료(`FeatureSeed`)는 바꾸지 않는다. 하지만 틀만 따로 실어 보내면 명세·계약에 반영되지 않는다. 지금 코드는 재료 칸을 그대로 쓴다.

| 단계 | 재료에서 그대로 쓰는 것 |
|---|---|
| 명세 초안 | 숨은 요구(함정 설명 = `hidden_requirement`·`trigger`·`naive_impl`·`why_naive_breaks`)와 허용 설계(`accepted_designs`). LLM 이 아니라 코드가 복사한다 (`spec/feature.py` `fill_from_seed_v4`, v12 도 이 경로) |
| 계약 입력 | 템플릿 사유를 `reasons` 로 좁히고 필수 조절값은 `harness` (`plan_contract.for_material`) · `contract_needs` → `needs_text` · 금지 낱말 `hidden_terms` → `forbidden_text` |
| 계약 검사 | `_reasons`(재료 사유 밖이면 거절) · `_needs`(`contract_needs`) · `_leaks`(`hidden_terms`) |

그래서 지금 경로로는 B 틀의 숨은 요구 대신 재료의 숨은 요구가 명세에 복사된다. v6 의 새 B 사유도 재료 `reasons` 에 없으면 계약 입력에서 빠지고 검사에서 거절된다. `design_matrix` 로 JWT(d1)를 빼기로 해도 명세 프롬프트로는 뺄 수 없다.

- **틀 적용 재료**: 틀이 바꾸는 칸만 덮어쓴 `FeatureSeed` 사본이다. 코드가 만든다. 나머지 칸(`business_need`·`stage2_*` 등)은 원 재료 그대로 둔다.
  - `hidden_requirement` ← 틀. B 면 `trigger`·`why_naive_breaks` 도 틀 것으로. A 는 틀이 재료 숨은 요구를 글자 그대로 담을 때만 (`keeps_hidden` — 아니면 재료 것을 두고 검토 표시).
  - `accepted_designs` ← `design_matrix` 에서 사람이 뺀 설계를 제외.
  - `reasons` ← 틀 `reason`. `harness` 는 그 사유에 맞게.
  - `contract_needs` ← 금지된 저장 대상이면 stateful_target 을 뺀다 (§6).
  - `leak_terms` ← `public_forbidden` 의 낱말을 더한다. 그러면 명세 검사(1단계 지원자 화면)·계약 입력(`forbidden_text`)·계약 검사(`_leaks`)가 같은 목록으로 받는다. 저장 방식은 낱말이 아니라 검사 4 가 엔티티 단위로 본다.
- **생성 표시**에는 틀과 틀 적용 재료를 둔다. 명세 초안과 검사 3 이 읽고, 생성이 끊겼다 이을 때도 쓴다.
- **저장 자리 [미정]** (§10). 계약 단계에 닿으려면 빌더가 명세와 함께 읽는 곳에 있어야 한다.
  - (가) 인터뷰 사례는 승인 때 회사 사례로 등록하는 재료와 함께 등록한다. 빌더는 지금 경로(`source_incident`)대로 읽는다. 다만 다른 공고가 이 회사 사례를 다시 쓰면 첫 공고의 틀이 따라간다. 틀은 공고마다 정한다는 §3.1 과 어긋난다.
  - (나) 승인된 공통 과제와 함께 저장하고, 빌더는 그것이 있으면 원 재료 대신 쓴다. 회사 사례를 다시 쓸 때도 공고마다 틀을 둘 수 있다. 'TaskItem 에 재료를 따로 싣지 않는다'(`InterviewSpec`)는 지금 원칙을 바꾸고, 빌더가 읽는 자리가 늘어난다.

## 4. B·A 선택 [미정]

#308 본문은 B(동작 함정)를 기본으로 제안했다. 블랙박스로 시험할 수 있고 설계를 강요하지 않기 때문이다. 팩트체크로 드러난 빈칸은 다음과 같다.

1. **v5 템플릿에 B 를 잴 실패 사유가 없다.** 사유 9개 중 가장 가까운 `injected_failure_ignored` 는 update 실패에 성공 응답(200)이 없는지만 본다. 그래서 401 과 503 을 가르지 못한다. 'select 실패 주입 + 공개 오류 규칙의 특정 코드 단언' 사유를 새 템플릿 판(v6)에 더해야 한다. v5 는 승격 평가 중이니 그대로 둔다.
2. **숨은 기대는 특정 코드로 둔다.** 흔한 구현은 catch 없이 500 을 내서 '401 아님'을 그냥 통과한다 (알파 1).
3. SELECT 실패 주입 도우미(`sqlOn` select 꼴)는 #313 에서 됐다. 손으로 쓴 주입 경로(manifest `table_refs`)는 v6 때 같이 고친다.
4. **B 사유는 틀 적용 재료의 `reasons` 에도 들어가야 한다.** 계약 단계가 템플릿 사유를 재료 사유로 좁히기 때문이다 (§3.2).

정할 것: **B 기본 = v6 작업이 따라온다.** v5 판단 결과가 어차피 v6 을 부르면 B 사유와 `table_refs` 를 그 판에 같이 넣는다. v6 이 필요한 경우는 회귀 알파 실패, 또는 open-in-view 재생에서 숨은 테스트가 설정 하나를 잰다고 나올 때다. v5 가 그대로 오르면 A 를 먼저 하고 B·v6 은 뒤로 미룬다. 틀을 둘 다 만들어 검사하고 통과한 하나로 명세를 쓰는 본문 안은 LLM 호출이 두 배라 [미정]이다 (§10).

## 5. 검사

검사는 막지 않고 표시만 한다 (재료 분석과 같다 — 최종 판단은 사람, 불변식). 다만 검사 4 는 빌드 안전망이라 계약을 재요청한다.

1. **재현 가능성 (코드, 결정적) — 줄인다.** [구현: 3단계 — 근거 표는 템플릿 `failure_reasons[].feasible` 의 when 에 나오는 조절값, 근거는 재료 `harness` ∪ 분석 `split_params`(재료가 harness 를 안 적었으면 분석만), 조절값이 아닌 이름(rows)은 보지 않음] 사유별 필수 근거 표만 둔다 (예: `pool_acquire_timeout` → '동시 요청 ≥ 풀 크기'의 근거 — manifest 성립 조건 `concurrency >= pool_size`, '커넥션을 쥐는 시간'의 근거). 수치는 빌드 보정이 실험으로 정한다 [확정: 2026-11-25]. 템플릿 `tunes`·`feasible` 과 버그 B 검사(#313)가 이미 맡는 부분은 다시 두지 않는다. 근거가 비면 `gaps` 로 넘겨 보강 질문이 된다.
2. **설계 호환 (LLM).** [구현: 3단계 — 틀의 `design_matrix` 를 코드가 ⑧ 설계 질문으로 ('뺀다/남긴다', yes 설계가 남을 때만). '뺀다'면 다음 과제 만들기에서 `apply_frame(removed_designs=)` 가 재료 원문을 앞부분으로 맞춰 뺀다. 허용 설계는 2개 이상이어야 해서 둘뿐이면 대신 인정할 설계를 함께 받아 다음 재료 만들기 문답으로 넘긴다 — 다시 만든 재료가 여전히 둘이면 빼지 않고 표시. '요구 완화'는 재료를 바꾸는 일이라 [미정]] `design_matrix` 로 허용 설계마다 공개 요구를 지키는지 본다. 못 지키는 설계는 빼거나 요구를 완화하는 안을 표시하고, 사람이 고른다. 예: JWT × '접근 때 연장'. 고른 결과는 틀 적용 재료(`accepted_designs`·숨은 요구)로 간다. 허용 설계는 코드가 재료에서 복사하므로 명세 프롬프트 입력만으로는 뺄 수 없다 (§3.2).
3. **공개 중립성 (명세 뒤, LLM + 낱말 대조).** [구현: 3단계 — 코드만 (D7). 1단계 자료 본문·추가 요구 답·사실의 답에서 틀 금지 낱말(업무 요구·운영 조건 낱말에 걸리는 말 제외)과 금지 엔티티의 저장 꼴(테이블 정의·조회 SQL·'<이름> 테이블'·엔티티 클래스·Repository·조회 메서드). 2단계 자료는 보지 않는다 — 흔한 구현의 증상 단서 (v13 평가). 과제 글에서 다시 계산하는 표시] 공개 요구·시나리오만 보면 이번 누설을 못 잡는다. 자료(특히 distractor 역할의 기존 코드), 추가 질문 답, 사실(facts)까지 본다. 낱말 대조에는 `public_forbidden` 을 쓴다. 지금 명세 검사의 `leak_terms` 대조는 1단계 지원자 화면(제목·상황·공개 요구·수용 기준·추가 요구 답·자료 제목)만 보므로, 자료 본문·사실은 이 검사가 맡는다.
4. **빌드 쪽 안전망 (코드, 계약 검사).** 두 갈래다.
   - 저장 방식: 계약 엔티티가 틀이 금지한 저장 방식이면 거절한다. 새 엔티티만 보면 b3 의 Session(`existing=true`)을 놓치므로 새·기존 모두 본다. 낱말 대조로는 못 한다 — `contract_places` 가 식별자를 낱말로 풀어 `sessionId` 같은 공개 칸까지 걸리고, `hidden_terms` 는 공개 업무 요구(`business_need`)에 나온 말('세션')을 뺀다. 그래서 엔티티 단위로 본다.
   - 낱말: `public_forbidden` 의 낱말은 틀 적용 재료의 `leak_terms` 를 거쳐 `hidden_terms` 로 들어가므로, 지금 `contract._leaks` 가 그대로 본다.
   - `contract._needs` 와의 충돌은 §6 에서 정리한다.
   - 시작 코드·README [구현: #332 T-F2]: 같은 금지 목록을 빌드 입력(`ContractResult` → `BuildInputs.forbidden_storage`)으로 넘겨, 정적 검사(`static_check._starter_forbidden_storage`)가 시작 코드의 테이블·엔티티·저장소·조회 메서드 꼴을 생성기 재생성 사유로 막고(발급 값 예외로도 통과하지 않음, 테이블 선언 규칙이 없는 템플릿도) README 는 승인자 표시로 남긴다. 이름 대조는 계약 검사 4·정적 검사가 한 규칙(`starter/forbidden_storage.names_entity` — 끝 낱말들이 같으면, 단·복수 같게: `UserSession`·`user_session` 도 Session)을 쓴다. 틀의 why(LLM 글 — 허용 설계가 들어 있을 수 있음)는 계약 입력·재요청 사유에 싣지 않는다 (#332 B-F10). 생성기 입력에 금지 목록을 알리는 것은 gen_starter 새 판에서 (#332 WP7).
5. **인터뷰 보강.** [구현: 3단계 — 설계 질문 → 재현 근거 → 틀 빈칸 → 분석 빈칸, 합쳐 셋 (D6). 회사 사례는 표시만] #317 첫 판(빠진 정보 → ⑧ 질문 → ⑦ 로 되돌려 다시 만들기) 위에 틀 질문을 더한다. 사유별 필수 근거의 빈칸과, 설계 충돌에서 무엇을 남길지를 묻는다. 회사 사례는 표시만 한다.

## 6. stateful_target (`contract._needs`) [미정 — 틀에 합치기를 제안]

- **지금**: 재료 `contract_needs` 에 stateful_target 이 있으면 계약에 시드 행 + 숨은 케이스 data 를 강제한다. 다른 엔티티에 `existing` 이 하나라도 있으면 `existing: true` 도 요구한다 (`contract._needs` — 안내 문구는 늘 `existing: true`). 그래서 로그인 요청이 만드는 세션을 미리 채운 DB 테이블로 바꾼다. `interview_feature_seed` v1 의 규칙("기존 행과 정해진 전이가 반드시 필요한 경우에만")에도 어긋난다.
- **코드만으로는 못 가른다.** 흔한 구현의 저장 대상인지는 코드가 판단할 수 없다. 그래서 틀의 `public_forbidden`(저장 방식) 한 정의에서 `_needs` 와 검사 4 가 함께 나오게 한다. 금지된 저장 대상이면 틀 적용 재료의 `contract_needs` 에서 stateful_target 을 빼고 표시만 한다.
- **급하지 않다.** 지금 빌드를 막지는 않는다 (알파 2·3 은 이 상태로 review). 따로 고치면 `interview_feature_seed` v2 평가를 한 번 더 해야 한다.

## 7. 프롬프트·평가 [제안]

- **새 task `trap_frame` v1** (`eval: pending`).
  - 입력: 가명화 재료 블록 + 템플릿 정보 + 재료 분석 결과 (+ 보강 문답).
  - 재료 분석과 같은 단계에서 만든다. 생성 표시에는 분석 결과 전체가 아니라 `seed_flags`·`seed_gaps` 글만 남아, 생성이 끊겼다 이으면 분석 결과가 없다.
  - 출력: 틀 (B 면 바뀐 운영 조건·깨지는 이유 포함). 틀 적용 재료는 코드가 만든다 (§3.2).
  - 명세 생성 쪽 프롬프트라 평가를 통과한 뒤에 CURRENT 로 올린다 (생성기 예외가 아님).
- **평가셋 (qwen)**: 이번 세션 유지형(재현 불가 + 설계 강요), 재현 불가형, 정상형 몇 개. dev/test 를 나눈다 (eval-harness).
- **`draft_feature_task` 새 vN** (지금 v12, v13 은 평가만 — 2026-11-26): 틀의 공개 쪽(`public_rules`·`public_forbidden`)을 입력으로 받는다. 금지 엔티티 규칙은 1단계(보이는 곳·1단계 자료·추가 요구 답)로만 — 2단계 자료는 흔한 구현의 증상을 보여야 한다. 숨은 요구·허용 설계는 지금처럼 코드가 재료에서 채우므로 틀 적용 재료를 넘기면 된다. `design_matrix` 로 설계를 빼는 일은 프롬프트에 맡기지 않는다. 평가 뒤 CURRENT.
- **`plan_contract` 새 vN 은 필요할 때만.** 계약 입력의 `needs_text`·`forbidden_text`(공개 계약에 쓰지 않는 말)는 코드가 재료에서 만들어 `seed_rules` 칸에 붙인다 (v32 가 렌더). 틀 적용 재료를 넘기면 둘 다 바뀐다. `forbidden_text` 도 2026-11-10(5cfadc3)에 판을 올리지 않고 생겼다. '금지된 저장 방식은 엔티티로 두지 않는다' 같은 지시문이 따로 필요하면 새 vN 을 만든다. 생성기 예외라 같은 변경에서 CURRENT 를 올리고 PROMOTIONS 에 적는다.

## 8. 다른 관문과의 관계

- **변별 관문 (공개 테스트)**: 시간 규칙은 경계 ±1초 밖에서 재는 도우미(`assertRenewedWhileUsed`·`beforeExpiry`·`afterExpiry`)로 잰다 (#317 묶음, r3). 틀과 별개다.
- **보정 (#310)·함정 관문 (⑪)**: 틀의 `reason`·`evidence` 는 사유와 근거만 넘긴다. 수치는 보정이 정한다.
- **재료 분석 (#311·#316)**: 틀은 분석 결과를 입력으로 받는다. 운영 확인(2026-11-25)에서 분석은 템플릿 v2 에서도 '재현 가능'으로 판정했다 (3차 팩트체크상 v2 에서는 재현되지 않는 재료). 같은 재료(템플릿 v2 2회·v5 2회)에서 빠진 정보 표시도 4회 중 3회만 나왔다. 표시가 빠진 1회가 같은 판 두 회 사이에서 갈렸는지는 운영 기록으로 확인한다. 틀의 재현 판단은 분석 판정만 믿지 말고 검사 1 의 필수 근거 표로 다시 본다.

## 9. 순서 [제안]

1. (운영) v5 판단 → B·v6 결정과 이 문서의 [미정] 확정
2. (v5 판단이 v6 을 부르면) 템플릿 v6 — B 사유·`table_refs` select + 알파 3회 (재료당 1회)
3. `trap_frame` 프롬프트 + 평가셋 → 첫 평가
4. 틀을 쓰는 쪽: 틀 적용 재료(코드)와 저장 자리 → `_needs`·검사 4 (코드, 가상 틀로 단위 테스트) → `draft_feature_task` 입력 연결 (필요하면 `plan_contract` 새 vN) → 평가
5. 검사 2·3 + 검토 표시 → 처음부터 끝까지 알파 3회
6. 보강 질문에 틀 질문을 더한다
