# 함정 틀 (TrapFrame) — 설계 초안

> 상태: **[제안] 초안** (2026-11-25, #308 순서 4). 결정 넷은 [미정]으로 남긴다 (§10). B 기본 여부는 v5 승격 판단(#308 순서 1, 운영 서버) 결과를 보고 정한다.
> 근거: #308 본문, 팩트체크 1~4차 댓글, 정리 댓글(남은 일·순서), 운영 분석(r3 빼먹기, 2026-11-25).

명세를 쓰기 **전에** 함정의 모양을 정한다. 무엇을 숨기고 무엇을 공개하며, 공개 쪽에 무엇을 쓰면 안 되는지, 허용 설계가 공개 요구를 지킬 수 있는지를 먼저 정한다. 그다음 명세·계약 생성과 검사가 그 틀을 따른다.

## 1. 왜

ct-f6087a7ba679(세션 유지 과제)는 빌드 b1~b3·알파에서 모두 실패했다. 공개 계약·허용 설계·숨은 테스트가 서로 맞지 않았다. 팩트체크 뒤의 원인 정리는 아래와 같다.

| 원인 | 팩트체크 뒤 | 이미 고친 것 | 틀이 맡을 것 |
|---|---|---|---|
| 1 공개 쪽이 흔한 구현의 저장 방식을 유도 | 맞음. 샌 경로는 둘: (a) 재료 `contract_needs` 의 stateful_target → 계약 단계 재요청, (b) 명세 자료(기존 코드 `findSessionById`)·추가 질문 답 | — | 공개 쪽 금지 · 검사 3·4 · §6 |
| 2 허용 설계가 공개 요구를 못 지킴 | 맞음. JWT(d1)는 '접근 때 연장'(r3)을 못 지켜 알파 1~3 모두 메모리 만료 맵·세션 저장소를 더해 d2 로 수렴 | — | 검사 2 |
| 3 하네스로 재현 못 함 | 운영 기본(템플릿 v2)에서는 맞음. v4·v5 의 보정으로는 재현 | 보정(#310), 지연 켜기 검사(#313). v5 승격 판단 중 | 검사 1 은 줄인다 |
| 4 원천 근거가 얇음 | 맞음 (수치 미확인·`reviewed=false`) | 빠진 정보 표시(#314), 보강 질문 첫 판(#317) | 보강 질문에 틀 질문 더함 |

빌드를 직접 떨어뜨린 코드 버그(시드 고유 칸 중복, 피크 사유인데 버스트 행 없음)는 #313·#315 에서 고쳤다. 공개 테스트의 시간 경계 문제(r3 빼먹기)는 #317 묶음에서 고친다. 이 셋은 틀과 무관하다.

## 2. 위치와 흐름 [제안]

```
⑥ 사례 확인 → ⑦ 역량 → ⑧ seed: 기능형 재료(interview_feature_seed) → 재료 분석(analyze_material) → [함정 틀]
   → 명세 초안(draft_feature_task) → … → ⑨ 승인 → 빌드: 계약(plan_contract) → 생성기 → 관문
```

- 별도 층을 만들지 않는다. 틀은 ⑧ seed 단계의 재료 분석 옆에 둔다. 같은 입력(가명화 재료 블록 `material_block`, 템플릿 정보 `template_json`)을 쓰기 때문이다.
- **틀이 명세 초안 입력만 바꾸면 원인 1(a)를 못 막는다.** '공개 쪽 금지'는 계약 단계로도 가야 한다. 계약 생성 입력(`plan_contract.needs_text` 자리)과 계약 검사(`contract._needs`·검사 4)에도 넣는다.
- 회사 사례(co:)의 틀을 쓸 때마다 만들지는 [미정]이다 (§10). 재료 분석은 템플릿 판에 따라 결과가 달라져 쓸 때마다 돈다(#316).

## 3. 스키마 [제안]

기능형 재료(`FeatureSeed`)는 그대로 둔다. 재료는 '무슨 사고인가'를 담고, 틀은 '이 공고에서 무엇을 숨기고 무엇을 공개하나'를 담는다. 틀은 생성 표시(`InterviewGeneration`)에 실려 명세·계약 단계로 간다.

| 칸 | B 동작 함정 | A 설계 함정 |
|---|---|---|
| `kind` | `behavior` | `design` |
| `hidden_requirement` | 관찰 가능한 동작 (예: DB 조회 실패를 만료 401 로 처리하지 않는다) | 설계 조건 (예: 세션 검증 경로가 DB 커넥션을 쓰지 않는다) |
| `public_rules` | 오류 응답 규칙 — **특정 코드**(예: 의존 실패는 503). '401 아님' 같은 부정형은 쓰지 않는다 | 운영 조건 (풀 크기·DB 지연 가능성·피크 동시 요청) — 공개 글이나 facts 로 |
| `public_forbidden` | 흔한 구현의 기전을 드러내는 말 | 흔한 구현의 저장 방식 (예: Session 을 DB 엔티티로) — 엔티티·낱말 |
| `design_matrix` | 허용 설계 × 공개 요구 대조 (`holds`: yes·no·partial, 이유) | 같음 |
| `reason` · `evidence` | 실패 사유(템플릿 `failure_reasons` code)와 그 사유의 **필수 근거**(기전). 수치는 넣지 않는다 | 같음 |
| `gaps` | 근거 빈칸 → 보강 질문 재료 | 같음 |

provenance 는 다른 LLM 산출물과 같다 (`prompt_id@version+hash`, 모델·설정, `ontology_version`).

## 4. B·A 선택 [미정]

#308 본문은 B(동작 함정)를 기본으로 제안했다. 블랙박스로 시험할 수 있고 설계를 강요하지 않기 때문이다. 팩트체크로 드러난 빈칸은 다음과 같다.

1. **v5 템플릿에 B 를 잴 실패 사유가 없다.** 사유 9개 중 가장 가까운 `injected_failure_ignored` 는 update 실패에 성공 응답(200)이 없는지만 본다. 그래서 401 과 503 을 가르지 못한다. 'select 실패 주입 + 공개 오류 규칙의 특정 코드 단언' 사유를 새 템플릿 판(v6)에 더해야 한다. v5 는 승격 평가 중이니 그대로 둔다.
2. **숨은 기대는 특정 코드로 둔다.** 흔한 구현은 catch 없이 500 을 내서 '401 아님'을 그냥 통과한다 (알파 1).
3. SELECT 실패 주입 도우미(`sqlOn` select 꼴)는 #313 에서 됐다. 손으로 쓴 주입 경로(manifest `table_refs`)는 v6 때 같이 고친다.

정할 것: **B 기본 = v6 작업이 따라온다.** v5 판단 결과가 어차피 v6 을 부르면 B 사유와 `table_refs` 를 그 판에 같이 넣는다. v6 이 필요한 경우는 회귀 알파 실패, 또는 open-in-view 재생에서 숨은 테스트가 설정 하나를 잰다고 나올 때다. v5 가 그대로 오르면 A 를 먼저 하고 B·v6 은 뒤로 미룬다. 틀을 둘 다 만들어 검사하고 통과한 하나로 명세를 쓰는 본문 안은 LLM 호출이 두 배라 [미정]이다 (§10).

## 5. 검사

검사는 막지 않고 표시만 한다 (재료 분석과 같다 — 최종 판단은 사람, 불변식). 다만 검사 4 는 빌드 안전망이라 계약을 재요청한다.

1. **재현 가능성 (코드, 결정적) — 줄인다.** 사유별 필수 근거 표만 둔다 (예: `pool_acquire_timeout` → '동시 요청 > 풀 크기'의 근거, '커넥션을 쥐는 시간'의 근거). 수치는 빌드 보정이 실험으로 정한다 [확정: 2026-11-25]. 템플릿 `tunes`·`feasible` 과 버그 B 검사(#313)가 이미 맡는 부분은 다시 두지 않는다. 근거가 비면 `gaps` 로 넘겨 보강 질문이 된다.
2. **설계 호환 (LLM).** `design_matrix` 로 허용 설계마다 공개 요구를 지키는지 본다. 못 지키는 설계는 빼거나 요구를 완화하는 안을 표시하고, 사람이 고른다. 예: JWT × '접근 때 연장'.
3. **공개 중립성 (명세 뒤, LLM + 낱말 대조).** 공개 요구·시나리오만 보면 이번 누설을 못 잡는다. 자료(특히 distractor 역할의 기존 코드), 추가 질문 답, 사실(facts)까지 본다. 낱말 대조에는 `public_forbidden` 을 쓴다.
4. **빌드 쪽 안전망 (코드, 계약 검사).** 계약 엔티티가 틀이 금지한 저장 방식이면 거절한다. 새 엔티티만 보면 b3 의 Session(`existing=true`)을 놓치므로 새·기존 모두 본다. 지금 `contract._leaks` 는 숨은 낱말만 보므로 `public_forbidden` 대조를 더한다. `contract._needs` 와의 충돌은 §6 에서 정리한다.
5. **인터뷰 보강.** #317 첫 판(빠진 정보 → ⑧ 질문 → ⑦ 로 되돌려 다시 만들기) 위에 틀 질문을 더한다. 사유별 필수 근거의 빈칸과, 설계 충돌에서 무엇을 남길지를 묻는다. 회사 사례는 표시만 한다.

## 6. stateful_target (`contract._needs`) [미정 — 틀에 합치기를 제안]

- **지금**: 재료 `contract_needs` 에 stateful_target 이 있으면 계약에 `existing: true` + 시드 행 + 숨은 케이스 data 를 강제한다 (`contract._needs`). 그래서 로그인 요청이 만드는 세션을 미리 채운 DB 테이블로 바꾼다. `interview_feature_seed` v1 의 규칙("기존 행과 정해진 전이가 반드시 필요한 경우에만")에도 어긋난다.
- **코드만으로는 못 가른다.** 흔한 구현의 저장 대상인지는 코드가 판단할 수 없다. 그래서 틀의 `public_forbidden`(저장 방식) 한 정의에서 `_needs` 와 검사 4 가 함께 나오게 한다. 금지된 저장 대상이면 stateful_target 을 요구하지 않고 표시만 한다.
- **급하지 않다.** 지금 빌드를 막지는 않는다 (알파 2·3 은 이 상태로 review). 따로 고치면 `interview_feature_seed` v2 평가를 한 번 더 해야 한다.

## 7. 프롬프트·평가 [제안]

- **새 task `trap_frame` v1** (`eval: pending`).
  - 입력: 가명화 재료 블록 + 템플릿 정보 + 재료 분석 결과 (+ 보강 문답).
  - 출력: 틀.
  - 명세 생성 쪽 프롬프트라 평가를 통과한 뒤에 CURRENT 로 올린다 (생성기 예외가 아님).
- **평가셋 (qwen)**: 이번 세션 유지형(재현 불가 + 설계 강요), 재현 불가형, 정상형 몇 개. dev/test 를 나눈다 (eval-harness).
- **`draft_feature_task` 새 vN** (지금 v12): 틀의 `public_rules`·`public_forbidden`·`design_matrix` 를 입력으로 받는다. 평가 뒤 CURRENT.
- **`plan_contract` 새 vN**: `needs_text` 옆에 `public_forbidden` 을 넣는다. 생성기 예외라 새 vN 과 같은 변경에서 CURRENT 를 올리고 PROMOTIONS 에 적는다.

## 8. 다른 관문과의 관계

- **변별 관문 (공개 테스트)**: 시간 규칙은 경계 ±1초 밖에서 재는 도우미(`assertRenewedWhileUsed`·`beforeExpiry`·`afterExpiry`)로 잰다 (#317 묶음, r3). 틀과 별개다.
- **보정 (#310)·함정 관문 (⑪)**: 틀의 `reason`·`evidence` 는 사유와 근거만 넘긴다. 수치는 보정이 정한다.
- **재료 분석 (#311·#316)**: 틀은 분석 결과를 입력으로 받는다. 운영 확인(2026-11-25)에서 분석은 템플릿 v2 에서도 '재현 가능'으로 판정했다 (3차 팩트체크상 v2 에서는 재현되지 않는 재료). 같은 입력에서 빠진 정보 표시도 4회 중 3회만 나왔다. 틀의 재현 판단은 분석 판정만 믿지 말고 검사 1 의 필수 근거 표로 다시 본다.

## 9. 순서 [제안]

1. (운영) v5 판단 → B·v6 결정과 이 문서의 [미정] 확정
2. (B 이면) 템플릿 v6 — B 사유·`table_refs` select + 알파 3회 (재료당 1회)
3. `trap_frame` 프롬프트 + 평가셋 → 첫 평가
4. 틀을 쓰는 쪽: `_needs`·검사 4 (코드, 가상 틀로 단위 테스트) → `draft_feature_task`·`plan_contract` 입력 연결 → 평가
5. 검사 2·3 + 검토 표시 → 처음부터 끝까지 알파 3회
6. 보강 질문에 틀 질문을 더한다

## 10. 정할 것

- [미정] B 를 기본으로 할지 — 정하면 템플릿 v6 이 따라온다 (§4). v5 판단 뒤에 정한다.
- [미정] stateful_target 처리를 틀에 합칠지 (§6).
- [미정] 틀을 B·A 둘 다 만들지 (LLM 두 배), 선택 규칙으로 하나만 만들지 (§4).
- [미정] 회사 사례의 틀을 쓸 때마다 만들지, 재료에 저장할지 (§2).
