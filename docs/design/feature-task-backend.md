# 공통 과제 — 기능 개발형 (백엔드부터) 설계 [제안]

> 상태: 설계 (2026-11-06). PR-1(스키마·유형 선택·골격) 구현 중 — §12.
> 결정 표기는 온톨로지 레포와 같다 — `[확정]` / `[제안]` / `[미정]`.
> 관련: `prompts/draft_task/v3.md`(지금 유일한 공통 과제 유형), `src/task_spec/spec/{build,common,draft}.py`,
> `incidents/public_v1/`, `eval/spec/{run_draft,run_solo,run_trap_facts}.py`, `CLAUDE.md` 불변식.

## 0. 요약

- 공통 과제에 **유형**을 둔다: `incident`(지금의 이슈 진단·해결형) · `feature`(기능 개발형). **둘 다 유지**한다 [확정: 2026-11-06 사용자].
- **기능형은 "구현 + 디버깅" 두 단계**다 [확정: 2026-11-06 사용자]: 1단계 구현(40분) → 1단계 제출 뒤 "배포 후 운영 증상"을 공개 →
  2단계 디버깅(20분, 자기 구현에서 원인 진단·수정). 자세히 §4.3.
- 첫 대상은 **백엔드(`sw.backend`)** [확정: 2026-11-06 사용자]. 다른 직군은 백엔드 평가가 끝난 뒤.
- 골격(측정 역량·요구 수준·난이도·제한 시간 60분·기술 환경)은 지금 그대로 공고·온톨로지에서 결정적으로 정한다 (불변식 3). 바뀌는 건 LLM 이 채우는 본문의 형식, 검증 규칙, 평가 방법이다.
- 가장 큰 위험은 **AI 가 대신 풀어 버리는 것**이다. 기능 구현은 코딩 AI 가 가장 잘하는 일이라, 이슈형보다 쉽게 풀릴 수 있다. 그래서 "요구사항이 덜 정해져 있고, 판단·질문·검증이 있어야 맞게 만들 수 있는" 과제로 설계하고, 이슈형과 같은 AI 단독 풀이 테스트를 통과해야 승격한다.

## 1. 왜 필요한가

- 지금 공통 과제는 전부 이슈형이다: 겉 증상만 보여 주고 원인 구조를 숨긴 뒤, 자료 점진 공개로 진단·조치를 보게 한다 (`draft_task` v3).
- 백엔드 시범 공고에서 많이 나오는 역량은 **만드는 일**이다 — 온톨로지 `enables`(sw.backend) 상위: Java 프로그래밍, Spring 기반 백엔드 개발, RDBMS 활용 개발, SQL 작성·데이터 조회, REST API 설계·개발, 서버 애플리케이션 개발, ORM·데이터 접근 계층 개발 등.
- 이슈형은 "진단·대응" 역량은 잘 보지만, "요구사항을 해석해 설계하고 구현하는" 역량은 간접적으로만 본다. 공고 역량에 맞는 유형을 고를 수 있어야 공통 과제가 공고를 더 잘 대표한다.

## 2. 범위

| 포함 (1단계) | 제외 |
|---|---|
| `sw.backend` 공고의 공통 과제(track=common) 기능 개발형 | 다른 직군 (2단계 이후) |
| 유형 선택 규칙 · 승인자 유형 바꾸기 | 기능형 전용 확장 슬롯 (2단계 검토 — 1단계는 지금 슬롯 그대로, 아래 §7) |
| 생성 프롬프트·검증·승인 화면 표시 | 실제 코드 실행·자동 채점 환경 (응시 플랫폼 쪽 — P1 은 명세만) |
| 평가(생성 품질 · AI 단독 풀이 · 숨은 요구 사실 검산) | 과정 채점 설계 (기존 [미정] — §10) |

## 3. 유형 선택 규칙 [제안]

공통 과제는 공고 단위로 하나이고 그 공고 지원자 모두 같다 (불변식 3, 공통 과제 저장소 `CommonRef`). 유형도 공고 단위로 정한다.

0. **우선순위** [확정: 2026-11-06]: 승인자 지정(수정 요청의 `task_kind`) → 그 공고(같은 온톨로지 버전)에서 **가장 최근에 승인된 공통 과제의 유형**
   (같은 공고 지원자는 같은 과제 — 비교 가능성) → 아래 기본값 규칙. 예전 판(유형 필드 없음)은 incident 로 읽으므로,
   이미 이슈형 공통 과제가 승인된 공고는 승인자가 바꾸기 전까지 이슈형으로 남는다.
1. **기본값 (결정적)**: 공고 역량 중 "만드는 역량" 비율로 정한다.
   - 만드는 역량(예): REST API 설계·개발, 서버 애플리케이션 개발, Spring 기반 백엔드 개발, ORM·데이터 접근 계층 개발, 인증·인가 구현, 메시지 브로커 기반 비동기 처리, 배치 프로그램 개발, 캐시 기반 조회 성능 최적화
   - 진단 역량(예): 장애 대응·원인 분석, 서비스 성능 튜닝·대용량 트래픽 처리, 모니터링·로그 체계, 운영·유지보수
   - 공고 주 역량(담당업무·자격요건) 중 **진단 역량이 만드는 역량보다 많을 때만 `incident`, 아니면(동률 포함) `feature`** [확정: 2026-11-06 사용자].
   - 목록은 코드 상수가 아니라 데이터 파일(`src/task_spec/resources/task_kind/sw.backend.json`)로 둔다. 파일이 없는 직군은 incident.
     시범 공고 분포를 보고 목록을 조정한다 [미정: 목록].
   - 기능형 서술(`draft_feature_task`)이 아직 없으면 기본값이 feature 여도 incident 로 만들고 명세에 표시한다 (PR-1 — 지금 동작 유지).
2. **승인자 바꾸기**: 승인 화면 수정 요청(`revise_target=common`)에 `task_kind` 를 더해 유형을 바꿀 수 있다. 공통 과제는 공고 단위라, 바꾸면 그 공고의 공통 과제가 새 판(revision)이 된다 — 지금 공통 과제 수정과 같은 규칙.
3. 이미 만든 공통 과제(유형 필드가 없는 예전 판)는 `incident` 로 읽는다 (하위 호환).

## 4. 과제 구조

### 4.1 두 유형 비교

| 요소 | incident (지금) | feature (새로) |
|---|---|---|
| 상황 | 가상 회사의 업무 상황 + **겉 증상** | 가상 회사·서비스의 업무 맥락 + **만들 기능의 요구** |
| 공개 정보 | 증상, 자료 제목 목록 | 공개 요구사항, 공개 수용 기준, 자료 제목 목록 |
| 숨긴 것 | 원인 구조 | **숨은 요구사항·엣지 케이스** (동시성, 멱등성, 권한, 호환, 경계값 등) |
| 함정 | AI 가 그럴듯하게 틀리는 진단·처방 | AI 의 단순 구현이 놓치는 숨은 요구 |
| 점진 공개 | 자료 요청 (`max_requests`) | 자료 요청 + **질문하면 답하는 추가 요구·제약** (`max_clarifications`) |
| 먼저 말할 것 (`first_mention_of`) | 원인 개념 | 설계 결정·트레이드오프 개념 |
| 산출물 | 진단·조치 메모 등 | 핵심 구현, 테스트, 설계 메모(결정·근거·AI 에 맡긴 것) |
| 정답 | 원인 + 허용 조치 | 숨은 요구를 만족하는 **여러 설계를 허용** (`accepted_designs`) |

### 4.2 출력 스키마 `DraftFeatureOutput` [제안]

지금 `DraftTaskOutputV3` 와 겹치는 필드는 이름·의미를 그대로 쓴다 (승인 화면·평가 도구 재사용).

| 필드 | 지원자에게 | 내용 |
|---|---|---|
| `title` | 보임 | 기능 이름. 구현 방법·숨은 요구를 드러내지 않음 (예: "쿠폰 발급 API 추가") |
| `scenario` | 보임 | 업무 맥락과 사용자 요구 600자 안팎. 끝에 "자료 최대 N개 요청, 질문 최대 M개" 안내 |
| `requirements` (새) | 보임 | 공개 기능 요구 3~6개 (`r1`…) |
| `acceptance_public` (새) | 보임 | 공개 수용 기준 3~6개 — 관찰 가능한 문장, 숨은 요구는 쓰지 않음 |
| `traps` | 숨김 | 숨은 요구 1~3개 (`t1`…). 기존 `Trap`(description, why_ai_fails)을 그대로 쓰고 "AI 의 흔한 구현이 왜 이 요구를 깨는지"를 적음 |
| `clarifications` (새) | 질문 시 | 지원자가 물으면 공개할 추가 요구·제약 2~5개: `{clarification_id, topic, answer, reveals: [trap_id]}` |
| `max_clarifications` (새) | 보임 | 질문 수 상한 (2~4) |
| `artifacts` | 요청 시 | 기존 코드 발췌(컨트롤러·서비스·엔티티), API 명세 일부, 테이블 스키마, 설정, 트래픽·지표, 기존 테스트 — role: key(숨은 요구의 단서)/support/distractor(흔한 구현 패턴을 지지하는 기존 코드 등). 원시 자료만, 자료당 800자 이내 |
| `max_requests` | 보임 | 자료 요청 상한 (지금과 같음) |
| `acceptance_hidden` (새) | 숨김 | 채점용 수용 기준 — 숨은 요구마다 하나 이상 (`trap_id` 연결) |
| `accepted_designs` (새) | 숨김 | 숨은 요구를 만족하는 설계 2개 이상과 조건·함정 (예: 원자적 갱신 / 비관 잠금 / 고유 제약 + 재시도) — 한 가지 정답으로 감점하지 않게 |
| `deliverables` | 보임 | 2~4개, 60분 안 |
| `observables` | 숨김 | `first_mention_of`(설계 결정 개념), `catches_trap`, `requests_artifact`, **`asks_clarification`(새: 숨은 요구에 닿는 질문)** |
| `behavioral_anchors` | 숨김 | 수준 1·3·5, AI 활용 4축, 수행준거 id 인용 (지금 규칙 그대로) |
| `invariant` / `variable` | 숨김 | 심층 구조와 바꿀 표면 (지금과 같음) |
| `tech_used` | 보임 | 기술 환경 안의 언어만 (지금과 같음) |
| `debug_stage` (새) | 1단계 제출 뒤 | 2단계 디버깅: 배포 후 증상·자료·산출물·연결된 숨은 요구 — §4.3 |

`TaskItem` 에는 `task_kind`, `requirements`, `acceptance_public`, `acceptance_hidden`, `clarifications`, `max_clarifications`, `accepted_designs`, `debug_stage` 를 기본값과 함께 더한다 — 예전 체크포인트·저장된 공통 과제가 그대로 로드되게 (유형이 없으면 incident).
기능형 전용 필드는 `task_kind=feature` 일 때만 채울 수 있고, feature 는 공통 과제(track=common)에만 쓴다 (스키마 검사). id 사이 참조는 생성 검증(`spec/feature.py`, PR-2)이 본다.

### 4.3 두 단계 — 구현 → 디버깅 [확정: 2026-11-06 사용자]

| | 1단계 구현 (`FEATURE_BUILD_MIN` 40분) | 2단계 디버깅 (`FEATURE_DEBUG_MIN` 20분) |
|---|---|---|
| 공개 시점 | 처음부터 | **1단계 제출 뒤** (`debug_stage.reveal_after = stage1_submitted`). 단계 전환은 응시 플랫폼 몫, P1 은 명세에 적기만 |
| 보이는 것 | 위 §4.2 의 공개 필드 | `debug_stage.scenario`(배포 후 겉 증상 — 원인 개념 없이), 2단계 자료 목록(`debug_stage.artifacts`, 요청 시 공개, 상한 `max_requests`), 산출물 |
| 숨긴 것 | 숨은 요구·숨김 수용 기준·허용 설계 | `debug_stage.trap_ids`(증상이 어느 숨은 요구에서 나왔나), 먼저 말할 원인 개념(`debug_stage.observables`) |
| 산출물 | 핵심 구현·테스트·설계 메모 | 원인 진단과 수정. **1단계에서 이미 대응했다면 "이 증상이 내 구현에서 생기지 않는 근거"가 정답** |

- 왜: AI 단독 풀이(배송 감사·활성 사용자 예시)에서 숨은 테스트만으로는 AI 를 가르지 못했다. 2단계는 모든 지원자에게 같은 증상을 주고
  **진단 과정**을 보게 한다. 1단계에서 먼저 잡았는지(`catches_trap`)와 2단계 진단(`first_mention_of`)을 함께 본다.
  1단계 설계 메모를 먼저 내게 하는 것이 "AI 없는 첫 단계"(§10) 후보이기도 하다.
- 2단계 자료 id 는 1단계 자료와 같은 번호 공간에서 겹치지 않는다 (a1…). 2단계 증상은 `trap_ids` 중 하나 이상을 놓친 구현에서 실제로 생기는 모양이어야 한다 (숨은 요구 사실 검산에 포함).

## 5. 소재 카탈로그 — 공개 사례 `feature` 블록 [확정: 2026-11-06 사용자 — 별도 카탈로그 대신 incidents/public_v1 에 붙임]

- 공개 사례(직군마다 1건) 11건에 기능형 재료 `feature` 블록을 붙였다 (`incidents/public_v1/README.md` "feature 블록"). 사람 검토 전(`reviewed: false`).
- `draft_feature_task` v2 부터 이 블록을 입력으로 받고, 숨은 요구(t1)·허용 설계는 코드가 블록에서 채운다 (`spec/feature.py fill_from_seed`, v4 는 `fill_from_seed_v4`). LLM 은 겉모습만.
- 블록이 없는 직군(sw.qa·sales.marketing)은 기능형 기본값 대상이 아니다. 시작 코드 예제가 연결된 블록은 지금 sw.backend(`delivery-audit`) 하나.
- v1 → v2 비교 (2026-11-06, 직군별 1건, premium gpt-4.1): v1 은 5건 모두 상황·제목·2단계에 숨은 요구·원인이 샘. v2 는 제목·상황·공개 요구에서 사라지고
  2단계가 증상만 남음. 남은 것: 자료 역할 비율, 1단계 자료에 배포 뒤 증거 섞임, 추가 요구 답이 해법을 말함, 공고 역량과 재료 불일치(DBA), 공고 언어만 쓰는 기술 환경(프론트 Java).

- 추가 요구 두 층 답 [확정: 2026-11-06 사용자]: 추가 요구마다 `answer_hint`(모호, 일반 질문에)와 `answer`(구체, `match_terms` 가 들어간 질문에).
  진행자(응시 플랫폼)는 질문에 매칭 낱말이 있으면 구체 답, 없으면 모호한 답을 **고르기만** 한다 (보낼 때 문장을 바꾸지 않음 — 둘 다 승인 대상).
  모호한 답은 금지어·먼저 말할 개념·원 사례 원인 용어를 쓰지 않고, 단서 답이면 수치도 쓰지 않는다 (`spec/feature.py check_hints`).
  단서 추가 요구의 `match_terms` 중 공개 글(제목·상황·공개 요구·공개 수용 기준·제출물)에 이미 있는 말은 코드가 지운다 — 공개 글의 말은 일반 질문에도 들어가
  구체 답이 거의 늘 나가기 때문 (`prune_match_terms`). 지우기만 하고 재요청하지 않는다 (토큰 0). 다 지워지면 진행자는 늘 모호한 답을 주고
  승인자 화면에 표시한다 (`FLAG_HINT_ONLY`) [확정: 2026-11-06 사용자].
- 운영 조건 노출 검사 [확정: 2026-11-06 사용자]: 재료에 `trigger_terms`(운영 조건을 드러내는 말·바꿔 쓰기, 사람이 적음)를 두고, 1단계 제목·상황·공개 요구·
  공개 수용 기준에 나오면 재요청한다 (자료 본문·구체 답은 단서 자리라 검사하지 않음, `business_need` 에 나온 말은 뺌). 프롬프트에는 넣지 않는다 — 재요청은
  1회 상한이라 명세당 최대 호출 수(2회)는 그대로.
- 단서 추가 요구의 모호한 답 = 볼 곳 [확정: 2026-11-06 사용자 (B)] → `draft_feature_task` v5: 생성 모델은 단서 자료(1단계 자료 title)만 지목하고
  모호한 답은 코드가 "'<제목>' 자료에서 확인할 수 있습니다."로 만든다. 질문 안 함 → 도움 없음, 일반 질문 → 볼 곳, 정확히 짚은 질문 → 사실·수치.
  지목한 자료가 1단계에 없거나 방해 자료면 재요청. 1단계 자료 제목에 운영 조건 표현이 있으면 재요청 (재료 `discoverable_by` 의 괄호 앞 자료 이름에
  나온 말은 허용 — 예: DBA "DB 정리 작업 설정"). 매칭 낱말 중 띄어쓰기 없는 두 글자 이하 말은 코드가 지운다 (재요청 없음).
  명세 스키마(`Clarification`)는 그대로 — `answer_hint` 는 계속 글이라 승인 화면·전달 형식이 바뀌지 않는다.
- v5 비교 뒤 고친 것 [확정: 2026-11-06 사용자]: 재료의 자료 종류 이름에서 금지어를 뺌 (생성 모델이 이름을 자료 제목으로 그대로 써서 늘 재요청에 걸리던 재료 결함),
  단서 아닌 추가 요구는 모호한 답 = 구체 답이어도 통과, 재요청 사유에 걸린 문장 인용, `draft_feature_task` v6 (answer 필수 강조·상황에 운영 조건 금지).
  결과는 `prompts/draft_feature_task/PROMOTIONS.md`.
- 프롬프트 최적화 [확정: 2026-11-06 사용자 A·B·C]: 계산할 수 있는 칸(자료 번호·요청 한도·질문 한도·관찰 행동·2단계 연결·안내 문장)은 코드가 채운다,
  출력 스키마는 필드당 한 줄(`schema_style: compact`, 기존 프롬프트는 JSON Schema 그대로), 핵심 규칙 3개를 맨 앞과 출력 직전 확인 목록에 → `draft_feature_task` v4.
  2단 생성(겉모습·자료 분리)은 v4 평가 뒤 필요할 때만 [미정].
- **CURRENT = v4** [확정: 2026-11-06 사용자]: 같은 5개 공고·같은 검사기로 최종 통과 v1 0/5 · v2 1/5 · v4 4/5, 비용 −26% (근거 `prompts/draft_feature_task/PROMOTIONS.md`).
  검사가 못 잡던 누출 두 가지(상황 글이 운영 조건을 바꿔 말함, `match_terms` 가 공개 글의 넓은 말)는 아래 두 검사로 막는다 (결과는 PROMOTIONS.md "v4 주의").

### (예전 안) 별도 카탈로그 `features/public_v1/` [대체됨]

이슈형은 직군별 공개 장애 사례(`incidents/public_v1/*.json`, 검수 표시 `verified`)를 근거로 실제감을 낸다. 기능형도 같은 방식으로 **공개된 설계 사례**(엔지니어링 블로그·공식 문서)를 근거로 한다.

- 항목: `feature_id`, `sub`, `deep_structure`, `hidden_requirements`, `naive_impl`(AI·초심자의 흔한 구현), `why_naive_fails`, `accepted_designs`(조건·함정 포함), `surface`(바꿀 소재), `tech`, `source`(URL·게시일), `avoid_terms`, `verified`.
- 생성 입력에는 사례의 원리·숨은 요구·표면만 넣고, 조직명·제목·URL 은 넣지 않는다 (지금 `DraftTaskInputV2.incident` 와 같은 규칙). 사례 문장 그대로 베끼기 검사(`incident_copied` 와 같은 방식)도 적용한다.
- 백엔드 후보 패턴 (출처는 수집하며 검수 — 아래는 패턴만, 출처 확인 전) [미정]:
  1. 한정 수량 발급·차감 (동시 요청 시 초과 발급) — 동시성
  2. 결제·주문 요청 재시도 (중복 처리) — 멱등성
  3. 대량 데이터 내보내기 (요청 시간 초과, 메모리) — 비동기 작업·스트리밍
  4. 목록 API 페이지네이션 (오프셋 깊은 페이지, 데이터 변경 중 누락·중복) — 커서 기반
  5. 외부 API 연동 (느린 응답·부분 실패) — 타임아웃·재시도·보상
  6. 알림·이벤트 발송 (트랜잭션과 발송의 불일치) — 아웃박스
  7. 권한 계층이 있는 조회 (다른 조직 데이터 노출) — 인가 범위
  8. 소프트 삭제·감사 기록 (고유 제약 충돌, 이력 누락)
  9. 요청 빈도 제한 (분산 환경에서 우회)
  10. 시간·만료 경계 (타임존, 경계값)

## 6. 생성 흐름

1. `build_common` 은 지금 그대로 골격을 만들고 `task_kind` 를 정한다 (§3). 골격 값은 LLM 이 바꾸지 않는다.
2. `task_kind=feature` 면 새 프롬프트 **`draft_feature_task` v1** 을 부른다 [확정: 2026-11-06 — PR-2 구현].
   - 구현: `spec/feature.py` (검사·고쳐 쓰기·자료 섞기) + `spec/draft.py draft_task` 루프 재사용. 출력 `DraftFeatureOutput`, 2단계는 `DebugStageDraft`
     (공개 시점·시간은 결정적으로 붙임). 자료는 단계 안에서 섞고 1단계 a1…aN, 2단계 aN+1… 로 이어서 번호를 매긴다.
   - 기능형 카탈로그(§5) 전까지는 이슈형 공개 사례(`incidents/public_v1`)를 그대로 넣는다 — 사례의 "흔한 처방이 틀리는 원리"를 숨은 요구로,
     "겉 증상"을 2단계 증상으로 옮긴다.
   - **기본값 활성화 스위치** `FEATURE_TASK_DEFAULT`(기본 false): 꺼져 있으면 기본값 규칙이 feature 여도 이슈형으로 만들고 명세에 표시한다.
     승인자가 수정 요청에서 기능형을 지정하는 것은 늘 된다. 평가(§9, PR-4) 통과 뒤 켠다. `draft_task` 의 새 버전으로 하지 않는 이유: 출력 스키마가 달라 같은 과제 이름 아래 버전으로 두면 `CURRENT` 승격·평가 기록이 섞인다 (불변식 7 — 기존 vN 수정 금지, 평가 후 CURRENT).
   - 모델은 처음엔 `draft_task` 와 같은 `opencode:qwen3.8-flash` 로 시작하고, 평가에서 모델 비교를 한다. 출력이 길어 `max_tokens` 는 `draft_task` v3 와 같은 16000, `LLM_TIMEOUT_SECONDS`(기본 300) 안에 드는지 확인한다.
3. 자동 검증 (`spec/feature.py` [제안]) — 어긋나면 사유를 붙여 한 번 다시 요청, 그래도 어긋나면 고쳐 쓰고 `review_flags` (지금 정책과 같음):
   - 지금 규칙 재사용: 행동 기준의 수행준거 id 는 입력 목록 안에서만·측정 역량마다 하나 이상, 언어는 기술 환경 안에서만, 사례 베끼기·`avoid_terms`.
   - 새 규칙:
     - `observables.catches_trap`·`acceptance_hidden`·`clarifications.reveals` 의 id 는 `traps` 안에서만, 숨은 요구마다 숨김 수용 기준 하나 이상.
     - **숨은 요구 노출 금지**: 지원자에게 보이는 곳(title·scenario·requirements·acceptance_public·자료 제목)에 `first_mention_of` 개념과 숨은 요구의 핵심어를 쓰지 않는다 (이슈형의 "원인 노출 검사"와 같은 방식).
     - **구현 방법 지시 금지**: 공개 요구·수용 기준은 "무엇을"만 쓰고 "어떻게"(특정 잠금 방식·자료구조)를 쓰지 않는다 — 1차는 금지어 목록, 2차는 판정 LLM.
     - 범위: 공개 요구 ≤6, 산출물 ≤4, 자료 800자 이내 — 60분 안에 끝나는지 판정 항목에 포함.
     - `accepted_designs` 2개 이상.
4. LLM 이 실패하면 골격만 두고 `review_flags` 에 남긴다 (지금과 같음).

## 7. 확장 슬롯·경험 검증 (1단계)

- 지금 확장 슬롯(`draft_slot`)은 공통 과제의 상황을 이어 쓰는 30분 이슈형이다.
- **1단계: 확장 슬롯은 지금 방식 그대로 유지한다** [확정: 2026-11-06 사용자]. 기능형 공통 과제에도 지금 `draft_slot` 으로 슬롯을 만든다.
  - `draft_slot` 입력의 `common_task`(지원자가 이미 본 공통 과제 부분)에 기능형의 공개 요구·공개 수용 기준·자료 목록을 넣고,
    `forbidden`(슬롯에 쓰면 안 되는 공통 과제 핵심 개념)에 숨은 요구의 `first_mention_of` 개념을 넣는다 — 슬롯이 공통 과제의 숨은 요구를 드러내지 않게.
  - 기능형 공통 과제 + 이슈형 슬롯 조합이 자연스러운지는 1단계 평가에서 판정 항목으로 본다.
- 2단계에서 "같은 기능에 요구 하나를 더하는" 기능형 전용 슬롯(`draft_feature_slot`)이 필요한지 다시 판단한다.
- 경험 검증 후보 선택(대조·`claims_to_verify`)과 슬롯 배정은 과제 유형과 무관하므로 바뀌지 않는다.

## 8. 승인 화면 [PR-3 구현 2026-11-06]

- 과제 카드에 유형 표시 (이슈 해결형 / 기능 개발형). 승인 요약 `TaskBrief.task_kind`.
- 기능형 시간은 "1단계 구현 N분 + 2단계 디버깅 M분"으로, 2단계는 "1단계 제출 뒤 공개" 묶음(증상·제출물·2단계 자료·증상의 원인)으로 따로 보인다.
- 기능형 표시 순서: 공개 요구 → 공개 수용 기준 → 자료 목록(역할은 승인자만) → 질문 시 공개할 추가 요구(승인자만) → 숨은 요구·숨김 수용 기준·허용 설계(승인자만) → 행동 기준.
- 수정 요청에 "과제 유형 바꾸기"를 더한다 (§3-2). 승인은 지금처럼 `interrupt()` resume 으로만 (불변식 9).

## 10. 미정 · 결정 필요

- 만드는 역량 / 진단 역량 목록과 동률 규칙 (§3).
- 기능형 전용 슬롯이 필요한지 (§7 — 1단계는 지금 슬롯 유지).
- 과정 채점: 기능형은 최종 코드만 보면 AI 가 대신 풀 위험이 더 크다. "AI 없는 첫 단계"(예: 구현 전에 설계 결정 메모를 먼저 제출) 같은 응시 절차는 응시 플랫폼과 함께 정한다 — 기존 [미정](`draft_task` v3 주의)과 같은 문제.
- 실제 코드 실행·테스트 채점: P1 은 명세(`acceptance_public`·`acceptance_hidden`)까지만 만든다. 실행 환경은 범위 밖.
  → 시작 코드 템플릿 설계(`docs/design/starter-templates.md`, 2026-11-06)로 좁혀짐: 과제 **생성 때의 빌드 검증** 실행은 포함, 지원자 제출물 채점 실행은 제외.
- 카탈로그 출처 수집·검수 담당과 개수 (백엔드 최소 8건).
- AI 단독 풀이 예산.
