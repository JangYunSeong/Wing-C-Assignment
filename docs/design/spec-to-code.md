## 0. 요약

- 입력은 **승인된 기능형 공통 과제 판**(`task_kind=feature`)이고, 출력은 **검증을 통과한 오버레이 파일**(`starter` · `hidden` · `ref_*`)과 그것으로 빌드한 응시용·채점용 이미지다 (`starter-templates.md` §6.1).
- 명세는 자연어뿐이라 시작 코드·숨은 테스트·참조 구현이 같이 기댈 기준점이 없다. 그래서 먼저 **공개 계약 `TaskContract`**(API·입출력·엔티티·시드·공개 테스트 목록)를 만들고, 세 생성기는 **계약만 공유하고 서로의 산출물은 보지 않는다** (`starter-templates.md` §5 독립성).
  - 근거: 배송 감사 손 예시를 같은 API 계약·같은 숨은 시나리오로 Java·FastAPI·Next.js 에 만들었더니 판정 표가 세 판 모두 칸 하나 다르지 않았다.
- 숨은 테스트가 쓸 운영 조건(풀 크기·동시 요청·지연 주입 지점)은 계약과 따로 **`HiddenPlan`** 으로 두고 숨은 테스트 생성기만 본다. 계약은 지원자에게 보이는 정보라 숨은 요구를 담지 않는다.
  - `HiddenPlan` 의 수치는 **승인된 명세의 1단계 자료·구체 답에 실제로 있는 값**이어야 한다. 그래야 지원자가 발견할 수 있는 조건으로 채점한다 (§3.3).
- **하네스(지연·오류 주입·커넥션 추적·운영 설정 덮어쓰기)는 템플릿에 고정된 코드**다. LLM 은 하네스 API 를 부르는 케이스만 쓴다. 의도한 실패 사유도 템플릿이 정한 코드 목록에서만 고른다 (§4.1).
- 지원자용 **README 는 LLM 이 쓰지 않는다** — 승인된 명세 문장과 계약으로 결정적으로 채운다 (승인한 문장 = 지원자가 보는 문장).
- 검증(게이트 ①~⑨)이 실패하면 **실패를 원인 산출물에 배정해 그것만 다시 만든다** (산출물마다 1회). 그래도 실패하면 빌드 `failed` 로 승인 화면에 올린다.
- 검증은 **1회 실행 → 시간에 민감한 케이스만 반복** 순서로 시간을 아낀다 (§7.1). 게이트 통과와 별개로 **AI 기본 풀이 결과**를 승인 화면에 지표로 보인다 (막지 않음, §8) [제안].
- **테스트 먼저** [확정: 2026-11-08]: 계약 → 공개 테스트(`gen_public`)·숨은 테스트(`gen_hidden`)를 따로 → 구현 없이 컴파일하고 오류는 쓴 생성기에 되돌림 → 시작 코드·참조 구현은 **공개 테스트를 보고** 맞춘다 (숨은 테스트는 보지 않음). 숨은 게이트는 공개 테스트를 다 통과한 참조 구현만 믿는다 (§7).
- 첫 범위: Java Spring 템플릿 v1 하나, 배송 감사 예시를 기준(golden)으로 둔다 (§9).

## 1. 범위 · 경계

| 포함 | 제외 |
|---|---|
| 공통 과제 빌드 그래프(`build_graph`)의 노드: 템플릿 선택 · 계약 · 생성 · 정적 검사 · 수리 | 지원자 run 그래프 (명세 생성·승인 — 지금 그대로) |
| 생성 프롬프트(`prompts/<task>/vN.md`)와 출력 스키마 | 템플릿 자체 작성 (`starter-templates.md` §3, #55) — 단 템플릿이 이 파이프라인에 내줘야 할 것은 §4.1 |
| 실패 배정 규칙, 재생성 예산, 검증 시간 예산 | verifier 실행·게이트 판정 구현 (#55) |
| 평가 방법 (`CURRENT` 승격 조건) | 이미지 빌드·발행·플랫폼 계약 (§6.1, #52) |

- 이 단계의 입력은 공고·온톨로지·명세·카탈로그·프로젝트 설명뿐이다. 지원서는 쓰지 않는다 (불변식 3). 그래서 지원자 데이터가 LLM 으로 가는 경로가 없다 (불변식 2와 무관).
- 시작 시점은 `starter-templates.md` §4 그대로다: **명세 승인 → 빌드 → 시작 코드 승인 → 발행** [확정: 2026-11-06 사용자].

- `gen_refs` 는 시작 코드가 있어야 그 위에 구현을 쓸 수 있어 `gen_starter` 뒤에 돈다. 숨은 테스트는 시작 코드 내부를 보지 않는다 (게이트 ⑥) — 테스트 먼저라 순서상으로도 앞선다.
- 공개 테스트는 시작 코드에서 **저장 확인(`PersistenceCheckTest`)만 통과하고 기능 테스트는 실패**해야 한다 (구현 전임을 확인). 참조 구현은 공개 테스트를 **모두 통과**해야 숨은 게이트 판정에 쓴다 (§7).
- 구현: `nodes/starter/build.py`(`build_and_repair` — `compiler` 를 주면 `compile_and_fix`), verifier `starter/verify/gradle.GradleVerifier`(`verify` · `compile_tests`, 스택별 선택은 `starter/verify.verifier_for`).
- 상태 `common_task_build.status`: `pending → generating → verifying → review`(실패 `failed`) `→ approved → published` (§4 그대로). `repairing` 은 따로 두지 않고 `generating` 으로 돌아간다.
- 그래프 State 는 오버레이 **본문을 담지 않는다** — 파일은 `starter_file` 테이블(#52)에 쓰고 State 에는 `(kind, path, sha256)` 목록만 (체크포인트 크기·숨은 테스트 노출 방지).
- **응시용 이미지의 기준 커밋** [제안]: 응시용 이미지를 만들 때 작업 경로를 git 저장소로 만들고, 조립 트리로 첫 커밋을 고정 작성자·고정 시각으로 넣는다. 그러면 기준 커밋 sha 가 모든 지원자에게 같고, 응시 중 커밋 기록(플랫폼 쪽)의 시작점을 sha 하나로 대조할 수 있다. sha 는 이미지 라벨과 `common_task_build` 에 남긴다.

## 3. 공개 계약 `TaskContract` · `HiddenPlan`

### 3.1 왜 필요한가

- 숨은 테스트는 **공개 계약으로만** 판정한다 (게이트 ⑥). 계약이 없으면 생성기마다 엔드포인트·필드 이름을 따로 상상해, 검증 실패의 대부분이 "함정"이 아니라 "서로 안 맞음"(404·역직렬화 오류)이 된다.
- 독립성(테스트와 구현이 같은 오해를 공유하지 않게)과 일관성(같은 인터페이스)을 동시에 얻는 방법은 **작은 공통 기준점 하나만 공유**하는 것이다.

### 3.2 형태 [제안]

```
TaskContract                         ← 지원자에게 보임 (README "계약" 절)
  interface_kind: http | cli | file   (템플릿 manifest 가 허용하는 것 중)
  endpoints[]:  id(e1…) · method(http 만) · path · summary · headers · query · request(필드) · responses(상태 코드·설명·본문 필드 또는 returns: m1 · m1[] · v1 · v1[]) · refs(r*·p*)
  entities[]:   id(m1…) · name · fields · relations · foreign_keys("필드 → 엔티티" — DB 외래 키로 둘 것만)      ← #58 [데이터 모델]
                · existing(이 과제 전에 있던 테이블인가 — 숨은 케이스 data 는 existing 엔티티에만, 새 엔티티는 0행)
                · state(상태를 바꾸는 엔티티만: field · values · transitions "A→B" · rejected_status) [확정: 2026-11-08, plan_contract v10]
    필드:        name · type · required · constraints · refs(r*·p* — 이 필드가 나온 공개 요구·수용 기준, 1개 이상)
    헤더 필드:   위 필드 + per_request(요청마다 새 값인가 — 요청 번호·멱등 키는 true, 요청자는 false. 권한 칸 auth 의 헤더 밖에서 비면 재요청) [2026-11-14, plan_contract v27 — #181]
  response_shapes[]: id(v1…) · name · fields — 응답에만 있는 모양, 테이블 아님 (시드·외래 키·state·existing 없음) [2026-11-13]
                · row_of(한 건이 어느 테이블 엔티티의 한 행인가 — 집계면 null) [2026-11-14, plan_contract v29 — #185]
  settings[]:    key(스프링 속성, 점 표기) · type(int) · default · meaning · refs — 구현이 읽어야 하는 설정 (스프링 템플릿만) [2026-11-13, #161]
  seed[]:       entity id · rows(정확한 행 수, id 1~rows) · groups(id 범위마다 처음 값, 1~rows 를 빈틈·겹침 없이) · 값 규칙 (가상 데이터만, §10-16)
  fixtures[]:    id(f1…) · kind(db·file·service·browser·env) · summary · content · path(file 만 — 위치 패턴, 마디는 {명령 옵션}; 받은 날짜 폴더는 type date 옵션 마디) [2026-11-15, plan_contract v30 — #187]
  public_tests[]: id(pt1…) · ac_id(p*) · 무엇을 확인하나 (공개 수용 기준 1:1 이상)
                · rows(테스트가 id 로 다루는 시드 행의 처음 값 — API 가 돌려주는 엔티티·요청으로 바꾸는 행만, 조인돼 보이는 원천 행은 fit_row_targets 가 뺌)
                · rows[] — 그 테스트가 쓸 시드 행의 처음 값 (entity_id · values) [2026-11-13 #164]. 코드가 그 처음 값의 시드 그룹·공개 몫 상수를
```

### 3.3 결정적 검사

- **양방향 대응**:
  - 모든 `r*` 가 `covers` 에 있고, 모든 `p*` 에 공개 테스트가 하나 이상, 모든 `h*` 에 `HiddenPlan.cases` 가 하나 이상.
  - 거꾸로 **계약의 모든 엔드포인트·엔티티·필드가 어떤 `r*`·`p*` 에서 나온다** — 요구에 없는 필드(예: 재시도 키·처리 상태 필드)는 낱말 목록에 안 걸려도 구조로 해법을 흘린다.
- 계약의 경로·필드·이름이 템플릿 `fill_slots`·명명 규칙과 맞는다 (예: Spring 패키지 경로, HTTP 경로 문자).
- 계약 전체 문자열에 `leak_terms`·`trigger_terms`·`stage2_cause_terms` 가 없다 (기능형 서술 검사와 같은 낱말 목록·같은 함수 재사용).
- **`HiddenPlan` 수치 = 명세에 보이는 수치**: `harness` 의 각 값(풀 크기·동시 요청 수 등)이 승인된 명세의 1단계 자료 본문이나 추가 요구 구체 답(`answer`)에 나온다. 없으면 지원자가 발견할 수 없는 조건으로 채점하게 되고, 다르면 자료와 채점이 어긋난다.
  - 손 예시: 풀 8·동시 32 가 요청 자료 a2(운영 설정)·a3(요청 지표)와 진행자 구체 답에 있고, 하네스가 같은 값을 운영 설정으로 덮어썼다.
  - **대조 방법**: 자유 글의 숫자를 그대로 찾지 않는다 ("8" 은 아무 데나 나온다). 템플릿 `harness_params` 마다 **표기 패턴**(키 이름·동의어·단위, 예: `pool_size` ← `maximumPoolSize=8` · `풀 8개` · `connection_limit=8`)을 두고, 자료 본문·구체 답에서 그 패턴으로 뽑은 값과 같은지 본다. 패턴으로 못 뽑으면 "없음"이다.
  - **명세에 수치가 없으면 재요청으로 고칠 수 없다** — 명세는 이미 승인됐고 `plan_contract` 는 명세를 바꾸지 않는다. 그래서 재요청하지 않고 바로 빌드 `failed`, 사유 "명세 1단계 자료에 운영 수치 없음 (`<param>`)" → 승인자가 **명세 수정 요청(새 판)** 을 고른다.
  - 이런 실패를 줄이려고 명세 단계에서 먼저 막는다 [제안]: 기능형 서술 검증(`spec/feature.py` 의 운영 조건 검사 옆)에 "템플릿이 정해지는 기능형이면, 1단계 자료·구체 답에 그 템플릿 `harness_params` 의 필수 값이 패턴으로 뽑힌다"를 더해 명세 생성 때 재요청한다. 명세 단계는 템플릿을 모르므로 `select_template` 을 명세 승인 전에도 한 번 돌려 필수 키만 넘긴다.
- `harness` 의 키는 템플릿 `manifest.harness_params` 안의 것만, `cases[].의도한 실패 사유`는 `manifest.failure_reasons` 안의 코드만.
- 크기 상한: 엔드포인트 1–6, 엔티티 1–8 (60분 과제 기준 [미정]).
- **명세에 나온 API 는 계약에** (2026-11-07 스모크에서 보탬): 제목·상황·공개 요구·공개 수용 기준에 나온 `METHOD /path`(기존 API 포함)가 계약에 있어야 하고, 공개 테스트·숨은 케이스가 언급하는 API 도 계약에 있어야 한다. 응답 `returns` 는 계약 엔티티를 가리킨다.
- **자료의 운영 값은 모두 HiddenPlan 에**: 선택 조절값이어도 명세 자료에서 표기 패턴·표 열로 뽑히면 넣는다 — 빼면 하네스 기본값이 대신 들어가 실패 사유가 달라진다. 자료에 없는 선택 값을 넣으면 재요청 (지어낸 값).
- 표기 패턴만으로 못 읽는 표(요청 지표처럼 열 이름 + 값 줄)는 manifest `spec_columns`(열 이름 정규식)로 그 열의 숫자를 읽는다.
- **패턴 값이 정답, 근거 인용은 엄격하게** (2026-11-07 알파 테스트): 표기 패턴이 값을 뽑으면 그 값만 정답이다. 서로 다른 값이 여럿이면 manifest `pick`(unique·max·min)으로 고르고, unique 인데 여럿이면 통과시키되 승인자 확인. 패턴과 다른 값은 숫자가 하나뿐인 근거 인용일 때만 받고 표시한다. 근거 인용 경로에서는 백분율·시각을 값 후보에서 빼고 160자 상한, 남은 숫자가 여럿이면 승인자 확인. (분포 "1개: 38% … 4개 이상: 7%" 를 통째로 인용하면 동시 탭 수 1~4 아무것이나 통과했다 — 1 이면 함정이 아예 일어나지 않는다.)
- **재료가 사유를 적으면 계약·빌드가 모두 그 목록만** (`FeatureSeed.reasons` → `templates.restrict_reasons`, 계약 `for_material`·빌드 `BuildInputs`, 2026-11-14): 계약 입력·검사만 재료 사유로 좁히고 숨은 테스트 생성기 입력·정적 검사는 템플릿 목록 전체를 봐, 갱신 손실·재시도 중복 알파에서 숨은 테스트가 '시간 초과·5xx 수' 확인에 재료에 없는 `pool_acquire_timeout` 을 붙였다 (충돌을 500 으로 돌려준 구현이 '풀 대기 초과'로 채점됨). 목록 밖 사유를 붙이면 정적 검사가 재요청한다 — 그 요구와 무관한 실패를 확인하는 단언에는 사유를 붙이지 않는다.
- **재료가 값 만드는 규칙을 적으면 그 규칙으로 대조** (`FeatureSeed.harness_rules`, 2026-11-13): 일반 검사는 인용 속 값 후보가 하나여야 받는다 — 어느 수가 근거인지 모르기 때문이다. 그런데 어느 수를 어떻게 맞추는지는 숨은 요구(재료)가 안다: 목록 재료 hana006 이 '평균: 21.3 p50: 19.8' 을 인용하고 p50 을 반올림한 20 을 맞게 썼는데 세 번 다 거절됐다. 규칙 = 이름표(앞이 우선, 예: p50 → 중앙값 → 평균; 어느 것도 없으면 이름표 없는 수) · 단위(예: 건) · 고르기(only·max·min) · 맞추기(exact·nearest·up·down, 시간 조절값은 단위 환산 뒤). 계약 검사(`contract.value_check` — 2026-11-15 부터 값 글자로, 아래)가 이 규칙으로 값을 다시 계산해 계약 값과 같아야 받고, 다르면 규칙과 계산한 값을 적어 재요청한다 (승인자 표시 없음 — 규칙으로 확인됨). 계약 입력의 조절값 설명에도 같은 규칙 문장이 붙는다. 규칙 없는 조절값은 위 일반 검사 그대로.
- **근거 인용 + 값 글자 — 검사는 인용 문장에서 값을 추측하지 않는다** (`hidden_plan.evidence_value`, plan_contract v31, 2026-11-15): 위 두 검사는 인용 문장에서 어느 수가 값인지 코드가 골라 읽었다 — 표기가 나올 때마다 규칙이 하나씩 늘었고(11-07 분포·11-11 반올림·11-13 이름표), 2026-11-15 운영에서는 인용 줄머리 절 번호 '3.1 … 500ms' 의 3.1 을 값으로 읽어 request_timeout_s 기대값 4 를 만들고(재요청이 그 틀린 값을 알려 줬다) 범위 '14~16ms' 는 이름표가 앞 수에만·단위가 뒤 수에만 붙어 매번 걸렸다. 그래서 계약이 인용과 함께 **그 안에서 값이 적힌 글자**(수와 단위, 범위면 범위째)를 내고, 검사(`contract.value_check`)는 그 글자가 가리키는 값 토큰 하나만 재료 규칙(없으면 값 그대로·정수로 맞춤)대로 환산해 대조한다. 이름표·고르기(max·min)·여럿 판정은 **같은 종류의 값 토큰끼리만** — 시간 조절값이면 시간 단위가 붙은 수(머리 줄 단위 `(ms)` 가 있으면 그 표의 수), `units` 가 있으면 그 단위가 붙은 수, 그 밖은 단위 없는 수·개수. 단위 없는 수는 시간 값이 아니다(인용에 시간 단위가 하나도 없을 때만 조절값 단위로 읽고 승인자 표시). 범위는 고르기가 max·min 이면 그 끝, only 면 범위 안의 값을 모두 받는다. 값 글자가 없거나 인용 속 값 하나를 가리키지 않으면 재요청. 짝 표기('p50/p95: 15/33ms')처럼 값과 이름표·단위가 떨어진 줄은 확인할 수 없어 다른 줄을 인용하게 한다 — 그런 줄밖에 없으면 명세 단계가 운영 값을 구조로 남기는 길(후속)로.
  인용 글자를 고친 경우의 조각 보정(`evidence_fragment`)은 값 글자가 든 가장 긴 조각만 본다 — 걸리면 더 짧게 자르지 않는다 (잘라서 p50 값을 빼면 이름표 판정을 피해 간다).
- **시드와 케이스 행** (§10-16, `starter/seed_rows.py`): 시드 groups 가 id 1~rows 를 빈틈·겹침 없이 덮고, 처음 값·케이스 `initial` 의 필드가 엔티티에 있으며 값 목록(`enum(A|B)` 형식 또는 제약 문장의 따옴표 낱말 2개 이상)이 있으면 그 안. 버스트 케이스 행 수 ≥ manifest `burst_rows` 조절값의 곱(Java: `concurrency × bursts`). 케이스 순서대로 처음 값이 맞는 그룹의 **큰 id 부터** 이어진 범위를 나누되 작은 id 10행(`RESERVED_ROWS`)은 지원자·공개 테스트 몫 — 나눌 수 없으면 재요청. 나눈 범위는 `gen_hidden` 입력의 케이스 아래 `데이터: <엔티티> id a~b (…)` 줄로 간다.
- **재요청은 최근 문제만, 2회까지** (2026-11-08): 문제 여러 개를 한 번에 다 고치지 못해 실패한 실행이 있어(상류 평가 3/9) 재요청을 2회로, 매번 직전 답의 문제만 붙인다.
- **코드가 맞추는 것** (재요청 대신, 바꾼 것은 `adjustments` 로 승인 화면에): 빠진 숨은 조절값 → manifest 기본값 · 행 수(`fit_seed`) — 처음 값마다 **공개 테스트 몫 3행**도 숨은 범위·작은 id 밖에 (2026-11-08: 숨은 케이스가 11~172 를 다 가져가 공개 몫이 없었다) · covers 는 공개 요구(`r*`) 키만 — 수용 기준(`p*`) 키는 빼고(공개 테스트가 대응, #180), 빠진 요소를 그 요소가 적은 `r*` refs 대로 잇는다(`fit_covers` — refs 는 공개 id 만이라 숨은 요구가 들어오지 않음, refs 가 `p*` 뿐인 요소는 잇지 않고 재요청) · 화살표 글만 적은 전이를 `state` 칸으로 + 상태 필드 constraints 문장을 칸에서(`fit_state`, `starter/state_rule.py`).
- **상태 규칙 칸** (`state_problems`): 필드가 엔티티에 있음 · 전이 양끝이 values 안 · 거절 코드가 응답에 · 시드·숨은 케이스 처음 값이 values 안 · **숨은 케이스 처음 값에서 나갈 허용 전이**가 있음 (롤백·버스트 케이스가 규칙을 통과하는 요청을 보낼 수 있게). 2026-11-08: 계약 첫 답 9개 중 5개가 전이를 빠뜨림(자유 글 시절) → 칸으로 바꾼 뒤 0/9.
- **재료가 선언한 필요 요소** (`FeatureSeed.contract_needs` — `stateful_target` · `transition_rules` · `empty_record_entity`): 숨은 요구가 계약에 꼭 필요로 하는 것을 재료가 선언하고 코드가 대조한다 (`contract._needs`).
- **통과 조건은 HTTP 로 관찰할 수 있는 것만**: 숨은 케이스 `expect` 가 조절값 이름(풀 크기 등)을 말하면 재요청 — 연결 수 같은 내부 동작은 단언할 수 없다.
- **테이블 이름은 템플릿 규칙으로** (2026-11-07, `starter/tables.py`, manifest `naming.table`): 숨은 테스트는 시작 코드를 보지 않으므로 오류 주입 정규식의 테이블을 계약에서 안다 — 생성 스모크에서 경로로 짐작(`deliveries`, 실제 `delivery`)해 주입이 안 걸렸다. 규칙은 스택마다 다르다 (`DeliveryAuditLog` 기준, 공식 문서·소스로 확인): Spring Boot JPA `delivery_audit_log` · Rails `delivery_audit_logs` · Django `<앱>_deliveryauditlog` · Hibernate 기본(Spring 없이, 이름 그대로·따옴표 없음 → PostgreSQL `deliveryauditlog`, 표준대로 대문자로 접는 Oracle 등 `DELIVERYAUDITLOG`) · Prisma(`@@map` 없음, PostgreSQL 기준 따옴표로 대소문자 유지) `"DeliveryAuditLog"` · 프론트엔드·파일형은 없음. 템플릿이 정한 SQL 예약어로 나오면 복수형 (`order` → `orders`). 계약(README)에 "`Delivery` — 테이블 `delivery`" 로 보인다.

- **코드가 쓰는 파일** (생성기가 같은 경로를 쓰면 버리고 렌더본): 시드 SQL(`starter/seed_sql.py`) · 숨은 테스트 도우미 `ContractCase`(케이스별 id 범위 `HC1_FIRST`…, 테이블 이름 `TABLE_…`, 처음 값별 다음 상태 `NEXT_OK_…`·`NEXT_BAD_…`, 계약 API 함수·200 본문 파싱, `peak(…)`) · 공개 테스트 도우미 `PublicCase`(공개 몫 행 `PUBLIC_…`, 다음 상태, 계약 API 함수 — 숨은 범위·주입 없음) · 저장 확인 `PersistenceCheckTest`(새 엔티티를 JPA 메타모델로 만들어 저장, id 생성 확인) · 조절값 파일 · README (`starter/hidden_helpers.py`·`starter/render.py`). README 를 뺀 이 파일들의 경로는 `hidden_helpers.code_written_paths` 한 곳이 정하고, 정적 검사의 크기 상한과 생성기 컴파일 오류 배정에서 뺀다 (생성기가 고칠 수 없다 — #178).
  - 시드 그룹이 값을 정하지 않은 필수 칸은 형식별 결정적 기본값이다. **날짜·시각 칸은 행마다 다르고 id 순서와 어긋나게**(2026-11-13, `seed_sql.time_value` —
    소수 주기 순열, 약 7일 안의 분 단위·날짜는 약 1년 안): 모든 행이 같은 고정 시각이면 '최신순'이 뜻을 잃고, id 순서대로 늘리면 id 로만 정렬한 구현이

    날짜-시간·YYYY-MM-DD)이나 `…At` 이름이면 날짜·시각으로 본다(보조 — 계약이 형식을 datetime 으로 적는 것이 원칙, plan_contract 몫).
    README 시드 줄에는 "행마다 다른 값, id 순서와 무관 (예: id 1 → …)"으로 적는다. 근거: 행마다 조회 알파(2026-11-12) — `createdAt`(string, 'ISO 8601')에
    `'createdAt-<id>'` 가 들어가 풀이 6개 모두 진행자에게 정렬 기준을 물었다.
- **코드가 합치는 파일** (2026-11-08, `starter/config_merge.py`, manifest `config_merge`): 설정 파일(Java 는 `application.yml`)은 생성 직후 — 시드 SQL 을 쓰는 자리와 같다 — 바탕(템플릿 → 시작 코드) 위에 키 단위로 합친다. 저장되는 오버레이·검증·이미지가 모두 같은 설정을 쓴다. 잠긴 키(`spring.datasource.url`·`spring.jpa.hibernate.ddl-auto`·`spring.sql.init.mode`)는 늘 바탕 값으로, 바탕에 없으면 지운다(Spring Boot 가 테스트 컨텍스트마다 다른 이름의 메모리 DB 를 붙이는 기본 동작). 되살리거나 되돌린 키는 "코드가 고친 것"(adjustments)으로 승인 화면에. 참조 구현 입력의 시작 코드 파일에는 지금 적용되는 설정 파일이 함께 보인다 (프롬프트는 그대로, 입력만). 근거: 알파(2df170e2) — 참조 구현 4개가 모두 yml 을 통째로 다시 써 `ddl-auto`·`sql.init` 을 지우거나(Hibernate 가 테이블을 다시 만들어 시드가 사라짐, 모든 요청 404) DB 주소를 고정(컨텍스트끼리 같은 DB → schema.sql 두 번 실행, 기동 실패); 수리 배정은 '테스트 의심'·'계약 모호'로 짚었다. 그래서 배정도 보탬 — 모든 구현이 같은 기동 실패·기존 테스트·공개 테스트 오류를 낼 때, 모두 다시 쓴 공유 파일(템플릿·시작 코드에 이미 있는 파일)을 원인 후보로 수리 요청·검토 표시에 싣는다 (`repair._shared_note`).
- **요청 헤더 값** (2026-11-08, `starter/header_values.py`): 계약 공개 테스트 예시(`<헤더>=<값> … → <상태>`)에서 헤더마다 규칙(권한)을 통과하는 값·거절되는 값을 뽑아 도우미(`ContractCase`·`PublicCase`)에 `HEADER_<헤더>_OK`·`_DENIED` 상수와 `okHeaders()` 로 준다. 좁게 읽는다 — 계약에 선언된 헤더 이름 바로 뒤의 값, 그 뒤 처음 나오는 상태 중 그 헤더를 받는 엔드포인트가 선언한 것만, 양쪽에 나온 값은 버림. 값을 정할 수 없으면 지어내지 않는다: 권한 거절(401·403)을 선언했는데 통과 값 예시가 없으면 계약 재요청(`header_problems`), 거절 응답이 없는 헤더는 아무 값(`grader`). 테스트가 두 상수 어느 것도 아닌 값을 글자로 쓰면 재요청(`static_check._literal_headers`). 배정: 시작 코드가 공개 테스트에서 실패하는데(새 기능 없음) 숨은 케이스를 통과하면 시작 코드가 아니라 `gen_hidden` — 요청이 기능 단계에 닿았는지 먼저 확인하라는 수리 요청 (`repair._starter_solves`). 근거: 알파(2df170e2) — 숨은 테스트가 지어낸 요청자 `grader` 로 모든 요청이 403, hc2('성공 기록 0건'만 단언)를 기능 없는 시작 코드가 통과, 배정은 시작 코드를 두 번 다시 만듦.

  시간을 재는 요청(`Burst.fire`·`rounds`·`peak`) 안에서 요청을 둘 이상 보내면 재요청(`_timed_requests` — 도우미 API 함수도 센다, 분기는 둔다).
  배정: 흔한 구현이 의도한 사유로 떨어져도 허용 구현이 **사유 없는 단언**에서 떨어지면 허용 구현 탓으로 단정하지 않고 숨은 테스트를 한 번 의심한다

- **권한 규칙 칸** (2026-11-09, `Endpoint.auth` · `starter/auth_rule.py`, plan_contract v13): 권한 실패(401·403 또는 권한 사유 코드)를 내는 엔드포인트는 칸이 필수 — 헤더가 있다는 것만으로는 아니다(요청자를 기록용으로만 받는 계약이 대부분). `role`(요청자 엔티티·식별 필드·권한 필드·통과 값·경로와 같아야 할 필드) · `fixed`(통과하는 헤더 값) · `other`(글 — '자동 보장 안 됨' 확인 표시). role 은 코드가 시드 끝에 요청자 행 두 개(통과용·거절용)를 덧붙이고 숨은 케이스·공개 몫 배정에서 뺀다 — 권한 필드가 바꾸려는 상태와 같은 필드일 수 있다. 그 행의 식별 값이 `HEADER_<헤더>_OK`·`_DENIED`(예시 문장보다 우선), 헤더 constraints 문장도 칸에서 코드가 쓴다. StateRule 과 같은 방식. 근거: smilegate_2026#002 계약 14개가 권한을 4가지로 정했고(8개는 '요청자 식별자'뿐), 통과 예시가 시드와 맞지 않아 계약이 거절되거나(`<MASTER 등급 멤버의 memberId>`) 모든 요청이 403.
- **ui 화면 진입·배경 요청** (2026-11-09, `Screen.on_load` · `TaskContract.background`, plan_contract v14): ui 계약은 화면마다 들어올 때 무엇을 읽고 어떤 서버 요청이 나가는지(없으면 '서버 요청 없음'), 화면 조작 없이 나가는 요청과 그 시점(동기화·재시도, 없으면 '없음')을 정해야 한다 — 비면 재요청, README 계약 절에도 나간다. 근거: React 알파(naver_2026#003)에서 공개 테스트는 '목록에 들어오면 GET', 오프라인 우선 구현 4개는 로컬 저장소만 읽어 모두 '요청이 오지 않음'(HARNESS_ERR). '서버에 반영됨' 수용 기준을 앱의 조회 요청이 아니라 목 서버 상태로 확인하는 규칙은 테스트 생성기·하네스 쪽(React 템플릿 담당) 몫.
- **상태 값은 1단계 자료 그대로** (2026-11-09, `contract.material_state_problems`): state 칸 값이 자료의 값 목록(SQL `ENUM(…)`, `enum X {…}`, `A|B|C`)과 절반 이상 겹치는데 자료 밖 값이 있으면 첫 답에서만 재요청, 그 뒤엔 확인 표시(요구가 새 상태를 더할 수 있다). 근거: 같은 계약 14개 중 8개가 자료 밖 값(GENERAL·NORMAL·SUB_MASTER·RANK).
- **주입한 요청의 응답 코드** (2026-11-09, `static_check._injected_status_asserts`): 저장 실패를 주입한(manifest 저장 실패 사유의 `requires` 패턴) 숨은 케이스가 응답 코드를 특정 값·범위로 단정하면(`isLessThan`·`isBetween`, 계약이 선언한 5xx 가 아닌 `isEqualTo`·`isIn`) 재요청. 계약은 저장 실패 때의 응답을 정하지 않는다 — '성공 아님'(`isNotEqualTo(200)`·`isGreaterThanOrEqualTo(400)`)만 둔다. 근거: 알파(2df170e2, 하네스 rollback 수정 뒤) — hc2 가 커밋 실패 주입 뒤 `statusCode() < 500` 을 `rollback_left_success` 사유로 단언해 흔한 구현·허용 설계 3개가 두 회차 모두 같은 줄에서 떨어짐.
- **생성기 `CURRENT` 와의 차이** [미정 — §10-17]: 위 버전은 평가에서 고정해 쓰는 것이고, 2026-11-08 기준 `CURRENT` 는 `gen_starter` v3 · `gen_naive`·`gen_accepted` v2 · `gen_hidden` v2 (`gen_public` v1, `plan_contract` v10). 고정 없이 돌리면 공개 테스트를 받지 않는 옛 프롬프트가 쓰인다.

- **시작 코드는 "구현 자리를 비운" 코드다**: 엔티티·저장소·컨트롤러 시그니처·시드·기존 기능 테스트까지 쓰고, 기능 본문은 `TODO` 로 둔다(컴파일되게 — Java 는 예외를 던지는 스텁).
- **기존 테스트와 공개 테스트를 구분한다**:
  - 기존 기능 테스트(게이트 ②)는 시작 코드에서 **통과**한다.
  - 새 기능의 공개 테스트는 시작 코드에서 **실패**하고, 허용 구현·흔한 구현 모두에서 **통과**해야 한다 (게이트 ⑤ 누설 없음).
  - **공개 테스트를 지원자에게 줄지는 [미정]**이다. 손 예시는 기존 기능 테스트만 주고 공개 수용 기준은 채점 쪽에서 봤다. 실패하는 공개 테스트를 주면 AI 가 테스트를 돌려 가며 고칠 수 있어 난이도·변별이 달라진다. 어느 쪽이든 저장·작성자가 달라지므로 §4.3 에 둘 다 적는다.
- **흔한 구현 수**: 전부 놓친 판 1개 + 숨은 요구마다 하나만 놓친 판 1개. 숨은 요구가 1개면 둘은 같으므로 1개. **허용 구현 수**: 허용 설계마다 1개.
- 호출 수 = 계약 1 + 시작 코드 1 + 숨은 테스트 1 + 흔한 구현(1 + 숨은 요구 수, 숨은 요구 1개면 1) + 허용 구현(허용 설계 수). 숨은 요구 3·허용 설계 4 면 11회 — 상한 [미정, §10].
- 각 생성기 출력에는 provenance(`prompt_id@version+hash`, 모델·설정, `ontology_version`, 템플릿 ref)를 붙인다 (불변식 8).
- `render_readme`: `README.tpl.md` 의 자리(상황·요구·공개 기준·산출물·계약·실행 방법·채점 방법 한 문장)에 승인된 명세 문장, 계약 표, `manifest.commands` 를 넣는다. LLM 호출 없음. 숨은 수용 기준·숨은 요구·허용 설계·2단계 내용은 자리가 없다.
  문제 분석 판(요청 글이 있는 명세)은 두 판 — 지원자 `README.md` 는 얇은 판(배경 글·요청 글·계약 모양만), 원래 판 `README.full.md` 는 승인 화면·평가 키트에만 (analysis-stage.md §6 구현).
- `gen_hidden` 에 주는 숨은 요구 설명은 `traps[].description`·h* 기준·`HiddenPlan` 까지다. seed `why_naive_breaks`(흔한 구현이 깨지는 이유)까지 줄지는 [미정] — 주면 실패 지점을 정확히 노리는 테스트가 나오지만, `gen_naive` 가 보는 `naive_impl` 과 같은 서술을 공유해 두 생성기가 같은 이해(같은 오해)를 갖게 된다 (독립성).

### 4.1 템플릿이 이 파이프라인에 내줘야 할 것 (`manifest.yaml` 추가 필드) [제안]

손 예시 세 스택에서 하네스는 스택마다 손으로 다시 짜야 했고 미묘했다:
- Java: BeanPostProcessor 로 지연 주입, Hikari 대기 추적.
- FastAPI: SQLAlchemy 이벤트로 지연·세션 추적.
- Next.js: PostgreSQL 와이어 프로토콜 프록시로 지연·커넥션 추적, 로그로 Prisma 오류 분류.
- 공통: 커밋 시점 오류 주입(지연 제약 트리거), 운영 설정 덮어쓰기(예: `connection_limit=8&pool_timeout=5`).

이것을 LLM 이 매번 쓰면 깨진다. 그래서 템플릿이 고정 코드로 갖고 아래 필드로 내준다.

| 필드 | 내용 | 쓰는 곳 |
|---|---|---|
| `hidden/harness/` (잠김) | 지연·오류 주입, 커넥션·대기 추적, 서버 기동, HTTP 도우미, 운영 설정 덮어쓰기 | `gen_hidden` 은 API 문서만 보고 케이스를 씀 |
| `harness_params` | 조절값 이름·타입·범위·필수 여부 + **표기 패턴**(명세 자료에서 값을 뽑는 키 이름·동의어·단위) + **설정 키**(시작 코드 설정 파일에서 이 값을 담는 키, 예 `spring.datasource.hikari.maximum-pool-size`) (예: `pool_size`, `concurrency`, `query_delay_ms`, `inject_commit_failure_ids`) | `HiddenPlan.harness` 검사 (§3.3), 정적 검사 (§6) |
| `failure_reasons` | 사유 코드 → 스택별 로그·예외 패턴 (예: `pool_acquire_timeout` ← Hikari "Connection is not available" / Prisma `P2024`, `tx_start_timeout` ← Prisma `P2028` 시작 대기) | `HiddenPlan.cases` 검사, verifier 사유 대조 (게이트 ③) |
| 결과 분류 | 실행기가 대상마다 `SETUP-ERR`(빌드·기동 실패) / `ASSERT`(단언 실패) / `HARNESS-ERR`(하네스 예외) / `PASS` 를 낸다 | 실패 배정 (§7) — Next.js 손 예시가 이미 `SETUP-ERR` 를 따로 냄 |
| `stack_conditions` | 이 스택에서 허용 설계가 성립하는 조건 (§4.2) | `gen_accepted` |

### 4.2 허용 설계의 스택 조건

- 재료의 허용 설계(`accepted_designs`)는 스택 구분이 없다. 같은 설계라도 스택마다 자연스러운 변형이 함정에 걸린다.
  - Next.js 손 예시: 콜백 안에서 `$transaction` 을 한 번 더 여는 변형, 실패 기록을 콜백 안 catch 에서 기본 클라이언트로 쓰는 변형이 t1 에서 떨어졌다 (`delivery-audit-nextjs/REPORT.md` §8).
- 그래서 `gen_accepted` 에는 허용 설계 1건과 함께 **그 스택의 조건**(템플릿 `stack_conditions` 또는 재료의 스택별 메모)을 준다. 이것이 없으면 §7 에서 "허용 구현 하나만 실패 → 그 구현" 으로 잘못 배정될 수 있다.
- 조건의 원천(재료에 둘지, 템플릿에 둘지)은 [미정] — 같은 원리(커넥션 하나 쓰는 순서)의 스택별 표현이라 템플릿 쪽이 재사용이 낫다.

### 4.3 공개 테스트의 저장·작성자

공개 테스트를 지원자에게 줄지(§4 [미정])에 따라 둘 곳과 쓰는 생성기가 다르다. `starter_file.kind`(#52)에 **`public_test`** 를 더한다 [제안].

| | 지원자에게 줌 | 주지 않음 |
|---|---|---|
| `kind` | `starter` (응시용 이미지에 들어감) | `public_test` (채점용 이미지에만 — `hidden` 과 같은 취급, 응시용·API·로그 노출 금지) |
| 쓰는 생성기 | `gen_public` [확정: 2026-11-08 — 테스트 먼저] | `gen_public` — 공개 정보만으로 쓰는 테스트라 `gen_hidden` 에 맡기지 않는다 (숨은 테스트와 섞이면 게이트 ⑤ 누설 판정이 흐려짐). 처음 안(`gen_starter` 가 같이 씀)은 시작 코드가 자기 테스트에 맞춰져 테스트 먼저가 안 됨 |
| README "계약" 절 | `public_tests` 목록 실음 | 목록 빼고 공개 수용 기준 문장만 (기준 자체는 원래 공개) |
| 검증 | 시작 코드에서 **실패**(구현 전임을 확인 — 게이트 ② 의 기존 테스트 통과와 별개), 참조 구현에서 통과, ⑤ 누설 | 같음 (채점용 이미지에서 실행) |

- 둘 다 채점에는 쓴다: 채점용 `grade` 가 공개 테스트와 숨은 테스트를 함께 돌리고 `result.json` 의 케이스 `kind` 로 구분한다 (`public` / `hidden`).

## 5. 2단계(디버깅) 자료와의 관계

- 기능형 2단계 증상(`debug_stage.scenario`)은 "흔한 구현을 배포한 뒤 생기는 증상"이다. 지금은 명세 생성 때 LLM 이 자료(로그·지표)를 글로 쓴다.
- 이 파이프라인에서는 흔한 구현을 실제로 돌리므로 **그 실행 기록(시간 초과 로그·풀 대기 지표)으로 2단계 자료를 만들 수 있다** [제안]. 실행에서 나온 사실이라 "자료가 원인과 맞지 않는" 문제가 줄어든다.
  - 근거: 기능형 서술 v6 평가(2026-11-06)에서 LLM 이 쓴 자료가 판정 낱말("missing"·"mismatch")·금지어 때문에 재요청 뒤에도 떨어진 일이 있었다.
- 다만 2단계 자료는 이미 승인된 명세의 일부라, 바꾸면 명세 판이 바뀐다. 1차 범위에서는 **비교만** 한다: 실행 기록이 명세 2단계 자료와 어긋나면 승인 화면 `review_flags` 로 알린다 [제안]. 자료 교체는 [미정].

## 7. 실패 배정 · 수리 (`repair`) [제안]

검증 실패를 **어느 산출물의 잘못인지** 가른 뒤 그것만 다시 만든다. 다시 만들 때는 실패 사유(게이트·케이스 id·사유 코드 — 다른 산출물 본문은 아님)를 붙인다. 배정은 실행기의 결과 분류(§4.1: `SETUP-ERR` / `ASSERT` / `HARNESS-ERR`)와 사유 코드를 근거로 한다.

  - **④ 함정에 빠진 허용 구현 먼저** (2026-11-15, `repair._gate4`): 허용 구현이 모두 숨은 케이스에서 떨어지면 테스트를 의심하지만, 모두 그 케이스의 의도한 사유(흔한 구현이 빠지는 함정)로 떨어지고 흔한 구현도 그 사유로 잡혔으면 "구현들이 설계를 못 따름" 과 "테스트가 올바른 설계까지 함정으로 봄" 을 가를 수 없다 — 싼 쪽부터 허용 구현을 한 번 다시 만들고, 그래도 모두 같으면 테스트를 의심한다 (사유 표시가 잘못 붙은 테스트일 수 있어 이 출구는 남긴다). 근거: 프론트 빌드 b2 에서 맞던 숨은 테스트를 다시 만들어 깨뜨렸다.
  - **기동 실패 근본 원인**: 기동 실패면 가장 깊은 `Caused by` 한 줄을 수리 요청에 싣는다 (`TargetRun.setup_detail`).
- **예산**: 산출물마다 재생성 1회(컴파일 오류만이면 2회), 빌드 전체 재생성 최대 3회 [제안]. 예산을 넘거나 배정이 모호하면(두 쪽 다 의심) 재생성하지 않고 `failed` — 승인자가 다시 빌드 · 문서 과제로 전환 · 명세 수정 중 고른다 (§4 그대로).
- 시작 코드를 다시 만들면 그 위에 쓴 참조 구현도 무효라 `gen_refs` 도 다시 돈다 (숨은 테스트는 그대로 — 계약이 같으므로).
- 계약 자체가 원인으로 보이는 실패(여러 생성기가 같은 엔드포인트에서 서로 다른 형식을 가정, **또는 참조 구현이 모두 같은 계약 제약에 같은 오류로 부딪힘** — 2026-11-07: 명세는 "요청마다 기록(… 이전 상태 …)" 인데 계약이 이전 상태를 필수로 둬 없는 배송 건 요청에서 not-null)는 수리하지 않고 `failed` + 사유 "계약 모호" — 계약을 다시 만들면 모든 산출물이 무효라 비용이 크다. 계약 재생성 허용 여부 [미정].
- 수리 이력(어떤 게이트 → 어떤 산출물 → 결과)은 `common_task_build` 에 남기고 승인 화면에 보인다. 내용(코드)은 로그에 남기지 않는다.

- **⑩ 공개 테스트 변별** [확정: 2026-11-13 사용자 — #164 '관문 + 데이터 칸']: 숨은 테스트에는 흔한 구현이 떨어져야 하는 ③ 이 있지만 공개 테스트는
  '시작 코드에서 실패·참조 구현은 통과'만 봤다. 그래서 확인 방법이 한 점·느슨해도 막는 것이 없었다 (손 시범 후보 5건 중 4건, `plan_contract` v26 지침만으로는
  qwen 4건 중 1건). ⑩ 은 경우(경계·정렬·건수·거르기·값)를 나열하지 않고 원칙을 잰다. 변형은 공개 테스트를 통과한 허용 구현이 바뀔 때만 다시 만들고
  (공개 테스트만 바뀌면 같은 변형을 다시 돌림), 결과는 `BuildOutcome.variants`·알파 `report.json` `build.variants`. 구현 `starter/variants.py` ·
  `build._variant_gate` · 검증기 `verify_variants`(Gradle·Python·Node). 손 시범 유효성 검사의 돌연변이도 같은 생성기로 만든다 (`eval/pilot/mutants.py`).
  숨은 테스트 쪽은 ③ 이 흔한 구현 하나만 본다 — 허용 설계에 적힌 함정대로 짠 변형까지 넓히는 것은 [미정] (같은 생성기로 가능).

### 7.1 검증 시간 예산 [제안]

- 손 예시 기준 대상 하나(빌드·기동·숨은 테스트)가 40–70초다. 숨은 요구 3·허용 설계 4 면 대상 8개다. 이를 5회 반복하면 약 40분이고, 수리가 붙으면 그 배수가 된다. 운영 서버는 한 대다.
- ④ 를 허용 설계 전부로 하면 설계마다 구현 생성 1회 + 대상 하나(40–70초). ⑪ 은 함정이 적힌 설계마다 생성 1회 + 대상 하나(공개·숨은 테스트 — 40–70초).
- ⑩ 은 변형마다 대상 하나(공개 테스트만, 숨은 테스트 없음 — 약 30초)를 더한다. 공개 수용 기준 3개 × 갈래 최대 3 이면 약 3~5분, 생성 호출은 기준마다 1회.
- 그래서 빌드 파이프라인에서는 단계적으로 돌린다.
  1. **1회 전체 실행**으로 게이트 ①~⑦·⑨ 를 판정하고 실패 배정·수리를 한다.
  2. 통과하면 **시간에 민감한 케이스만**(`manifest` 가 표시한 동시성·지연 케이스, 예 t1) 반복·지연 0·자원 축소로 게이트 ⑧ 을 본다. 대상도 흔한 구현 1·허용 구현 1 로 줄인다.
  3. 5회 전체 반복은 **golden 재현·승격 평가 때만** 돌린다.
- 동시 실행 수는 서버 자원에 맞춘 상한을 둔다 (`starter-templates.md` §11 [미정]).

## 8. 승인 화면 (`starter_approval`)

- 판정 표(대상 × 케이스 × 반복), 게이트 ①~⑨ 결과, 계약, README 미리보기, 바뀐 파일(`starter` 만 — `hidden` 은 케이스 목록·통과 조건 요약까지, 본문은 [미정]), 수리 이력, `review_flags`, 기준 커밋 sha.
- 시작 코드 승인 = 채점 기준 승인이므로(`starter-templates.md` §4) 숨은 테스트를 사람이 어디까지 볼지가 중요하다. 1차는 **케이스 목록 + `HiddenPlan` + 판정 표**를 보이고, 본문은 펼쳐 보기로 [제안].
- **AI 기본 풀이 결과** [제안 — 막지 않는 지표]:
  - `ref_naive` 는 재료에 적힌 흔한 구현이라, 숨은 테스트가 그 실수를 잡는다는 것만 보장한다. 실제 AI 가 그 실수를 하는지는 따로 봐야 한다. 손 예시 Java r1·r2 에서는 4개 모델 모두 함정을 피했다.
  - 그래서 코딩 모델에 응시용 이미지의 README·시작 코드만 주고(재료 힌트 없음) 풀게 한 결과를 채점해 승인 화면에 보인다.
  - 다 통과하는 과제는 "AI 활용 검증" 축을 재지 못한다는 신호다. 승인자가 소재를 바꾸거나 그대로 둘지 판단한다.
  - 비용 때문에 표본으로만 돌릴 수 있다. 모델은 OpenAI·OpenCode 쪽이다 — Claude 는 API 로 부르지 않는다 (사용자 규칙).
  - **실행 구조가 따로 필요하다**: 코딩 모델이 빌드·테스트를 돌려 가며 풀려면 에이전트가 LLM API 를 불러야 하는데, 검증 sandbox 는 `--network none` 이다. 둘을 한 컨테이너에 둘 수 없다.
    - (a) **에이전트 루프는 sandbox 밖**(verifier 쪽 프로세스, LLM API 만 나감)에서 돌리고, 파일 쓰기·명령 실행만 응시용 이미지 컨테이너 안에서 `exec` 로 한다. 컨테이너는 그대로 네트워크 없음. 실제 AI 활용(돌려 보며 고치기)에 가깝다 [제안].
    - (b) 도구 없이 README·시작 코드를 한 번에 주고 구현 파일을 받는다. 만들기 쉽지만 실제 AI 활용보다 약한 기준이라 "AI 도 못 푼다"를 과대평가한다.
    - 어느 쪽이든 새 실행기(에이전트 루프·도구 정의·호출 상한·기록)가 필요해 구현 순서 8 의 범위가 크다. 실행기 안의 응시 기록에 숨은 테스트·참조 구현이 닿지 않게 응시용 이미지만 쓴다.
- 승인 결정: 승인 / 다시 빌드(사유) / 문서 과제로 전환 / 명세 수정 요청(새 판).

- 직군별 하네스가 할 일 (manifest 초안 머리말): 프론트엔드 — 같은 출처 브라우저 탭 N 개·오프라인 전환·로컬 DB 검사, 데이터 엔지니어 — 메타데이터 DB 고정물·권한 확대·배포 파일 원자성, DBA — PostgreSQL 쓰기 부하·오래 열린 트랜잭션·복제 슬롯을 만들고 점검 결과 읽기, ML — 서빙 경로 출력을 바꿔 넣고 배포 전 검증이 막는지.

- **반영 (2026-11-07, `plan_contract` v7 — 이후 CURRENT 로 승격)**: ① 인터페이스 `ui` — 계약 `screens`(경로·요소 test id·역할·브라우저 저장소), 화면이 부르는 서버 API 는 `endpoints`, README 에 화면 절.
  ② 응답 상태는 엔드포인트마다 — HTTP 100~599, cli·file 종료 코드 0~255. ③ manifest `seed_rows` — 끄면 시드·행 배정 대신 계약 `fixtures`(공개 입력 환경)와 숨은 케이스 `setup`(숨김, 하네스가 환경을 바꾸는 단계).
  ④ 공개 조절값은 `hidden_plan.evidence` 에 자료 문장 그대로 + `evidence_value` 에 그 안의 값 글자 — 코드가 자료에 있고 값 글자가 그 안의 값 하나를 가리키는지 확인(`value_check`, 2026-11-15), 템플릿 패턴은 빠른 길로만, LLM 전 사전 검사 폐지(근거가 "없음"인 필수 값이 명세 결함).

### 11.2 서비스 builder (#129, 2026-11-12)

명세 승인과 과제 생성은 따로다 [확정: 2026-11-12 사용자] — 사람이 `POST /common-tasks/{id}/builds` 로 생성을 요청하면 빌드 큐(#128)에
들어가고, API 와 따로 도는 builder(`python -m task_spec.builder`, `src/task_spec/builder/`)가 하나씩 가져간다.

- 순서는 알파(`eval/starter/run_alpha.py`)와 같다: 재료·직군 템플릿 → `plan_contract` → `build_and_repair`(검증은 격리 컨테이너 #127)
  → README → 응시용·채점용 이미지·검증(응시용 오프라인 테스트, 제출물 채점, 응시용 레이어 금지 경로) → 빌드 저장소 적재(review).
- 묶음은 승인 전이라 descriptor 의 `approval=pending` — 전달은 시작 코드 승인(#130) 뒤 approved 로 다시 쓴 묶음만.
- 시작 코드 승인(#130)은 빌드 승인 그래프(`graph/build_approval.py`, interrupt — thread 는 빌드·결과마다)가 DB 에 기록하고, **묶음 확정은 builder**
  (`builder/finalize.py`) [확정: 2026-11-12 사용자 ③ A]: 새 작업을 가져가기 전마다 "approved 인데 확정 전"인 빌드의 descriptor 를 approved 로
  다시 쓰고(SHA256SUMS 갱신 — 저장소가 tar·README 는 그대로인지 검사) 평가 키트(승인자 판단 포함)를 등록한 뒤 `packages_final_at` 을 남긴다.
  전달(#116)은 확정된 빌드만 (`store.request_delivery`). 확정 실패(예: `+dirty` 온톨로지)는 상태를 두고 사유만 남긴다.
- 실행기(`builder/runner.py`)가 상태 전이·비용(작업당 `BUILD_BUDGET_USD`, 하루 `BUILD_DAILY_BUDGET_USD`)·lease heartbeat·실패 사유를 맡고,
  단계(`builder/steps.py`)는 바꿔 끼운다 (시험은 가짜 단계). 실패 사유는 단계 + 원인 요약 또는 예외 종류만 — 생성 코드·명세 원문은
  저장소·로그에 넣지 않는다 (예외 전문은 git 밖 작업 폴더의 error.txt).
  실패한 빌드도 끝까지 가지 못한 데까지의 계약·숨은 계획·승인자 표시·수리 기록을 성공 빌드와 같은 칸에 남긴다 (`BuildRecord.failure`,
  `template_ref` 가 비어 있으면 결과가 아니라 실패 기록으로 읽음) [2026-11-15 — 실패 빌드는 계약을 저장하지 않아 프론트 하네스 경로 버그를
  메시지 구조로만 짚었다]. 사유 칸은 그대로 짧게, 수리 사유 문장은 성공 빌드처럼 DB 에만.
- 설정은 API 의 Settings 와 따로(`BuilderSettings`) — 지원자 데이터 경로·온톨로지를 받지 않는다 (불변식 3). 운영 배포(전용 사용자·
  DB 역할·컨테이너)는 #129 PR 2.
