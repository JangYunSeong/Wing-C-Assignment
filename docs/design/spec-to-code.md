## 0. 요약

- 입력은 **승인된 기능형 공통 과제 판**(`task_kind=feature`)이고, 출력은 **검증을 통과한 오버레이 파일**(`starter` · `hidden` · `ref_*`)과 그것으로 빌드한 응시용·채점용 이미지다 (`starter-templates.md` §6.1).
- 명세는 자연어뿐이라 시작 코드·숨은 테스트·참조 구현이 같이 기댈 기준점이 없다. 그래서 먼저 **공개 계약 `TaskContract`**(API·입출력·엔티티·시드·공개 테스트 목록)를 만들고, 세 생성기는 **계약만 공유하고 서로의 산출물은 보지 않는다** (`starter-templates.md` §5 독립성).
  - 근거: 배송 감사 손 예시를 같은 API 계약·같은 숨은 시나리오로 Java·FastAPI·Next.js 에 만들었더니 판정 표가 세 판 모두 칸 하나 다르지 않았다.
- 숨은 테스트가 쓸 운영 조건(풀 크기·동시 요청·지연 주입 지점)은 계약과 따로 **`HiddenPlan`** 으로 두고 숨은 테스트 생성기만 본다. 계약은 지원자에게 보이는 정보라 숨은 요구를 담지 않는다.
  - `HiddenPlan` 의 수치는 **승인된 명세의 1단계 자료·구체 답에 실제로 있는 값**이어야 한다. 그래야 지원자가 발견할 수 있는 조건으로 채점한다 (§3.3).
- **하네스(지연·오류 주입·커넥션 추적·운영 설정 덮어쓰기)는 템플릿에 고정된 코드**다. LLM 은 하네스 API 를 부르는 케이스만 쓴다. 의도한 실패 사유도 템플릿이 정한 코드 목록에서만 고른다 (§4.1).
- 지원자용 **README 는 LLM 이 쓰지 않는다** — 승인된 명세 문장과 계약으로 결정적으로 채운다 (승인한 문장 = 지원자가 보는 문장).
- 검증(게이트 ①~⑨)이 실패하면 **실패를 원인 산출물에 배정해 그것만 다시 만든다** (산출물마다 1회). 그래도 실패하면 빌드 `failed` 로 승인 화면에 올린다.
- 검증은 **1회 실행 → 시간에 민감한 케이스만 반복** 순서로 시간을 아낀다 (§7.1). 게이트 통과와 별개로 **AI 기본 풀이 결과**를 승인 화면에 지표로 보인다 (막지 않음, §8) [제안].
- 첫 범위: Java Spring 템플릿 v1 하나, 배송 감사 예시를 기준(golden)으로 둔다 (§9).

## 1. 범위 · 경계

| 포함 | 제외 |
|---|---|
| 공통 과제 빌드 그래프(`build_graph`)의 노드: 템플릿 선택 · 계약 · 생성 · 정적 검사 · 수리 | 지원자 run 그래프 (명세 생성·승인 — 지금 그대로) |
| 생성 프롬프트(`prompts/<task>/vN.md`)와 출력 스키마 | 템플릿 자체 작성 (`starter-templates.md` §3, #55) — 단 템플릿이 이 파이프라인에 내줘야 할 것은 §4.1 |
| 실패 배정 규칙, 재생성 예산, 검증 시간 예산 | verifier 실행·게이트 판정 구현 (#55) |
| 평가 방법 (`CURRENT` 승격 조건) | 이미지 빌드·발행·플랫폼 계약 (§6.1, #52) |

- 이 단계의 입력은 공고·온톨로지·명세·카탈로그·프로젝트 설명뿐이다. 지원서는 쓰지 않는다 (불변식 3). 그래서 지원자 데이터가 LLM 으로 가는 경로가 없다 (불변식 2와 무관).
- 시작 시점은 `starter-templates.md` §4 그대로다: **명세 승인 → 빌드 → 시작 코드 승인 → 발행** [확정: 2026-11-06 사용자].

## 2. 흐름

```
명세 승인 (공통 과제 판 approved, task_kind=feature) → common_task_build(pending) 생성
  ① select_template    결정적. 공고 매칭 기술 → 템플릿 id@vN. 없으면 문서 과제 + review_flags (빌드 종료)
  ② plan_contract      LLM 1회 → TaskContract + HiddenPlan
                       → 결정적 검사 (§3.3). 실패하면 사유 붙여 1회 재요청
  ③ 병렬 생성 — 서로의 산출물을 보지 않는다
       gen_starter    계약 + 명세 공개 부분 + 템플릿 → 시작 코드(구현 자리는 비움) + 기존 기능 테스트 (+ 공개 테스트 — §4 [미정])
       gen_hidden     계약 + HiddenPlan + h* 기준·숨은 요구 + 템플릿 하네스 API → 숨은 테스트 케이스 + 케이스 목록
       gen_refs       계약 + 시작 코드 + naive_impl · 허용 설계(+스택 조건) → 흔한 구현들 + 허용 구현들   (시작 코드가 나온 뒤)
       render_readme  결정적. README.tpl.md ← 명세 문장 + 계약
  ④ static_check       결정적 (§6)
  ⑤ build_images       응시용(기준 커밋 포함)·채점용 이미지 (starter-templates.md §6.1)
     → request_verify  verifier 가 게이트 ①~⑨ — 1회 → 시간 민감 케이스만 반복 (§7.1)
     (ai_baseline)     선택: 코딩 모델의 기본 풀이를 채점 — 지표만, 막지 않음 (§8) [제안]
  ⑥ repair             실패를 원인 산출물에 배정 → 그것만 재생성 → ④ 로 (§7)
  ⑦ starter_approval   interrupt — 판정 표 · 계약 · 바뀐 파일(starter) · 수리 이력 · AI 기본 풀이 결과
  ⑧ publish            검증한 다이제스트를 그대로 (starter-templates.md §6.1)
```

- `gen_refs` 는 시작 코드가 있어야 그 위에 구현을 쓸 수 있어 `gen_starter` 뒤에 돈다. `gen_hidden` 은 `gen_starter`·`gen_refs` 와 병렬이다 (숨은 테스트는 시작 코드 내부를 보지 않는다 — 게이트 ⑥).
- 상태 `common_task_build.status`: `pending → generating → verifying → review`(실패 `failed`) `→ approved → published` (§4 그대로). `repairing` 은 따로 두지 않고 `generating` 으로 돌아간다.
- 그래프 State 는 오버레이 **본문을 담지 않는다** — 파일은 `starter_file` 테이블(#52)에 쓰고 State 에는 `(kind, path, sha256)` 목록만 (체크포인트 크기·숨은 테스트 노출 방지).
- **응시용 이미지의 기준 커밋** [제안]: 응시용 이미지를 만들 때 작업 경로를 git 저장소로 만들고, 조립 트리로 첫 커밋을 고정 작성자·고정 시각으로 넣는다. 그러면 기준 커밋 sha 가 모든 지원자에게 같고, 응시 중 커밋 기록(플랫폼 쪽)의 시작점을 sha 하나로 대조할 수 있다. sha 는 이미지 라벨과 `common_task_build` 에 남긴다.

## 3. 공개 계약 `TaskContract` · `HiddenPlan`

### 3.1 왜 필요한가

- 숨은 테스트는 **공개 계약으로만** 판정한다 (게이트 ⑥). 계약이 없으면 생성기마다 엔드포인트·필드 이름을 따로 상상해, 검증 실패의 대부분이 "함정"이 아니라 "서로 안 맞음"(404·역직렬화 오류)이 된다.
- 독립성(테스트와 구현이 같은 오해를 공유하지 않게)과 일관성(같은 인터페이스)을 동시에 얻는 방법은 **작은 공통 기준점 하나만 공유**하는 것이다.

### 3.2 형태 [제안]

```
TaskContract                         ← 지원자에게 보임 (README "계약" 절)
  interface_kind: http | cli | file   (템플릿 manifest 가 허용하는 것 중)
  endpoints[]:  id(e1…) · method(http 만) · path · summary · headers · query · request(필드) · responses(상태 코드·설명·본문 필드 또는 returns: m1 · m1[]) · refs(r*·p*)
  entities[]:   id(m1…) · name · fields · relations      ← #58 [데이터 모델]
    필드:        name · type · required · constraints · refs(r*·p* — 이 필드가 나온 공개 요구·수용 기준, 1개 이상)
  seed[]:       entity id · 행 수 범위 · 값 규칙 (가상 데이터만)
  public_tests[]: id(pt1…) · ac_id(p*) · 무엇을 확인하나 (공개 수용 기준 1:1 이상)
                  — README 에는 공개 테스트를 지원자에게 줄 때만 싣는다 (§4.3)
  covers:       req_id(r*) → endpoint/entity id 목록

HiddenPlan                           ← 숨은 테스트 생성기만 봄 (지원자·시작 코드 생성기에 안 감)
  harness:      템플릿 manifest 가 선언한 조절값(harness_params)에 넣을 값만 — 풀 크기 · 동시 요청 · 지연/오류 주입 지점과 값
                ← 승인된 명세 1단계 자료·구체 답의 수치와 같아야 함 (§3.3)
  cases[]:      id(hc1…) · ac_id(h*) · trap_id · 시나리오 한 줄 · 기대(통과 조건) · 의도한 실패 사유(템플릿 failure_reasons 코드)
```

- 구현: `src/task_spec/schemas/build.py`(`TaskContract`·`HiddenPlan`·`GeneratedFiles`·`FileRef`·`BuildState`), `src/task_spec/schemas/template.py`(manifest 중 이 파이프라인이 쓰는 부분 — `harness_params`·`failure_reasons`·`naming`·`interfaces`·`stack_conditions`). 필드마다 `refs` 를 두어 양방향 대응(§3.3)을 필드 단위로 본다.

- 계약은 **무엇을**만 적고 어떻게(트랜잭션 경계·잠금·캐시)는 적지 않는다. 숨은 요구 핵심어(seed `leak_terms`·`trigger_terms`)는 계약에 나오면 안 된다 (§3.3).
- `HiddenPlan.cases[].의도한 실패 사유`는 게이트 ③ 의 "실패 사유가 의도한 것" 판정에 그대로 쓴다 (예: `pool_acquire_timeout`). verifier 의 보고서 파서가 이 코드로 대조한다. 코드는 자유 글이 아니라 템플릿 `failure_reasons` 목록에서만 고른다 (§4.1).
- 프로젝트 설명(#58)이 없으면 엔티티·수치는 명세(`scenario`·자료)와 seed 에서만 뽑는다.

### 3.3 결정적 검사

- **양방향 대응**:
  - 모든 `r*` 가 `covers` 에 있고, 모든 `p*` 에 공개 테스트가 하나 이상, 모든 `h*` 에 `HiddenPlan.cases` 가 하나 이상.
  - 거꾸로 **계약의 모든 엔드포인트·엔티티·필드가 어떤 `r*`·`p*` 에서 나온다** — 요구에 없는 필드(예: 재시도 키·처리 상태 필드)는 낱말 목록에 안 걸려도 구조로 해법을 흘린다.
- 계약의 경로·필드·이름이 템플릿 `fill_slots`·명명 규칙과 맞는다 (예: Spring 패키지 경로, HTTP 경로 문자).
- 계약 전체 문자열에 `leak_terms`·`trigger_terms`·`stage2_cause_terms` 가 없다 (기능형 서술 검사와 같은 낱말 목록·같은 함수 재사용).
- **`HiddenPlan` 수치 = 명세에 보이는 수치**: `harness` 의 각 값(풀 크기·동시 요청 수 등)이 승인된 명세의 1단계 자료 본문이나 추가 요구 구체 답(`answer`)에 나온다. 없으면 지원자가 발견할 수 없는 조건으로 채점하게 되고, 다르면 자료와 채점이 어긋난다.
  - 손 예시: 풀 8·동시 32 가 요청 자료 a2(운영 설정)·a3(요청 지표)와 진행자 구체 답에 있고, 하네스가 같은 값을 운영 설정으로 덮어썼다.
  - **대조 방법**: 자유 글의 숫자를 그대로 찾지 않는다 ("8" 은 아무 데나 나온다). 템플릿 `harness_params` 마다 **표기 패턴**(키 이름·동의어·단위, 예: `pool_size` ← `maximumPoolSize=8` · `풀 8개` · `connection_limit=8`)을 두고, 자료 본문·구체 답에서 그 패턴으로 뽑은 값과 같은지 본다. 패턴으로 못 뽑으면 "없음"이다.
  - **명세에 수치가 없으면 재요청으로 고칠 수 없다** — 명세는 이미 승인됐고 `plan_contract` 는 명세를 바꾸지 않는다. 그래서 재요청하지 않고 바로 빌드 `failed`, 사유 "명세 1단계 자료에 운영 수치 없음 (`<param>`)" → 승인자가 **명세 수정 요청(새 판)** 을 고른다.
  - 이런 실패를 줄이려고 명세 단계에서 먼저 막는다 [제안]: 기능형 서술 검증(`spec/feature.py` 의 운영 조건 검사 옆)에 "템플릿이 정해지는 기능형이면, 1단계 자료·구체 답에 그 템플릿 `harness_params` 의 필수 값이 패턴으로 뽑힌다"를 더해 명세 생성 때 재요청한다. 명세 단계는 템플릿을 모르므로 `select_template` 을 명세 승인 전에도 한 번 돌려 필수 키만 넘긴다.
- `harness` 의 키는 템플릿 `manifest.harness_params` 안의 것만, `cases[].의도한 실패 사유`는 `manifest.failure_reasons` 안의 코드만.
- 크기 상한: 엔드포인트 1–6, 엔티티 1–8 (60분 과제 기준 [미정]).
- **명세에 나온 API 는 계약에** (2026-11-07 스모크에서 보탬): 제목·상황·공개 요구·공개 수용 기준에 나온 `METHOD /path`(기존 API 포함)가 계약에 있어야 하고, 공개 테스트·숨은 케이스가 언급하는 API 도 계약에 있어야 한다. 응답 `returns` 는 계약 엔티티를 가리킨다.
- **자료의 운영 값은 모두 HiddenPlan 에**: 선택 조절값이어도 명세 자료에서 표기 패턴·표 열로 뽑히면 넣는다 — 빼면 하네스 기본값이 대신 들어가 실패 사유가 달라진다. 자료에 없는 선택 값을 넣으면 재요청 (지어낸 값).
- 표기 패턴만으로 못 읽는 표(요청 지표처럼 열 이름 + 값 줄)는 manifest `spec_columns`(열 이름 정규식)로 그 열의 숫자를 읽는다.

## 4. 생성기

모든 생성기는 출력이 `{files: [{path, content}]}` 이고, 경로는 `fill_slots`(숨은 테스트는 `hidden/cases/`) 안이어야 한다. 경로 규칙·상한은 `starter/overlay.py` 가 본다 (#55).

| 노드 | 프롬프트 | 보는 것 | 보지 않는 것 | 산출 `kind` |
|---|---|---|---|---|
| `gen_starter` | `gen_starter/v1` | 계약, 명세 공개 부분(제목·상황·요구·공개 기준), 템플릿 골격·`fill_slots` | `HiddenPlan`, 숨은 요구, 허용 설계 | `starter` |
| `gen_hidden` | `gen_hidden/v1` | 계약, `HiddenPlan`, h* 기준, 숨은 요구 설명, 템플릿 하네스 **API 문서**(하네스 코드 자체는 잠김) | 시작 코드 본문, 참조 구현 | `hidden` |
| `gen_naive` | `gen_naive/v1` | 계약, 시작 코드, seed `naive_impl`, (하나만 놓친 판이면) 지킬 숨은 요구 목록 | 숨은 테스트 | `ref_naive` |
| `gen_accepted` | `gen_accepted/v1` | 계약, 시작 코드, 허용 설계 1건(`summary`·`conditions`) + **그 스택의 조건**(§4.2) | 숨은 테스트, 다른 허용 설계 | `ref_accepted` |

- **시작 코드는 "구현 자리를 비운" 코드다**: 엔티티·저장소·컨트롤러 시그니처·시드·기존 기능 테스트까지 쓰고, 기능 본문은 `TODO` 로 둔다(컴파일되게 — Java 는 예외를 던지는 스텁).
- **기존 테스트와 공개 테스트를 구분한다**:
  - 기존 기능 테스트(게이트 ②)는 시작 코드에서 **통과**한다.
  - 새 기능의 공개 테스트는 시작 코드에서 **실패**하고, 허용 구현·흔한 구현 모두에서 **통과**해야 한다 (게이트 ⑤ 누설 없음).
  - **공개 테스트를 지원자에게 줄지는 [미정]**이다. 손 예시는 기존 기능 테스트만 주고 공개 수용 기준은 채점 쪽에서 봤다. 실패하는 공개 테스트를 주면 AI 가 테스트를 돌려 가며 고칠 수 있어 난이도·변별이 달라진다. 어느 쪽이든 저장·작성자가 달라지므로 §4.3 에 둘 다 적는다.
- **흔한 구현 수**: 전부 놓친 판 1개 + 숨은 요구마다 하나만 놓친 판 1개. 숨은 요구가 1개면 둘은 같으므로 1개. **허용 구현 수**: 허용 설계마다 1개.
- 호출 수 = 계약 1 + 시작 코드 1 + 숨은 테스트 1 + 흔한 구현(1 + 숨은 요구 수, 숨은 요구 1개면 1) + 허용 구현(허용 설계 수). 숨은 요구 3·허용 설계 4 면 11회 — 상한 [미정, §10].
- 각 생성기 출력에는 provenance(`prompt_id@version+hash`, 모델·설정, `ontology_version`, 템플릿 ref)를 붙인다 (불변식 8).
- `render_readme`: `README.tpl.md` 의 자리(상황·요구·공개 기준·산출물·계약·실행 방법·채점 방법 한 문장)에 승인된 명세 문장, 계약 표, `manifest.commands` 를 넣는다. LLM 호출 없음. 숨은 수용 기준·숨은 요구·허용 설계·2단계 내용은 자리가 없다.
- `gen_hidden` 에 주는 숨은 요구 설명은 `traps[].description`·h* 기준·`HiddenPlan` 까지다. seed `why_naive_breaks`(흔한 구현이 깨지는 이유)까지 줄지는 [미정] — 주면 실패 지점을 정확히 노리는 테스트가 나오지만, `gen_naive` 가 보는 `naive_impl` 과 같은 서술을 공유해 두 생성기가 같은 이해(같은 오해)를 갖게 된다 (독립성).

### 4.1 템플릿이 이 파이프라인에 내줘야 할 것 (`manifest.yaml` 추가 필드) [제안]

손 예시 세 스택에서 하네스는 스택마다 손으로 다시 짜야 했고 미묘했다:
- Java: BeanPostProcessor 로 지연 주입, Hikari 대기 추적.
- FastAPI: SQLAlchemy 이벤트로 지연·세션 추적.
- Next.js: PostgreSQL 와이어 프로토콜 프록시로 지연·커넥션 추적, 로그로 Prisma 오류 분류.
- 공통: 커밋 시점 오류 주입(지연 제약 트리거), 운영 설정 덮어쓰기(예: `connection_limit=8&pool_timeout=5`).

이것을 LLM 이 매번 쓰면 깨진다. 그래서 템플릿이 고정 코드로 갖고 아래 필드로 내준다.

| 필드 | 내용 | 쓰는 곳 |
|---|---|---|
| `hidden/harness/` (잠김) | 지연·오류 주입, 커넥션·대기 추적, 서버 기동, HTTP 도우미, 운영 설정 덮어쓰기 | `gen_hidden` 은 API 문서만 보고 케이스를 씀 |
| `harness_params` | 조절값 이름·타입·범위·필수 여부 + **표기 패턴**(명세 자료에서 값을 뽑는 키 이름·동의어·단위) + **설정 키**(시작 코드 설정 파일에서 이 값을 담는 키, 예 `spring.datasource.hikari.maximum-pool-size`) (예: `pool_size`, `concurrency`, `query_delay_ms`, `inject_commit_failure_ids`) | `HiddenPlan.harness` 검사 (§3.3), 정적 검사 (§6) |
| `failure_reasons` | 사유 코드 → 스택별 로그·예외 패턴 (예: `pool_acquire_timeout` ← Hikari "Connection is not available" / Prisma `P2024`, `tx_start_timeout` ← Prisma `P2028` 시작 대기) | `HiddenPlan.cases` 검사, verifier 사유 대조 (게이트 ③) |
| 결과 분류 | 실행기가 대상마다 `SETUP-ERR`(빌드·기동 실패) / `ASSERT`(단언 실패) / `HARNESS-ERR`(하네스 예외) / `PASS` 를 낸다 | 실패 배정 (§7) — Next.js 손 예시가 이미 `SETUP-ERR` 를 따로 냄 |
| `stack_conditions` | 이 스택에서 허용 설계가 성립하는 조건 (§4.2) | `gen_accepted` |

### 4.2 허용 설계의 스택 조건

- 재료의 허용 설계(`accepted_designs`)는 스택 구분이 없다. 같은 설계라도 스택마다 자연스러운 변형이 함정에 걸린다.
  - Next.js 손 예시: 콜백 안에서 `$transaction` 을 한 번 더 여는 변형, 실패 기록을 콜백 안 catch 에서 기본 클라이언트로 쓰는 변형이 t1 에서 떨어졌다 (`delivery-audit-nextjs/REPORT.md` §8).
- 그래서 `gen_accepted` 에는 허용 설계 1건과 함께 **그 스택의 조건**(템플릿 `stack_conditions` 또는 재료의 스택별 메모)을 준다. 이것이 없으면 §7 에서 "허용 구현 하나만 실패 → 그 구현" 으로 잘못 배정될 수 있다.
- 조건의 원천(재료에 둘지, 템플릿에 둘지)은 [미정] — 같은 원리(커넥션 하나 쓰는 순서)의 스택별 표현이라 템플릿 쪽이 재사용이 낫다.

### 4.3 공개 테스트의 저장·작성자

공개 테스트를 지원자에게 줄지(§4 [미정])에 따라 둘 곳과 쓰는 생성기가 다르다. `starter_file.kind`(#52)에 **`public_test`** 를 더한다 [제안].

| | 지원자에게 줌 | 주지 않음 |
|---|---|---|
| `kind` | `starter` (응시용 이미지에 들어감) | `public_test` (채점용 이미지에만 — `hidden` 과 같은 취급, 응시용·API·로그 노출 금지) |
| 쓰는 생성기 | `gen_starter` (공개 정보만 보므로 그대로) | `gen_starter` 가 같이 쓰되 출력에서 경로로 갈라 `public_test` 로 저장 — 공개 정보만으로 쓰는 테스트라 `gen_hidden` 에 맡기지 않는다 (숨은 테스트와 섞이면 게이트 ⑤ 누설 판정이 흐려짐) |
| README "계약" 절 | `public_tests` 목록 실음 | 목록 빼고 공개 수용 기준 문장만 (기준 자체는 원래 공개) |
| 검증 | 시작 코드에서 **실패**(구현 전임을 확인 — 게이트 ② 의 기존 테스트 통과와 별개), 참조 구현에서 통과, ⑤ 누설 | 같음 (채점용 이미지에서 실행) |

- 둘 다 채점에는 쓴다: 채점용 `grade` 가 공개 테스트와 숨은 테스트를 함께 돌리고 `result.json` 의 케이스 `kind` 로 구분한다 (`public` / `hidden`).

## 5. 2단계(디버깅) 자료와의 관계

- 기능형 2단계 증상(`debug_stage.scenario`)은 "흔한 구현을 배포한 뒤 생기는 증상"이다. 지금은 명세 생성 때 LLM 이 자료(로그·지표)를 글로 쓴다.
- 이 파이프라인에서는 흔한 구현을 실제로 돌리므로 **그 실행 기록(시간 초과 로그·풀 대기 지표)으로 2단계 자료를 만들 수 있다** [제안]. 실행에서 나온 사실이라 "자료가 원인과 맞지 않는" 문제가 줄어든다.
  - 근거: 기능형 서술 v6 평가(2026-11-06)에서 LLM 이 쓴 자료가 판정 낱말("missing"·"mismatch")·금지어 때문에 재요청 뒤에도 떨어진 일이 있었다.
- 다만 2단계 자료는 이미 승인된 명세의 일부라, 바꾸면 명세 판이 바뀐다. 1차 범위에서는 **비교만** 한다: 실행 기록이 명세 2단계 자료와 어긋나면 승인 화면 `review_flags` 로 알린다 [제안]. 자료 교체는 [미정].

## 6. 정적 검사 (`static_check`)

`starter-templates.md` §4-3 을 구체화한다. 모두 결정적이고, 실패하면 그 산출물에 배정한다 (§7).

| 검사 | 대상 | 배정 |
|---|---|---|
| 경로·잠금·상한·`..`·탭/줄바꿈 | 모든 산출물 | 그 생성기 |
| 잠긴 하네스(`hidden/harness/`)를 고침 | `hidden` | `gen_hidden` |
| 숨은 요구 핵심어(`leak_terms`·`trigger_terms`·`stage2_cause_terms`)·숨은 테스트 이름이 공개 파일(코드·주석·README·공개 테스트)에 있음 | `starter`, README | `gen_starter` (README 면 명세 문제 → review_flags) |
| 미끼 코드 — 숨은 요구 쪽 해법·문제 지점을 가리키는 주석·설정이 시작 코드에 있음 (배송 감사 r1 교훈: 풀·스레드 설정과 `REQUIRES_NEW` 가 늘 보였음) | `starter` | `gen_starter` |
| `HiddenPlan` 의 운영 수치가 시작 코드 설정에 박혀 있음 (운영 값은 하네스가 채점 때 덮어쓴다 — 시작 코드에는 개발용 값만). **`harness_params` 의 설정 키에 든 값만** 대조한다 — 코드·주석의 아무 숫자와 비교하면 우연히 같은 값(8·32 등)이 오탐된다. `gen_starter` 는 `HiddenPlan` 을 보지 않으므로 걸리면 대개 템플릿 기본값이 운영 값과 같은 경우 → 템플릿 기본값을 바꿀 신호 | `starter` 설정 파일 | `gen_starter` (템플릿 기본값이면 review_flags) |
| 비밀 값·네트워크 호출·실존 회사·제품 이름 | 모든 산출물 | 그 생성기 |
| 템플릿 기술 밖 언어·새 의존성 | 모든 산출물 | 그 생성기 |
| 숨은 테스트가 내부 클래스·메서드를 import (게이트 ⑥ 사전 확인) | `hidden` | `gen_hidden` |
| 케이스 목록이 `HiddenPlan.cases` 와 1:1, selector 가 실제 테스트에 있음 | `hidden` | `gen_hidden` |

## 7. 실패 배정 · 수리 (`repair`) [제안]

검증 실패를 **어느 산출물의 잘못인지** 가른 뒤 그것만 다시 만든다. 다시 만들 때는 실패 사유(게이트·케이스 id·사유 코드 — 다른 산출물 본문은 아님)를 붙인다. 배정은 실행기의 결과 분류(§4.1: `SETUP-ERR` / `ASSERT` / `HARNESS-ERR`)와 사유 코드를 근거로 한다.

| 실패 | 판정 | 다시 만들 것 |
|---|---|---|
| ① 빌드 실패 / ② 기존 테스트 오류 (시작 코드만으로 컴파일·실행이 안 됨) | 시작 코드 | `gen_starter` |
| 참조 구현이 `SETUP-ERR` (컴파일 오류) | 그 구현 | 해당 `gen_naive` / `gen_accepted` |
| ③ 흔한 구현이 숨은 테스트 통과 · 허용 구현도 모두 통과 | 숨은 테스트가 약함 | `gen_hidden` |
| ③ 흔한 구현이 통과 · 흔한 구현이 숨은 요구를 실제로 지킴 (정적 표지: 예 별도 트랜잭션 없음·재시도 키 있음 — 템플릿별 규칙) | 흔한 구현이 너무 잘 짬 | `gen_naive` |
| ③ 실패하지만 사유 코드가 의도와 다름 — 404·역직렬화 | 계약 불일치 — 오류 위치(테스트 쪽 / 구현 쪽)로 가름 | 해당 생성기 |
| ③ 실패하지만 `HARNESS-ERR` (테스트 자체 예외) | 숨은 테스트 | `gen_hidden` |
| ③' 하나만 놓친 구현이 그 테스트가 아닌 다른 테스트로만 잡힘 | 숨은 테스트 간 의존 | `gen_hidden` |
| ④ 허용 구현이 **모두** 같은 케이스에서 실패 | 숨은 테스트가 너무 엄격 | `gen_hidden` |
| ④ 허용 구현 **하나만** 실패 | 먼저 그 스택 조건(§4.2)을 붙여 그 구현만 재생성 → 그래도 실패면 설계 조건 부족 → review_flags | `gen_accepted` 그 하나 |
| ⑤ 흔한 구현이 공개 테스트에서 실패 | 공개 테스트가 함정을 잡음 (누설) | `gen_starter` |
| ⑦ 주입 테스트가 허용 설계를 떨어뜨림 | 숨은 테스트 — 감점 여부는 `starter-templates.md` §11 [미정] | `gen_hidden` |
| ⑧ 반복마다 결과가 다름 / ⑨ 시간 초과 | 숨은 테스트 불안정·과부하 | `gen_hidden` |

- **예산**: 산출물마다 재생성 1회, 빌드 전체 재생성 최대 3회 [제안]. 예산을 넘거나 배정이 모호하면(두 쪽 다 의심) 재생성하지 않고 `failed` — 승인자가 다시 빌드 · 문서 과제로 전환 · 명세 수정 중 고른다 (§4 그대로).
- 시작 코드를 다시 만들면 그 위에 쓴 참조 구현도 무효라 `gen_refs` 도 다시 돈다 (숨은 테스트는 그대로 — 계약이 같으므로).
- 계약 자체가 원인으로 보이는 실패(여러 생성기가 같은 엔드포인트에서 서로 다른 형식을 가정)는 수리하지 않고 `failed` + 사유 "계약 모호" — 계약을 다시 만들면 모든 산출물이 무효라 비용이 크다. 계약 재생성 허용 여부 [미정].
- 수리 이력(어떤 게이트 → 어떤 산출물 → 결과)은 `common_task_build` 에 남기고 승인 화면에 보인다. 내용(코드)은 로그에 남기지 않는다.

### 7.1 검증 시간 예산 [제안]

- 손 예시 기준 대상 하나(빌드·기동·숨은 테스트)가 40–70초다. 숨은 요구 3·허용 설계 4 면 대상 8개다. 이를 5회 반복하면 약 40분이고, 수리가 붙으면 그 배수가 된다. 운영 서버는 한 대다.
- 그래서 빌드 파이프라인에서는 단계적으로 돌린다.
  1. **1회 전체 실행**으로 게이트 ①~⑦·⑨ 를 판정하고 실패 배정·수리를 한다.
  2. 통과하면 **시간에 민감한 케이스만**(`manifest` 가 표시한 동시성·지연 케이스, 예 t1) 반복·지연 0·자원 축소로 게이트 ⑧ 을 본다. 대상도 흔한 구현 1·허용 구현 1 로 줄인다.
  3. 5회 전체 반복은 **golden 재현·승격 평가 때만** 돌린다.
- 동시 실행 수는 서버 자원에 맞춘 상한을 둔다 (`starter-templates.md` §11 [미정]).

## 8. 승인 화면 (`starter_approval`)

- 판정 표(대상 × 케이스 × 반복), 게이트 ①~⑨ 결과, 계약, README 미리보기, 바뀐 파일(`starter` 만 — `hidden` 은 케이스 목록·통과 조건 요약까지, 본문은 [미정]), 수리 이력, `review_flags`, 기준 커밋 sha.
- 시작 코드 승인 = 채점 기준 승인이므로(`starter-templates.md` §4) 숨은 테스트를 사람이 어디까지 볼지가 중요하다. 1차는 **케이스 목록 + `HiddenPlan` + 판정 표**를 보이고, 본문은 펼쳐 보기로 [제안].
- **AI 기본 풀이 결과** [제안 — 막지 않는 지표]:
  - `ref_naive` 는 재료에 적힌 흔한 구현이라, 숨은 테스트가 그 실수를 잡는다는 것만 보장한다. 실제 AI 가 그 실수를 하는지는 따로 봐야 한다. 손 예시 Java r1·r2 에서는 4개 모델 모두 함정을 피했다.
  - 그래서 코딩 모델에 응시용 이미지의 README·시작 코드만 주고(재료 힌트 없음) 풀게 한 결과를 채점해 승인 화면에 보인다.
  - 다 통과하는 과제는 "AI 활용 검증" 축을 재지 못한다는 신호다. 승인자가 소재를 바꾸거나 그대로 둘지 판단한다.
  - 비용 때문에 표본으로만 돌릴 수 있다. 모델은 OpenAI·OpenCode 쪽이다 — Claude 는 API 로 부르지 않는다 (사용자 규칙).
  - **실행 구조가 따로 필요하다**: 코딩 모델이 빌드·테스트를 돌려 가며 풀려면 에이전트가 LLM API 를 불러야 하는데, 검증 sandbox 는 `--network none` 이다. 둘을 한 컨테이너에 둘 수 없다.
    - (a) **에이전트 루프는 sandbox 밖**(verifier 쪽 프로세스, LLM API 만 나감)에서 돌리고, 파일 쓰기·명령 실행만 응시용 이미지 컨테이너 안에서 `exec` 로 한다. 컨테이너는 그대로 네트워크 없음. 실제 AI 활용(돌려 보며 고치기)에 가깝다 [제안].
    - (b) 도구 없이 README·시작 코드를 한 번에 주고 구현 파일을 받는다. 만들기 쉽지만 실제 AI 활용보다 약한 기준이라 "AI 도 못 푼다"를 과대평가한다.
    - 어느 쪽이든 새 실행기(에이전트 루프·도구 정의·호출 상한·기록)가 필요해 구현 순서 8 의 범위가 크다. 실행기 안의 응시 기록에 숨은 테스트·참조 구현이 닿지 않게 응시용 이미지만 쓴다.
- 승인 결정: 승인 / 다시 빌드(사유) / 문서 과제로 전환 / 명세 수정 요청(새 판).

## 9. 평가 · 승격

- **기준 예시(golden)**: 배송 감사 손 예시 — `/ssd/make_task/data/feature_starters/delivery-audit/`(Java r2b), `delivery-audit-fastapi/`, `delivery-audit-nextjs/` (git 밖, **개발 서버**. 운영 서버에는 없다 — golden 재현은 개발 서버에서 하거나, 운영 서버로 옮길 때 지원자 데이터가 아님을 확인하고 `data/` 아래로. 의존성은 2026-11-06 정리, 잠금 파일로 다시 설치).
  - 세 판이 같은 계약이라 **스택이 바뀌어도 같은 판정 표**가 나오는지까지 볼 수 있다.
  - 같은 명세로 파이프라인을 돌려 판정 표가 손 예시와 같은 모양인지 본다: 흔한 구현 t1·t2·t2-commit FAIL, 하나만 놓친 구현 t1·t2-commit FAIL, 허용 설계 ALL PASS, 5회 동일.
- **통과율**: 백엔드 기능형 seed 6건 이상으로 빌드 성공률(재생성 포함) · 재생성 횟수 · 게이트별 실패 분포 · 생성 시간·비용.
- **AI 단독 풀이**: 생성된 시작 코드 + README 만 주고 코딩 AI 가 구현 → 숨은 테스트 채점 (`starter-templates.md` §9 와 같은 방식). 손 예시 r1 에서 4개 모델 모두 함정을 피했으므로 **판별력은 소재 문제**이고, 이 파이프라인의 승격 조건은 "손 예시와 같은 판정 표를 재현"까지로 둔다 [제안]. 판별력은 §8 의 AI 기본 풀이 지표로 과제마다 따로 본다.
- 프롬프트별 `CURRENT` 승격은 평가 통과 후 (불변식 7). 생성기는 따로 승격한다.

## 10. 미정 · 결정 필요

1. **코드 생성 모델**: 지금 `opencode:qwen3.8-flash` 는 명세 생성에서도 출력 2만 토큰+·스키마 오류·빈 응답 재시도가 잦았다. 코드 생성(특히 숨은 테스트·계약)은 더 강한 모델로 나눌지. 이 단계 입력에는 지원자 데이터가 없어 외부 모델 제약은 없다 (Claude 는 API 로 쓰지 않는다).
2. **숨은 테스트와 참조 구현을 다른 모델로** 쓸지 (독립성, `starter-templates.md` §5).
3. **호출 수 상한**: 숨은 요구 3·허용 설계 4 면 생성 11회 + 검증 대상 8개. 숨은 요구·허용 설계 수 상한을 둘지, 하나만 놓친 판을 생략할 조건.
4. **계약을 언제 승인하나**: 시작 코드 승인 때 함께(지금 안) / 명세 승인 쪽으로 당김(계약이 바뀌면 시작 코드가 무효라 일찍 정하는 편이 쌈).
5. **계약 재생성 허용** (§7) — 허용하면 모든 산출물 재생성.
6. **2단계 자료를 실행 기록으로 교체**할지 (§5).
7. **승인자가 숨은 테스트 본문을 보는 범위** (§8).
8. 프로젝트 설명(#58)이 있을 때 `[데이터 모델]`·규모 수치를 계약·`HiddenPlan` 에 **그대로** 쓸지, 가상화(업종·이름 바꿈)를 거칠지 — 명세 생성과 같은 규칙이어야 한다.
9. **공개 테스트를 지원자에게 줄지** (§4) — 주면 난이도·변별이 달라진다.
10. **AI 기본 풀이**(§8) 표본 비율·모델·비용 상한, 그리고 "다 통과"일 때 승인 화면에서 무엇을 권할지.
    - 실행 구조: (a) sandbox 밖 에이전트 루프 + 컨테이너 `exec` / (b) 도구 없는 한 번 생성 (§8). (a) 면 새 실행기를 만든다.
11. **허용 설계 스택 조건의 원천** (§4.2) — 재료 / 템플릿.
12. **검증 시간 예산** (§7.1) — 시간 민감 케이스 반복 횟수, 동시 실행 상한.
13. **명세 단계에서 운영 수치를 미리 검사**할지 (§3.3) — 하면 명세 승인 전에 `select_template` 을 한 번 돌려야 한다.
14. **`gen_hidden` 에 `why_naive_breaks` 를 줄지** (§4) — 정확도 / 독립성.
15. **`kind=public_test` 추가** (§4.3, #52 테이블).
