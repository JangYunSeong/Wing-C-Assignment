# 기능 개발형 공통 과제의 시작 코드 — 템플릿 설계 (직군 확장 포함) [제안]

> 상태: 설계 초안 (2026-11-06, 전달 방식 2026-11-07 변경 — §6). 관련: `docs/design/feature-task-backend.md` (기능 개발형 과제 설계).
> 결정 표기는 온톨로지 레포와 같다 — `[확정]` / `[제안]` / `[미정]`.

## 0. 요약

- 기능 개발형 과제는 지원자가 받아서 바로 구현을 시작할 **시작 코드(뼈대 프로젝트)** 가 있어야 한다.
- **스택별 고정 템플릿**을 레포에 버전 고정으로 두고, LLM 은 템플릿이 허용한 자리(엔티티·서비스·설정 값·기존 테스트 등)만 채운다 [제안]. LLM 이 프로젝트 전체를 쓰지 않으므로 빌드가 덜 깨지고 출력이 몇천 토큰으로 줄어든다.
- 생성된 시작 코드는 **격리된 빌드 컨테이너**에서 검증한다: 빌드 · 기존 테스트 통과 · **흔한 구현(참조 풀이)은 숨은 테스트에서 실패 · 허용 설계는 통과**. 숨은 요구가 함정으로 작동하는지를 실행으로 확인한다.
- 응시 플랫폼에는 과제 판마다 **응시용·채점용 컨테이너 이미지 두 개**를 다이제스트로 넘긴다 [확정: 2026-11-07 사용자 — SFTP·JSON 묶음 폐기]. P1 검증도 같은 채점용 이미지로 돌리므로 검증한 것 = 채점하는 것 (§6).
- 백엔드부터 시작해 **프론트엔드 · 데이터 엔지니어 · AI 엔지니어 · DBA** 로 넓힌다 [확정: 2026-11-06 사용자 — 직군 확장]. 템플릿 구조·검증 흐름은 직군과 무관하게 같고, 직군마다 스택과 검증 방법만 다르다.

## 1. 왜 템플릿인가

| 방식 | 장점 | 단점 |
|---|---|---|
| LLM 이 프로젝트 전체 생성 | 유연함 | 빌드 설정·의존성 버전이 자주 깨짐, 출력 1만 토큰 이상, 매번 리뷰 불가 |
| **고정 템플릿 + LLM 은 허용 자리만** | 결정적 빌드 설정, 리뷰·롤백 가능, 출력 수천 토큰, 템플릿 단위 CI | 스택마다 템플릿 유지 비용 |

공통 과제는 공고당 한 번 만들고 그 공고 지원자 모두 같은 과제를 받으므로(불변식 3), 생성 비용은 지원자 수에 비례하지 않는다.

## 2. 직군별 스택 — 시범 공고 근거

온톨로지 시범 공고의 문장↔도구 연결(`line_tool`)에서 공고 수를 셌다 (한 공고에 여러 개 가능).

| 직군 (`sub`, 시범 공고 수) | 많이 나온 언어·프레임워크·플랫폼 | 첫 템플릿 [제안] | 다음 |
|---|---|---|---|
| 백엔드 (`sw.backend`, 105) | Java 87, Spring 55·Spring Boot 37, JPA 13, PostgreSQL 35, C# 16, JS 17·Node.js 5, Python 7 | **Java 17 + Spring Boot 3 + JPA + H2 (Gradle)** | **Python FastAPI + SQLAlchemy** → **TypeScript Next.js (Route Handler·Server Action + Prisma)** → ASP.NET Core, Kotlin(Spring 변형), NestJS(필요 시) |
| 프론트엔드 (`sw.frontend`, 12) | React 8, Vue 4, TypeScript 4, JavaScript 4, 상태관리 3 | **React + TypeScript + Vite + Vitest·Testing Library + 가짜 API(MSW)** | Vue 3 |
| 데이터 엔지니어 (`data.eng`, 11) | Python 10, SQL 9, Spark 7, Airflow 7, Hadoop 6, Kafka 5 | **Python 3.11 + PySpark(로컬 모드) + pytest**, SQL 변형은 DuckDB | Airflow DAG 템플릿(DAG 파싱·태스크 단위 테스트) |
| AI 엔지니어 (`data.ml`, 22) | Python 16, PyTorch/TensorFlow 10, 모델 서빙 5, MLOps 4, Kubernetes 6, LangChain/LangGraph 2 | **Python + FastAPI 서빙 + 작은 CPU 모델(scikit-learn·소형 PyTorch) + pytest** | LLM 앱 변형(LangGraph + 가짜 LLM — 채점에 외부 API 금지) |
| DBA (`infra.dba`, 3) | MySQL·MariaDB·SQL Server·Tibero·MongoDB 각 3, PostgreSQL·Oracle 2, Python·Shell 2 | **PostgreSQL 16 컨테이너 + SQL 스크립트(마이그레이션·인덱스·백업/복구) + 검증 하네스(Python)** | MySQL 8 |

- **백엔드 Python·Node 템플릿** [확정: 2026-11-06 사용자 — 백엔드에 Python·Node 계열 추가]: 온톨로지 공고(623개, 대기업 위주)에서는 Node.js 6 · Next.js 2 · FastAPI 1 · NestJS 1 로 적지만, 스타트업·AI 회사 공고를 덮으려고 공고 수와 별개로 넣는다.
  - Python 백엔드는 FastAPI + SQLAlchemy + pytest — AI 엔지니어 템플릿(FastAPI 서빙)과 빌드 이미지·기반 구조를 같이 쓴다.
  - Node 계열 백엔드는 **TypeScript Next.js** [확정: 2026-11-06 사용자] — Route Handler(`app/api/**/route.ts`)를 API 로, Server Action 을 서버 쪽 변경 처리로 쓰고, DB 는 Prisma + SQLite(시작 코드)·PostgreSQL(변형). 숨은 테스트는 `next build && next start` 로 띄운 서버에 HTTP 계약으로 요청한다 (다른 백엔드 템플릿과 같은 방식). Node 빌드 이미지는 프론트 React 템플릿과 같이 쓴다. NestJS 는 필요할 때 추가한다.
  - 같은 숨은 요구라도 스택마다 재현 방식이 다르다 (예: 풀 교착 — Spring 분리 트랜잭션 / SQLAlchemy 세션 안의 새 세션 / Prisma 대화형 트랜잭션 안에서 트랜잭션 밖 클라이언트로 다시 조회·기록 + `connection_limit`). 소재는 스택마다 빌드 검증(§5 ③~⑤)을 따로 통과해야 한다.
- DBA 는 표본이 3건뿐이라 신뢰도가 낮다. Oracle·Tibero·SQL Server 는 이미지에 넣을 수 없는 라이선스라 템플릿은 PostgreSQL·MySQL 로 한다.
- 데이터 분석(`data.analytics`, 6: SQL 5, Python 4, BI 도구)은 **분석형** — "다시 실행할 수 있는 분석"을 제출물로 받는다 [확정: 2026-11-06 사용자 — 방향]. 템플릿 **DuckDB + SQL + Python(pandas/polars) + pytest** (데이터 엔지니어와 Python 빌드 이미지 공유). BI 도구는 컨테이너 검증이 안 돼 뺀다.
  - 지원자는 `analysis/run.py --data <경로> --out result.json` 을 채운다 (결과 형식은 README 의 공개 계약). 숨은 테스트는 **다른 시드·다른 함정으로 만든 가상 데이터셋**에 그 분석을 다시 돌려, 생성기가 아는 정답(실제 효과·심은 문제)과 비교한다 — 백엔드의 동시 요청 테스트와 같은 자리. 숫자를 박아 넣은 답은 다른 데이터셋에서 틀린다.
  - 함정은 교과서 규칙(SRM·심슨의 역설 등 — AI 가 이미 앎)보다 **데이터를 들여다봐야 보이는 것**(특정 앱 버전의 이벤트 누락·이름 변경, 특정 세그먼트의 실제 감소 등)을 우선한다 (§9 배송 감사 r1 교훈).
  - 첫 손 예시: "활성 사용자 하락" — 측정 착시(t1) + 실제 세그먼트 감소(t2) (`data/feature_starters/mau-drop-analytics/`, git 밖, 작성 중).
- GPU 는 쓰지 않는다 (빌드·검증 환경은 CPU). AI 과제는 작은 모델·적은 데이터로 설계한다.

## 3. 템플릿 구조

```
templates/<직군>/<스택>/vN/
  project/            동작하는 최소 프로젝트 (빌드 설정, 앱 골격, 내장 DB·가짜 서비스, 테스트 설정, 실행 스크립트)
  manifest.yaml       아래 필드
  README.tpl.md       지원자용 README 틀 (공개 요구·공개 수용 기준·산출물·API 계약 자리)
  hidden/harness/     숨은 테스트 하네스 (잠김 — 지연·오류 주입, 커넥션 추적, 서버 기동, HTTP 도우미, 운영 설정 덮어쓰기)
  hidden/cases/       과제별 숨은 테스트 케이스 자리 (오버레이 `kind=hidden` 이 여기만 씀 — spec-to-code.md §4.1)
templates/<직군>/<스택>/CURRENT
```

- 버전은 프롬프트와 같은 규칙 — 기존 `vN` 은 수정하지 않고 새 버전을 추가, `CURRENT` 변경은 평가 통과 후 (불변식 7 과 같은 취지).
- `manifest.yaml`:

| 필드 | 내용 |
|---|---|
| `id`, `version`, `family`, `stack` | 예: `backend/java-spring-boot3-jpa`, v1, 언어·프레임워크·런타임 버전 |
| `build_image` | 검증에 쓸 빌드 이미지 이름·다이제스트 |
| `commands` | `build`, `test`, `hidden_test`, `grade` (컨테이너 안 명령 — `grade` 는 채점용 이미지의 진입점, §6) |
| `workspace` | 응시용 이미지 안 작업 경로 (기본 `/workspace`) |
| `fill_slots` | LLM 이 쓸 수 있는 경로 패턴과 종류 (entity / service / controller / config / seed / existing_test / docs) |
| `locked` | 건드리면 안 되는 파일 (빌드 설정, 래퍼, 하네스) |
| `limits` | 파일 수·크기 상한, 금지 의존성 추가 |
| `network` | 항상 `none` (검증 컨테이너에 네트워크 없음) |

## 4. 생성 흐름

> 생성 단계(공개 계약 · 생성기 · 실패 배정 · 검증 시간 예산)의 구체 설계는 `docs/design/spec-to-code.md` 에 있다.

**시점 [확정: 2026-11-06 사용자]: 공통 과제 명세 승인 → 시작 코드 빌드 → 시작 코드 승인 → 발행.** 시작 코드는 지원자 런 안에서 만들지 않는다.

```
지원자 런:  … draft_spec → approval(interrupt) → finalize
                                  │ 공통 과제 판이 approved 이고 task_kind=feature 면 빌드 작업 생성
                                  ▼
공통 과제 빌드 (공고·판마다 한 번, 지원자 런과 별개):
  select_template → gen_starter ∥ gen_hidden ∥ gen_refs → static_check
  → build_images(응시용·채점용) → verifier(§5 ①~⑨, 그 다이제스트로) → 시작 코드 승인(바뀐 파일·판정 표)
  → publish(같은 다이제스트를 레지스트리에, §6)
```

- 이유: ① 검증이 길다(배송 감사 예시 판정 표 1회 4~5분, ①~⑨ 는 반복·조건 변형까지 20분 이상) — 승인 전에 돌리면 첫 지원자 승인 화면이 그만큼 늦다. ② 승인자가 명세(숨은 요구·난이도)를 고치면 생성물을 버려야 한다. ③ 공고 단위 작업을 지원자 런에 묶지 않는다.
- 상태 `common_task_build.status`: `pending → generating → verifying → review`(실패 `failed`) `→ approved → published`. 공통 과제 판(`common_id`, `revision`)에 묶여, 같은 판을 재사용하는 지원자는 시작 코드도 재사용한다. 명세를 고치면 새 판 → 새 빌드.
- **승인 두 번, 역할이 다르다**: 명세 승인 = 무엇을 측정하나, 시작 코드 승인 = 어떻게 채점하나(숨은 테스트 = 채점 기준). 숨은 테스트를 사람이 보지 않고 발행하지 않는다 — "사람 승인 없이 확정하지 않는다"(불변식 9, AI 기본법 고영향 AI)를 채점 기준까지 넓힌 것.
- 시작 코드 승인은 가볍게: 게이트 ①~⑨ 전부 통과면 판정 표·README 변경만 보고 한 번에 승인, 실패 항목이 있으면 사유를 함께 보여 준다.
- 명세만 승인되고 시작 코드 승인 전이면 그 공통 과제는 응시 플랫폼에 나가지 않는다(`published` 전).

1. 공통 과제 골격(측정 역량·수준·기술 환경·60분)과 유형 `feature` 가 정해지면, 기술 환경으로 템플릿을 고른다 (`stack` 매칭, 없으면 시작 코드 없이 문서 과제로 두고 `review_flags`).
2. 과제 본문(`draft_feature_task`)이 정해지면 코드 생성을 **호출을 나눠** LLM 에 맡긴다. 각 호출은 다른 호출의 산출물을 보지 않는다 (§5 독립성). 경로는 모두 `fill_slots`(숨은 테스트는 `hidden/`) 안에서만.
   - 2a. 시작 코드 `StarterFill {files}` — 과제 본문 + 템플릿.
   - 2b. **숨은 테스트** `HiddenTests {files}` — `acceptance_hidden` + README 의 공개 계약(API·입출력 형식) + 템플릿 `hidden/` 하네스만 본다. 시작 코드 내부 구현은 보지 않는다.
   - 2c. 흔한 구현 `reference_naive` — `naive_impl` 설명 + 시작 코드. 변형 2개 이상: 숨은 요구를 전부 놓친 구현, 숨은 요구 **하나만** 놓친 구현(숨은 요구마다).
   - 2d. 허용 구현 `reference_accepted` — `accepted_designs` **마다 하나** + 시작 코드.
   - 호출이 늘어나는 비용은 생성(OpenCode) 단가 기준으로 작지만, 숨은 요구·허용 설계 수에 비례한다 — 상한 [미정].
3. 정적 검사: 경로·크기·잠긴 파일, 기술 환경 밖 언어, 네트워크 호출·비밀 값, 실존 회사·제품 이름, 공개 파일(README·코드 주석)에 숨은 요구 핵심어가 없는지 (기능형 설계의 "숨은 요구 노출 금지"와 같은 규칙).
4. **빌드 검증** (§5). 실패하면 사유를 붙여 한 번 다시 요청, 그래도 실패하면 빌드 `failed` — 시작 코드 승인 화면에 사유와 함께 올리고, 승인자가 다시 빌드·문서 과제로 전환·명세 수정 중에서 고른다.
5. 통과한 시작 코드는 템플릿 대비 오버레이 파일로 DB 에 저장하고, 공통 과제 판에 템플릿 참조·이미지 다이제스트 두 개·검증 결과를 남긴다 (§6, #52).
   - 이미지는 정적 검사 뒤, 검증 **전에** 만든다. 검증은 그 이미지 다이제스트로 돌리고, 발행은 같은 다이제스트를 올리기만 한다 — 다시 빌드하지 않는다.

| ③ 숨은 테스트 × 흔한 구현 | 목표 숨은 요구 테스트가 **실패**하고, 실패 사유가 의도한 것 (예: 풀 획득 시간 초과). 컴파일 오류·404·테스트 자체 예외는 실패로 치지 않는다 | 실패 요청이 모두 풀 획득 5초 초과로 끝남 |
| ③' 하나만 놓친 흔한 구현 | 숨은 요구마다, 그것만 놓친 구현이 **그 테스트에서** 실패 — 숨은 요구가 다른 테스트에 기대어 잡히는 게 아님을 확인 | 규칙 검사 뒤 기록하는 구현은 t2 통과, t1 으로만 잡힘 |
| ④ 숨은 테스트 × 허용 구현 | `accepted_designs` **각각**의 구현이 전부 통과. 자연스러운 변형이 떨어지면 설계 설명에 조건을 붙이거나 테스트를 고친다 | 설계 1 을 `JdbcTemplate` 로(OSIV 기본값), 설계 2 를 동기 이벤트 리스너로 만든 변형이 t1 실패 → 조건 추가 필요 |
| ⑤ 누설 없음 | 흔한 구현이 공개 수용 기준과 자기 테스트를 **통과** — 공개 기준이 함정을 잡으면 숨은 요구가 새어 나간 것 | "실패 행 추가"형 흔한 구현은 공개 기준 "기록 1건"에 걸림 → 흔한 구현 서술을 좁힘 |
| ⑥ 공개 계약만 사용 | 숨은 테스트는 README 의 공개 계약(HTTP·CLI·파일 형식)으로만 판정. 내부 클래스·메서드 이름에 기대지 않음 | 설계가 달라도 같은 테스트로 채점됨 |
| ⑦ 도달 가능 | 공개 계약으로 숨은 요구를 재현할 수 없으면 하네스 주입(지연·오류)을 쓰되, 주입 테스트도 ④ 를 다시 통과해야 함 | HTTP 로 닿는 롤백이 규칙 위반뿐 → 커밋 오류 주입 테스트를 보탰더니 설계 3 이 떨어짐 (감점 여부 [미정]) |
| ⑧ 반복·여유 | 5회 같은 결과 + 하네스 지연 0 + 자원을 낮춘 설정(예: CPU 2)에서도 같은 결과 | 5회 동일, 지연 0 에서도 5/5 |
| ⑨ 시간 | 숨은 테스트 전체 실행 상한 (예: 3분) | 대상당 약 1분 |

- ③~⑤ 가 숨은 요구의 **기계적 사실 검산**이다 — 지금 이슈형은 LLM 판정(`judge_trap_facts`)으로만 본다.
- **독립성**: 테스트와 참조 구현을 같은 호출(같은 오해)이 쓰면 서로를 통과시킨다. 그래서 §4 2a~2d 를 나누고, 가능하면 숨은 테스트와 참조 구현을 다른 모델로 쓴다.
- **최종 확인은 실제 AI 단독 풀이**: 참조 흔한 구현은 "AI 가 낼 법한" 구현을 사람·LLM 이 흉내 낸 것이다. 시작 코드 + README 만 주고 코딩 AI 가 구현한 결과를 숨은 테스트로 채점해 함정 적중률을 잰다 (§9 평가, 비용 [미정]).
- 보안: LLM 이 쓴 코드를 실행하므로 rootless 컨테이너, **네트워크 없음**, 비밀 값·`.env`·DB 접속 정보 없음, 읽기 전용 마운트 + 작업용 임시 디렉터리, CPU·메모리·시간 상한. API 컨테이너 안에서 돌리지 않는다.
- **검증 = 채점 경로**: ①·② 는 응시용 이미지에서, ③~⑨ 는 참조 구현(`ref_naive`·`ref_accepted`)을 **제출물로 넣어 채점용 이미지의 `grade` 를 그대로** 돌린다 (§6 채점 계약과 같은 마운트·명령·출력). 플랫폼의 실제 채점과 다른 코드 경로가 없다.
- 검증은 공통 과제 생성 때 한 번 (공고당). 지원자 제출물 채점은 플랫폼이 우리 채점용 이미지로 한다 — 실행은 이 설계의 범위가 아니다 (§8).

| 대상 | 위치 | 이유 |
|---|---|---|

| 빌드 환경 | 스택별 **빌드 이미지** — 의존성 캐시를 미리 담음 (Gradle·Maven 오프라인 저장소, npm 캐시, pip wheel) | 운영 서버는 **내부망** — 검증 때 외부 저장소에 못 간다. 지금 배포처럼 이미지 저장·반입(`podman save/load`)으로 들여간다 |
| 생성된 시작 코드 | **DB 오버레이** — 템플릿에 더하거나 바꾼 파일만 `(common_id, revision, kind, path, content, sha256, size)` 로 저장 [확정: 2026-11-06 사용자, #52]. `kind` = `starter` · `hidden` · `ref_naive` · `ref_accepted` | 원본(승인 화면에서 바뀐 파일만 검토, 이미지를 다시 만들 근거). 생성물이라 git 에 넣지 않는다 |

| 참조·검증 결과 | DB — 공통 과제 판(`CommonRef`)에 연결: `template_ref`(id@vN+sha), 응시용·채점용 이미지 다이제스트, 검증 결과(단계별 성공·실패, 반복 수) | provenance (불변식 8 과 같은 취지) |

### 6.1 전달 — 응시용·채점용 이미지 [확정: 2026-11-07 사용자]

예전 안(템플릿 SFTP 폴더 + 지원자용 `starter` JSON + 채점 `testcases` JSON, 2026-11-06)은 **폐기**한다. 플랫폼에는 과제 판마다 이미지 두 개의 다이제스트만 넘긴다.

**왜 두 개인가**: 이미지를 받은 쪽은 레이어를 풀어 안의 파일을 모두 꺼낼 수 있다 (위 레이어에서 지워도 아래 레이어에 남는다). 숨은 테스트(= 채점 기준)가 응시자 컨테이너 이미지에 들어가면 함정이 새어 나간다. 그래서 받는 쪽이 다른 둘로 나눈다.

| | 응시용 (`candidate`) | 채점용 (`grader`) |
|---|---|---|
| 받는 쪽 | 응시 환경 — 지원자가 그 안에서 코딩 | 플랫폼 채점 서버만 |
| 내용 | 템플릿 + `kind=starter` 오버레이 + 문제 README | 템플릿 + `kind=hidden` 오버레이(숨은 테스트·하네스) + `grade` 스크립트 |
| 숨은 테스트 | **없음** | 있음 |
| 레지스트리 권한 | 응시 환경 계정 pull | 채점 계정만 pull (pull 기록) |

- `ref_*`(참조 풀이)는 **어느 이미지에도 넣지 않는다** — P1 검증에서 제출물로 마운트할 때만 쓴다.
- 레이어: `런타임 기반(jvm 등) → 템플릿 vN(뼈대 + 오프라인 의존성 캐시) → 과제 레이어(수십 KB)`. 큰 레이어는 템플릿 수만큼만 생기고 과제마다 늘어나는 건 작은 레이어 둘이다.
- **템플릿 이미지·응시용 이미지에 들어가는 것은 템플릿 `project/` 와 의존성 캐시뿐이다** [확정: 2026-11-07 사용자]. 템플릿 폴더의 `hidden/`(잠긴 하네스·자체 점검)과 `manifest.yaml`(조절값·실패 사유 코드 — 채점이 무엇을 노리는지가 거의 그대로 보임)은 **채점용 레이어에서만** 더한다.
  - 이유: 응시용은 템플릿 이미지 위에 쌓이므로, 템플릿 이미지를 `vN/` 폴더째로 만들면 아래 층에 하네스·manifest 가 남는다 — 레이어를 풀면 보인다.
  - 의존성 캐시도 같다: 하네스 전용 라이브러리(예: Next.js 판의 PG 프록시·채점용 `pg`)는 응시용 이미지에 넣지 않는다 (manifest `image.grader_only_dependencies`).
  - 확인: 응시용 이미지 레이어 검사(#52·#55 수용 기준)의 금지 경로에 `kind=hidden`·`ref_*` 와 함께 템플릿 `hidden/` 의 파일·조립 위치(`hidden_layout`), `manifest.yaml`, 하네스 전용 의존성을 넣는다. 금지 경로 목록은 `starter/templates.py` 가 manifest 에서 계산한다.
- 이름: `task/<common_id>-r<revision>-candidate@sha256:…`, `task/<common_id>-r<revision>-grader@sha256:…`. 태그가 아니라 **다이제스트로만** 참조한다.
- OCI 라벨: `common_id`·`revision`·`template_ref`·`ontology_version`·`tree_sha256`(조립 트리, 감사용). 지원자 데이터 없음.

**플랫폼과의 계약**

| 항목 | 내용 |
|---|---|
| 응시 | 응시용 이미지로 지원자별 컨테이너. 작업 경로 `manifest.workspace`(기본 `/workspace`), 시작 명령, 권장 자원 |
| 제출 | 응시 종료 시 작업 경로를 떠서 제출물로 둔다 (플랫폼 쪽 저장 — 지원자 데이터) |
| 채점 | `podman run --rm --network none -v <제출물>:/submission:ro -v <결과>:/out <grader>@sha256:… grade` — 네트워크 없음 필수, 제한 시간은 라벨 `grade.timeout_s` |
| 결과 | `/out/result.json` — `{common_id, revision, cases:[{id, trap_id, kind, passed, reason}], report_path}` + JUnit 등 원본 보고서. 케이스 목록·선택자는 채점용 이미지 안에 있다 |

- 우리 테스트케이스는 입력→기대 출력 쌍이 아니라 **실행 코드**다 (동시 요청·지연/오류 주입·커넥션 추적) — 그래서 형식(JSON)이 아니라 실행 환경째(이미지) 넘긴다.
- 분석형: 숨은 데이터셋·채점 코드는 채점용 이미지에, 공개 표본 데이터는 응시용 이미지에.
- 지킬 것: 템플릿 `vN` 불변(오버레이는 특정 버전 위에서만 맞음), 경로 검증(상대 경로·`..` 금지·`fill_slots` 안·잠긴 파일 덮어쓰기 금지·수·크기 상한), 승인·발행된 판의 이미지는 재채점 기간까지 지우지 않음.

| 직군 | 기능 과제 예 | 숨은 요구 예 | 기계 검증 방법 |

### 7.1 소재 수집 — 분야별로 모으고 스택별 변형을 만든다 [확정: 2026-11-06 사용자]

언어·프레임워크로 사례를 찾으면 공개 사례가 모자라다 (예: 한국 회사의 FastAPI 장애 글을 찾지 못함 — 성능 팁 글로 대체). 함정의 핵심은 원리(심층 구조)이고 스택은 그릇이므로, **분야(문제 종류)로 모으고 스택마다 코드만 바꾼 변형**을 만든다.

- 분야 예: 트랜잭션·커넥션, 타임아웃·연결 수명, 캐시, 재시도·중복(멱등), 배포 중 버전 혼재, 메모리(힙 밖 포함), 동시성·순서, 이벤트 처리.
- 사례마다 이식성 표시 `portability`: `agnostic`(원리가 스택과 무관 → 스택별 변형 작성) / `bound:<프레임워크>`(그 프레임워크 고유 → 그 템플릿에만).
- 스택별 변형 `stack_variants.<템플릿 id>`: 현상이 생기는 방식, 흔한 구현, 허용 설계(조건 포함), 하네스 주입 방식. **변형마다 §5 ①~⑨ 를 따로 통과해야 쓴다** — "이 스택에서도 재현되는가"를 판단이 아니라 실행으로 확인.
- 숨은 테스트는 공개 계약(HTTP·CLI·파일 형식)만 보므로 **시나리오·판정은 스택 간 재사용**, 하네스(지연·오류 주입·커넥션 추적)는 스택별 `hidden/` 에 둔다.

| 원리 | 이식성 | 스택별로 현상이 생기는 방식 |
|---|---|---|
| 커넥션을 쥔 채 같은 풀의 커넥션을 또 기다림 | agnostic | Spring `REQUIRES_NEW` / SQLAlchemy 요청 세션 안에서 새 세션 / Prisma 대화형 트랜잭션 안에서 바깥 클라이언트 |
| 서버 keep-alive 가 앞단 유휴 시간보다 짧음 | agnostic | Uvicorn·Node `keepAliveTimeout` 기본 5초, Tomcat 설정값 vs 로드밸런서 유휴 시간 |
| 배포 중 버전 혼재 | agnostic (증상은 스택별) | Next.js 페이지 데이터 404 → 강제 새로고침 / 일반 API 응답 형식 불일치 |
| 워커마다 네이티브 라이브러리가 CPU 전부 사용 | 일부 | Python pre-fork + PyTorch·NumPy 스레드 |
| React 이벤트 위임 순서 | bound:react | React 17+ 루트 위임 vs 네이티브 리스너 |

- 확인 중: 배송 감사 예시를 Python FastAPI 로 옮겨 같은 검증을 돌린다 (`data/feature_starters/delivery-audit-fastapi/`, git 밖).

- **포함**: 템플릿, 시작 코드 채우기, 공통 과제 생성 시 빌드 검증, 저장·provenance.
- **포함 (2026-11-07)**: 응시용·채점용 이미지 빌드·발행과 채점 계약(§6.1).
- **제외**: 지원자 제출물 실행·채점, 응시 화면, 제출 저장 — 응시 플랫폼 쪽. 플랫폼은 우리 채점용 이미지로 채점한다 (인계 형식 = 이미지, §6.1).
- `feature-task-backend.md` §2·§10 의 "실제 코드 실행은 범위 밖"은 이 문서로 **좁혀진다**: 과제 생성 때의 검증 실행은 포함, 지원자 채점 실행은 제외.

## 9. 평가 · 승격

- 템플릿마다 CI: 빈 템플릿이 빌드되고 하네스 스모크 테스트가 통과.
- 직군마다 기능형 과제 평가(백엔드 설계 §9 와 같은 틀): 생성 품질 · **빌드 검증 통과율**(① ~ ⑨) · AI 단독 풀이.
- 빌드 검증 통과율이 낮으면(예: 재요청 후 6건 중 5건 미만) 그 템플릿의 `fill_slots` 를 좁히거나 예시를 보강한다.
- **AI 단독 풀이는 Claude Code 세션으로 모델 4종(fable·opus·sonnet·haiku)** [확정: 2026-11-06 사용자 — Anthropic API 를 쓰지 않음]. 시작 코드 사본 + 진행자 도구(자료·질문 횟수 제한)만 주고 격리 폴더에서 풀게 한 뒤 숨은 테스트로 채점하고, 기록에서 금지 경로(숨은 테스트·참조 구현) 접근을 점검한다. 헤드리스 분리 세션(`claude -p`)은 자동 모드 안전 검사에서 막혀, 지금은 세션 안 서브에이전트(모델 지정)로 돌린다.
- 배송 감사 예시 r1 결과: **4개 모델 모두 함정을 피함**(숨은 테스트 전부 통과, haiku 포함) → 이 판은 AI 를 가르지 못한다. 원인 후보 — ① 공개 README 제출물 문구 "어떤 **트랜잭션·커넥션** 사용 방식" 이 함정 지점을 가리킴 (§4 정적 검사의 "공개 파일에 숨은 요구 핵심어 금지"를 손 예시에 적용하지 않았음), ② 풀·스레드 설정과 미끼 코드(`REQUIRES_NEW`)가 저장소에 늘 보임, ③ 원 사례가 유명. 원인을 나눈 재실험(문구 중립 / 설정을 자료로 / 미끼 제거)을 다음에 한다.

## 11. 미정 · 결정 필요

- ~~데이터 분석 직군의 과제 유형~~ → 분석형(다시 실행할 수 있는 분석 + 숨은 데이터셋)으로 정함 (§2, 2026-11-06). 남은 것: 메모(ANALYSIS.md)의 해석·전달 품질을 무엇으로 채점할지 (LLM 판정 기준 + 사람).
- DBA 표본 부족 — 공고를 더 모으거나 인프라 직군과 묶을지.
- ~~숨은 테스트·참조 풀이 전달 (SFTP)~~ → 채점용 이미지로 정함, 참조 풀이는 내보내지 않음 (§6.1, 2026-11-07). 남은 것:
  - 이미지 전달 채널: 내부 레지스트리(권한 분리·pull 기록) / `podman save` tar(지금 배포 방식) — 레지스트리 우선 [제안].
  - 플랫폼이 컨테이너를 응시·채점에 실행할 수 있는지 확인 (B 의 전제).
  - 과제 이미지 보관 기간 (재채점 기간), 이미지 서명(cosign 등) 여부.
  - `result.json` 세부 형식·제한 시간 기본값을 플랫폼과 맞춤.
- 오류 주입 숨은 테스트(§5 ⑦)가 허용 설계 일부를 떨어뜨릴 때 — 테스트를 고칠지, 그 설계를 감점할지 (배송 감사 예시: 커밋 오류 주입이 설계 3 을 떨어뜨림).
- §4 2a~2d 호출 수 상한, 숨은 테스트와 참조 구현을 다른 모델로 쓸지.
- 카탈로그(장애·기능 소재)의 정답 필드(원인·허용 조치·허용 설계)를 레포에 둘지(접근을 과제 설계자로 제한하는 규칙만), 별도 비공개 저장소로 분리할지.
  - 레포 접근자를 위협으로 본다면 **여기가 1순위**다 (2026-11-07): `incidents/public_v1/*.json` 의 feature 블록에 숨은 요구(`hidden_requirement`)·운영 조건(`trigger`)·허용 설계·누설 낱말이 있어, 공고가 어느 재료를 쓰는지만 알면 함정이 그대로 보인다. 템플릿 하네스·manifest 는 "어떤 종류의 함정을 볼 수 있다"까지만 드러내므로 우선순위가 낮다. 과제별 숨은 테스트·참조 풀이는 이미 DB 오버레이(git 밖)다.
- 빌드 이미지 크기·갱신 주기 (의존성 보안 업데이트), 템플릿 유지보수 담당.
- 검증 컨테이너의 자원 상한·동시 실행 수 (운영 서버 한 대).

## 12. 불변식 점검

| 불변식 | 이 설계에서 |
|---|---|
| 1 지원자 데이터 git 밖 | 템플릿은 일반 코드, 생성물은 데이터 볼륨. 지원자 데이터 없음 |
| 2 가명화 → LLM | 시작 코드 입력은 공고·온톨로지·카탈로그뿐 |
| 3 공고만으로 | 시작 코드도 공통 과제의 일부 — 공고 단위, 지원서 미사용 |
| 4 온톨로지 읽기만 | 기술 환경·역량 조회만 |
| 7 버전 관리 | 템플릿도 `vN` + `CURRENT`, 평가 후 변경 |
| 8 provenance | 템플릿 버전·해시, 응시용·채점용 이미지 다이제스트, 검증 결과 |
| 9 승인 interrupt | 명세 승인(지원자 런의 interrupt) 뒤, 시작 코드·숨은 테스트를 **따로 승인**(공통 과제 빌드의 interrupt) — 승인 전 발행 없음 |

**새로 지킬 규칙 (CLAUDE.md 불변식 후보)** [제안]
- LLM 이 쓴 코드는 `verifier` 샌드박스에서만 실행한다 (네트워크·비밀 값 없음). API·LangGraph 프로세스에서 실행하지 않는다.
- `hidden` 은 채점용 이미지에만 들어간다 — 응시용 이미지·API·로그·승인 요약에 나가지 않는다. `ref_*` 는 어디로도 내보내지 않는다.
- 템플릿 `vN` 불변, 조립은 `starter/assemble.py` 하나. 검증한 이미지 다이제스트 = 발행한 다이제스트 (발행 때 다시 빌드하지 않음).

## 13. 구현 레이어 [제안]

P1 의 지금 구조(FastAPI · LangGraph · Postgres)는 그대로 두고 **순수 코어 + 빌드 그래프 + 별도 검증 서비스 + 전달**로 나눈다.

```
templates/<직군>/<스택>/vN/          레포 — 뼈대·manifest.yaml·hidden 하네스 골격 (불변, CURRENT)

src/task_spec/
  starter/          순수 코어 (LLM·네트워크 없음, 아래 모두가 import)
    templates.py      템플릿 레지스트리: manifest·CURRENT·vN 불변 확인
    overlay.py        StarterFile(kind·path·content·sha256) · 경로 규칙(fill_slots·잠금·상한)
    assemble.py       템플릿 + 오버레이(kind 별) → 트리 · tree_sha256  ← 이미지 빌드의 유일한 조립 구현
    static_check.py   공개 파일의 숨은 용어 · 비밀 값 · 네트워크 호출 · 실존 이름
    store.py          starter_file · common_task_build · verify_job (Postgres, #52)
  graph/build_graph.py  공통 과제 빌드 그래프 (지원자 런 그래프와 별개, thread_id = build_id)
  nodes/starter/    select_template · gen_starter · gen_hidden · gen_refs (LLM, prompts/<task>/vN.md)
                    · request_verify (verify_job 넣고 결과 대기, 실패면 사유 붙여 1회 재요청) · starter_approval(interrupt)
  api/routers/common_tasks.py
    GET  /common-tasks/{id}/build        빌드 상태·판정 표·이미지 다이제스트 (승인 화면)
    POST /common-tasks/{id}/build/approve 시작 코드 승인 resume

verifier/          별도 컨테이너 task-verifier (API 와 분리, rootless podman)
  worker.py         verify_job 가져오기 → 과제 이미지 빌드(candidate·grader) → sandbox → 판정 표 → gate
  images.py         템플릿 이미지 + assemble 트리 → candidate·grader 이미지, 라벨, 다이제스트 기록
  publish.py        승인된 판의 같은 다이제스트를 레지스트리에 push (다시 빌드하지 않음)
  sandbox.py        --network none · CPU·메모리·시간 상한 · 읽기 전용 마운트 + 작업용 임시 디렉터리
                    (③~⑨ 는 grader 이미지에 ref_* 를 /submission 으로 마운트해 grade 실행 — 실제 채점과 같은 경로)
  runners/          스택별 실행·보고서 파서: gradle(JUnit XML) · pytest · vitest …
  gate.py           판정 표 → ①~⑨ (반복 5회 · 지연 0 · 자원 축소)

eval/solo/         AI 단독 풀이 하네스 (진행자 도구 · 채점 · 기록 점검) — 런타임 경로 밖
```

| 선택 | 이유 |
|---|---|
| 검증은 별도 서비스 + DB 작업 테이블(`verify_job`) | 신뢰할 수 없는 코드 실행 + 수 분 걸림. 큐를 새로 들이지 않고 지금 Postgres 로 |
| `starter/` 순수 코어를 API·노드·검증 서비스가 함께 import | 조립이 하나여야 승인 화면에서 본 파일 = 이미지에 든 파일 |
| 빌드는 지원자 런과 다른 그래프 | §4 시점 — 명세 승인 뒤 공고·판마다 한 번 |
| 이미지 빌드·push 는 API 가 아니라 verifier 쪽 | 이미지 빌드도 컨테이너 실행 권한이 필요 — API 프로세스에 주지 않는다. 원본은 DB 오버레이, 이미지는 그 파생물(다이제스트만 `common_task_build` 에) |
| AI 단독 풀이는 eval 전용 | Claude Code 세션이 필요하고 오래 걸림 — 템플릿·프롬프트 `CURRENT` 승격 기준으로만 |

구현 순서: ① `starter/` 코어 + Java 템플릿 v1(배송 감사 예시) → ② 저장소·마이그레이션(#52) → ③ `verifier` 최소판(Java 판정 표·게이트) → ④ 빌드 그래프·생성 노드·프롬프트·정적 검사(#50) → ⑤ 과제 이미지 빌드·레지스트리 발행·채점 계약 → ⑥ 시작 코드 승인 화면 → ⑦ `eval/solo/` 이전.
