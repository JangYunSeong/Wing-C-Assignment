# 채용담당자 인터뷰 과제 — P1 연결 규칙

> 상태: 2026-11-19. 결정 표기는 `[확정]` / `[제안]` / `[미정]`.
> 인터뷰 코드: `Modac-Lab-WingC/Wing-C-Interview` (이 레포 162a142 복사본 + 인터뷰 층, 아직 들여오지 않음).

인터뷰는 채용담당자와 채팅해 공고의 공통 과제를 정한다. 흐름은 실제 장애 사례 → 실패한 첫 시도 → 성공 기준 → 기능형 공통 과제 → 승인이다.
P1은 그 공고의 지원자마다 이력서 기반 경험 검증(슬롯 배정·면접 질문)을 얹는다.
두 쪽은 공통 과제 저장소(`public.common_task`)에서 만난다. 인터뷰 과제의 저장 키는 `prompt_ref` = `interview:{인터뷰 id}`다.

## 1. 지원자 실행은 인터뷰 과제를 그대로 쓴다 [확정: 2026-11-19 사용자]

### P1 쪽 (구현됨)

| 규칙 | 이유 | 코드 |
|---|---|---|
| 공고(같은 온톨로지 판)에 승인된 인터뷰 과제가 있으면 지원자 실행은 과제를 만들지 않고 그 과제를 쓴다. 유형도 그 과제의 것이다. | 채용담당자가 고른 실제 사례 과제 위에 P1 경험 검증을 얹는 것이 두 쪽을 붙이는 이유다. | `nodes/spec.py _interview_common` |
| 공고(같은 판)마다 승인된 인터뷰 과제는 하나다. 바꾸려면 지금 과제 id를 `replaces`로 짚는다. 같은 인터뷰의 고친 판도 마찬가지다. | 모집 중에 과제가 말없이 바뀌면 같은 공고 지원자끼리 비교할 수 없다 (불변식 3). | `spec/store.py approve_interview_task`, 색인 `common_task_one_interview` |
| 지원자 명세 승인은 인터뷰 과제를 다시 승인하지 않는다. 명세의 과제가 그 공고의 지금 과제인지만 확인하고, 아니면 409를 낸다. | `store.approve()`는 승인자·시각을 덮어쓰고, 교체된 과제를 다시 approved로 되살린다. | `make_finalize`, `replaced_common`, API `common_task_replaced` |
| 지원자 명세의 수정 요청으로 인터뷰 과제를 고치지 않는다. common·all 대상과 유형 바꾸기를 막고, 경험 검증만 다시 만들 수 있다. | 과제를 고칠 사람은 채용담당자다. 고치게 두면 P1 생성기가 공개 사례로 다시 만든다. | API `interview_task_locked`, 노드 기록 `interview_common_locked` |
| 인터뷰 과제가 다른 온톨로지 판에만 있으면 그 공고 실행을 멈춘다. 공개 사례 과제로 바꿔 만들지 않는다. | 과제 안의 역량·NCS·수행준거 id는 승인한 판의 것이다 (불변식 4). | ① `interview_task_version_mismatch`, `POST /runs` 409 |

교체된 뒤 승인 대기 중인 명세는 "경험 검증 다시 만들기"(`revise_target=verification`)로 지금 과제를 반영해 다시 만든다.

- **교체된 과제는 다시 승인하지 않는다.** 되돌리려면 그 내용을 새 판으로 저장해 승인한다. 승인 기록이 하나의 흐름으로 남게 하기 위해서다.
- **확인과 확정 사이.** 확정(finalize)이 "지금 과제"를 확인한 직후 교체되면, 그 명세는 이전 과제로 확정된다.
  이것은 교체 직전에 확정된 명세와 같으며, 교체 화면의 "이전 과제로 진행한 지원자 수"에 든다. 행 잠금으로 막지 않는다. 명세는 체크포인트에, 과제는 다른 표에 있어 한 트랜잭션으로 묶을 수 없다.
- **승인 충돌.** 동시에 둘이 승인하거나 교체하면 `InterviewTaskConflict`가 진 쪽에 지금 과제 id를 알려 준다. 이때 저장소는 아무것도 바꾸지 않는다(savepoint).

### 인터뷰 쪽 — 통합할 때 할 일

- **승인.** `approve_common` 대신 `approve_interview_task(conn, common_id, reviewer, at, replaces=)`를 부른다. 인터뷰 판본 확정과 같은 트랜잭션 안에서 부르고, `InterviewTaskConflict`는 지금 과제 id를 담아 409로 돌려준다.
- **교체 화면.** 지금 승인된 인터뷰 과제와, 그 과제로 진행한 지원자 수를 보여 준다. 사람이 교체를 고르면 `replaces`를 보낸다.
  지원자 수를 세는 방법은 정하지 않았다 [미정]. 실행 목록(체크포인트)에서 세거나, 확정 때 사용 기록 표를 둔다. 사용 기록 표는 실행 id와 연결되므로 privacy-auditor W3와 함께 검토한다.
- **P1 과제가 이미 승인된 공고** (`from-posting`). 같은 화면에서 그 사실과 지원자 수를 보여 준다.
  저장소는 막지 않는다. P1 과제는 프롬프트 판마다 키가 달라서 '지금 과제'가 하나로 정해지지 않는다.
- **`from-posting`.** 그 공고에 진행 중이거나 승인된 인터뷰가 있으면 알린다. 이어서 할지, 새로 해서 교체할지 고르게 한다.
- **온톨로지 판이 바뀌면 다시 승인한다.** 사례, 실패한 첫 시도, 성공 기준, 기준 답안과 그 검증은 판과 무관하므로 그대로 둔다.
  새 판에서 다시 하는 것은 공고 재분석 → 역량 선택(옛 id가 새 판에 있으면 미리 채움) → 과제 생성 → 승인이다.
  - 임시 공고(`prov-…`)를 새 판으로 다시 분석하는 길은 P1에도 없다 [미정].
  - 판 올림이 잦아지면 줄이는 방법을 둔다 [제안]. 과제가 인용한 id가 새 판에 모두 그대로 있으면 과제를 복사하고 확인만 한 번 받는다.

## 2. 인터뷰 승인은 interrupt 그래프로, 반려 포함 [확정: 2026-11-19 사용자]

지금 포크의 인터뷰 과제 승인은 그래프가 아니다. `POST /interviews/{id}/approve`가 판본을 확인한 뒤 DB 트랜잭션 하나로 끝낸다.
반면 인터뷰 뒤의 코딩 과제 빌드 승인은 이미 P1 `build_approval` 그래프를 탄다.
결정 1로 이 승인이 그 공고 지원자 전원의 과제를 정하게 됐으므로, 지원자 명세 승인과 같은 수준으로 불변식 9를 따른다.
구현은 인터뷰 층을 들여오는 통합 PR에서 한다.

빌드 승인 그래프(`graph/build_approval.py`)를 본뜬다.

```
interview_approval (interrupt) ─ approved → finalize_interview → END
                               └ rejected → reject_interview  → END
finalize_interview ─ 교체 충돌·판본 바뀜 → interview_approval (사유를 붙여 다시 기다림)
```

- **thread는 인터뷰 판본마다 하나다** (`interview-{id}-r{판본}`). 판본이 바뀌면 thread가 달라져, 옛 화면에서 누른 결정이 새 판본에 적용되지 않는다.
  resume하면 노드가 지금 판본과 단계를 다시 보고, 다르면 stale로 끝낸다.
- **interrupt 앞에서는 읽기만 한다.** 지금 approve 엔드포인트의 검사(기능형·템플릿·재료, 확인한 사례·답안과의 일치, 짚은 질문의 답, 질문·숨은 요구·평가 기준)를 이 노드로 옮긴다.
  대기 내용에는 교체 대상(지금 승인된 인터뷰 과제)과 그 과제로 진행한 지원자 수를 싣는다.
  인터뷰 본문은 싣지 않는다. 체크포인트에 사본을 두지 않기 위해서다.
- **결정 값:** `status`(approved·rejected), `reviewer`, `at`, `comment`(반려면 필수), `replaces`(화면이 보여 준 지금 과제 id).
- **`finalize_interview`:** 단계를 approved로 바꾸고, `approve_interview_task(conn, …, replaces=)`와 `evaluation_spec` 기록을 한 트랜잭션에서 한다.
  `InterviewTaskConflict`가 나면 사유를 실어 다시 기다린다.
- **`reject_interview`:** 사유를 인터뷰의 `review_note`에 남기고 단계는 `task_review` 그대로 둔다. `review_note`는 포크의 수정 요청 흐름이 다음 과제 생성에 넣는 칸이다.
  담당자는 기존 수정 흐름으로 고쳐 새 판본을 만들고 다시 승인을 받는다(새 thread). 누가·언제·왜 반려했는지는 체크포인트에 남는다.
- **API는 resume만 한다.** `GET /interviews/{id}/approval`은 thread를 시작하고 대기 내용을 보여 주고, `POST /interviews/{id}/approve`는 resume만 한다.
- **State와 결정 모델은 `schemas/`에 둔다.** 체크포인터 허용 목록에 들어가고, 이후 경로를 옮기지 않는다.
- **테스트(InMemorySaver):** 승인, 교체를 명시하지 않았을 때 다시 대기, 판본이 바뀌었을 때 stale, 반려(사유 없으면 다시 대기), API가 resume만 하는지를 확인한다.

## 회사 결정적 사건 저장소 — 같은 회사 안에서 공유 [확정: 2026-11-19 사용자]

인터뷰로 모은 실제 장애 사례(결정적 사건)를 그 인터뷰 하나에만 쓰지 않는다. DB에 저장해 같은 회사의 다른 공고, 특히 새로 올리는 직군의 과제 생성에 다시 쓴다.
쓸 수 있는 사례가 많을수록 과제 생성에 유리하다. 공개 사례(`incidents/public_v1`)는 지금처럼 git 파일로만 두고 DB에 넣지 않는다.

정한 것
1. **공유 범위:** 같은 회사 공고에만 쓴다. 회사는 공고의 회사 id(`postings/company.py`)로 가른다. 다른 회사의 과제나 LLM 입력에는 쓰지 않는다.
   - **공고의 회사는 사람이 입력한 값을 쓴다 [확정: 2026-11-19 사용자 — 인증 전 "일단 회사 입력할 수 있게"].** 사람이 정한 값(`posting_company`)이 공고 데이터(온톨로지 공고의 회사·임시 공고의 회사 칸)보다 먼저다.
   - 입력하는 곳은 세 군데다: 임시 공고 등록의 회사 칸(`POST /postings/suggest`), `PUT /postings/{id}/company`(온톨로지 공고도), 실행 만들기 `POST /runs`의 `company`(공고에 회사가 없을 때 정하고, 다른 회사면 409).
   - 회사는 필수가 아니다. 회사가 없는 공고는 공개 사례만 쓴다.
2. **공유 승인을 따로 받는다:** 등록(pending)만으로는 쓰지 않는다. 사람이 공유를 승인한(shared) 사례만 쓴다. 공유 승인은 interrupt 그래프로 받는다(불변식 9).
   - 등록할 때 가명화와 같은 로컬 탐지기로 검사한다. LLM 입력으로 가는 칸(원리·증상·원인·처방·단서·표면·인정 조치·가설, 기능형 재료)에 연락처·링크가 있으면 등록하지 않는다.
   - LLM에 보내지 않는 칸(원문 오류 문구·피할 이름 등)의 링크는 막지 않는다. 로그 속 사내 주소처럼 정상적으로 들어갈 수 있어서다.
   - 사람 이름·회사·제품 등으로 보이는 표현은 공유 승인 화면에 칸별 개수로만 보인다.
3. **재사용할 때 정답이 새지 않게 한다.**
   - 공고가 쓰던 사례를 계속 쓴다(같은 공고 지원자 비교 가능성, 불변식 3). 그 공고의 공통 과제가 쓴 사례를 승인된 것부터(최근 승인 순), 그다음 초안만 있는 것 순으로 앞에서부터 본다.
     - 아직 쓸 수 있는 회사 사례를 만나면 그 사례를 그대로 쓴다. 보관 뒤 고른 대체 사례도 이렇게 고정된다.
     - 공개 사례나 사례 없는 과제를 만나면 회사 사례로 바꾸지 않는다. 회사 사례는 공통 과제가 아직 없는 공고부터 쓴다.
     - 더 쓸 수 없는 회사 사례(보관·반려)는 건너뛰고 "다른 사례로 바뀜"을 표시한다. 회사의 공유 사례가 하나도 남지 않았으면 공개 사례로 바뀌고 같은 표시를 한다.
     - 경험 검증만 다시 만들 때(공통 과제 유지)는 고르지 않고, 그 과제 사례의 재사용 표시만 다시 센다.
   - 새로 고를 때는 다른 공고가 덜 쓴 사례를 먼저 고른다. 이미 다른 공고가 쓰는 사례면 명세에 표시한다(두 공고에 모두 지원한 사람은 함정·정답을 안다).
   - 밖으로 샌 사례는 보관(retired)한다. 그러면 새로 고르지 않고, 그 사례를 쓰던 공고는 다음 과제부터 다른 사례로 바뀐다(표시).

P1 쪽 (구현됨)
- **저장소:** `spec/company_incidents.py`, 표 `company_incident`.
  - id는 `co:<직군>:<12자>`, 내용은 공개 사례와 같은 형식이다.
  - 등록한 뒤 내용은 바꾸지 않는다. 고치려면 새로 등록하고 이전 것은 보관한다.
- **API `/incidents`:** 등록, 목록(회사·상태), 상세(그 사례를 쓴 공고 수), 공유 승인 thread 시작·resume, 보관.
  - 지금은 손으로 등록한다(`source=manual`).
  - TODO(auth): 회사별 열람 제한은 인증이 생긴 뒤에 한다.
- **공유 승인 그래프:** `graph/incident_share.py`. thread는 (사례, 내용 지문)마다 하나이고, 대기 내용에 사례 본문을 싣지 않는다.
- **과제 생성:** `draft_spec`이 위 규칙으로 고른 회사 사례를 그 직군 사례로 고정해 넘긴다. 과제 표시는 `FLAG_COMPANY_INCIDENT`다.
- **빌더:** 명세의 `source_incident`로 공개 사례는 파일, 회사 사례는 DB에서 찾는다.
  - 찾지 못하면 다른 재료로 바꾸지 않고 실패한다. 예전에는 말없이 그 직군의 다른 공개 사례로 빌드했다.
  - 빌더 DB 역할에 읽기 권한을 준다(`docker/builder/db-role.sql`, 배포 때 다시 실행).

인터뷰 쪽 — 통합할 때 할 일
- `finalize_interview`(결정 2)가 확인한 사례를 회사 사례로 등록한다(pending). 출처는 `{"kind": "interview", "interview_id", "revision"}`이고, 기능형 재료(`feature`)도 함께 넣는다.
  공유 승인은 따로 받는다.
- 지금 포크처럼 사례를 `pub:<직군>:interview-<id>`로 만들지 않는다. 공개 사례 id 공간을 쓰면 빌더가 찾지 못한다.

아직 정하지 않은 것 [미정]
- **"동시에 모집 중인 공고끼리는 같은 사례를 피한다":** 공고의 모집 상태 정보가 P1에 없어서, 지금은 "덜 쓴 사례 먼저 + 표시"로 대신한다.
- **공개 사례로 시작한 공고를 회사 사례로 바꾸는 명시적 동작:** 지금은 바꾸지 않는다.
- **인증 뒤 회사 판별:** 지금은 입력한 회사를 그대로 믿으므로, 다른 회사 이름을 입력하면 그 회사의 공유 사례가 과제와 LLM 입력에 쓰인다. 인증 없는 `GET /incidents`도 같다.
  인증을 붙일 때 입력자·사례 열람자를 회사와 묶는다.
- **결정 4(가명화 범위):** 공유 사례는 여러 공고와 LLM 호출로 퍼지므로, 공유를 실제로 켜기 전에 정한다.

## 3–4. 남은 결정 [미정]

3. **`/evaluation`을 부르는 곳이 `/pull`의 평가 대상(`delivery_target`)과 같은 시스템인지.**
   - 같다면 `PULL_TOKENS`와 역할별 엔드포인트로 합친다.
   - 포크 작성자와 평가팀에 확인해야 한다.

   - [제안] 먼저 P1 가명화기의 사람 이름·링크 탐지를 `sanitize_interview_text`에 붙인다.
   - 전체 가명화기 적용은 가상 서술로 측정한 뒤 정한다.
