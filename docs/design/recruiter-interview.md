# 채용담당자 인터뷰 과제 — P1 연결 규칙

> 상태: 2026-11-19. 결정 표기는 `[확정]` / `[제안]` / `[미정]`.
> 인터뷰 코드: `Modac-Lab-WingC/Wing-C-Interview` (이 레포 162a142 복사본 + 인터뷰 층). 대화 흐름을 이 레포로 옮기는 중 — 아래 「포크 대화 흐름 이식」(#262).

인터뷰는 채용담당자와 채팅해 공고의 공통 과제를 정한다. 흐름은 실제 장애 사례 → 실패한 첫 시도 → 성공 기준 → 기능형 공통 과제 → 승인이다.
P1은 그 공고의 지원자마다 이력서 기반 경험 검증(슬롯 배정·면접 질문)을 얹는다.
두 쪽은 공통 과제 저장소(`public.common_task`)에서 만난다. 인터뷰 과제의 저장 키는 `prompt_ref` = `interview:{인터뷰 id}`다.

## 1. 지원자 실행은 인터뷰 과제를 그대로 쓴다 [확정: 2026-11-19 사용자]

### P1 쪽 (구현됨)

| 규칙 | 이유 | 코드 |
|---|---|---|
| 공고(같은 온톨로지 판)에 승인된 인터뷰 과제가 있으면 지원자 실행은 과제를 만들지 않고 그 과제를 쓴다. 유형도 그 과제의 것이다. | 채용담당자가 고른 실제 사례 과제 위에 P1 경험 검증을 얹는 것이 두 쪽을 붙이는 이유다. | `nodes/spec.py _interview_common` |
| 공고(같은 판)마다 승인된 인터뷰 과제는 하나다. 바꾸려면 지금 과제 id를 `replaces`로 짚는다. 같은 인터뷰의 고친 판도 마찬가지다. | 모집 중에 과제가 말없이 바뀌면 같은 공고 지원자끼리 비교할 수 없다 (불변식 3). | `spec/store.py approve_interview_task`, 색인 `common_task_one_interview` |
| 지원자 명세 승인은 인터뷰 과제를 다시 승인하지 않는다. 명세의 과제가 그 공고의 지금 과제인지만 확인하고, 아니면 409를 낸다. | `store.approve()`는 승인자·시각을 덮어쓰고, 교체된 과제를 다시 approved로 되살린다. | `make_finalize`, `replaced_common`, API `common_task_replaced` |
| 지원자 명세의 수정 요청으로 인터뷰 과제를 고치지 않는다. common·all 대상과 유형 바꾸기를 막고, 경험 검증만 다시 만들 수 있다. | 과제를 고칠 사람은 채용담당자다. 고치게 두면 P1 생성기가 공개 사례로 다시 만든다. | API `interview_task_locked`, 노드 기록 `interview_common_locked` |
| 인터뷰 과제가 다른 온톨로지 판에만 있으면 그 공고 실행을 멈춘다. 공개 사례 과제로 바꿔 만들지 않는다. | 과제 안의 역량·NCS·수행준거 id는 승인한 판의 것이다 (불변식 4). | ① `interview_task_version_mismatch`, `POST /runs` 409 |

교체된 뒤 승인 대기 중인 명세는 "경험 검증 다시 만들기"(`revise_target=verification`)로 지금 과제를 반영해 다시 만든다.

- **교체된 과제는 다시 승인하지 않는다.** 되돌리려면 그 내용을 새 판으로 저장해 승인한다. 승인 기록이 하나의 흐름으로 남게 하기 위해서다.
- **확인과 확정 사이.** 확정(finalize)이 "지금 과제"를 확인한 직후 교체되면, 그 명세는 이전 과제로 확정된다.
  이것은 교체 직전에 확정된 명세와 같으며, 교체 화면의 "이전 과제로 진행한 지원자 수"에 든다. 행 잠금으로 막지 않는다. 명세는 체크포인트에, 과제는 다른 표에 있어 한 트랜잭션으로 묶을 수 없다.
- **승인 충돌.** 동시에 둘이 승인하거나 교체하면 `InterviewTaskConflict`가 진 쪽에 지금 과제 id를 알려 준다. 이때 저장소는 아무것도 바꾸지 않는다(savepoint).

### 인터뷰 쪽 — 통합할 때 할 일

- **승인.** `approve_common` 대신 `approve_interview_task(conn, common_id, reviewer, at, replaces=)`를 부른다. 인터뷰 판본 확정과 같은 트랜잭션 안에서 부르고, `InterviewTaskConflict`는 지금 과제 id를 담아 409로 돌려준다.
- **교체 화면.** 지금 승인된 인터뷰 과제와, 그 과제로 진행한 지원자 수를 보여 준다. 사람이 교체를 고르면 `replaces`를 보낸다.
  지원자 수를 세는 방법은 정하지 않았다 [미정]. 실행 목록(체크포인트)에서 세거나, 확정 때 사용 기록 표를 둔다. 사용 기록 표는 실행 id와 연결되므로 privacy-auditor W3와 함께 검토한다.
- **P1 과제가 이미 승인된 공고** (`from-posting`). 같은 화면에서 그 사실과 지원자 수를 보여 준다.
  저장소는 막지 않는다. P1 과제는 프롬프트 판마다 키가 달라서 '지금 과제'가 하나로 정해지지 않는다.
- **`from-posting`.** 그 공고에 진행 중이거나 승인된 인터뷰가 있으면 알린다. 이어서 할지, 새로 해서 교체할지 고르게 한다.
- **온톨로지 판이 바뀌면 다시 승인한다.** 사례, 실패한 첫 시도, 성공 기준, 기준 답안과 그 검증은 판과 무관하므로 그대로 둔다.
  새 판에서 다시 하는 것은 공고 재분석 → 역량 선택(옛 id가 새 판에 있으면 미리 채움) → 과제 생성 → 승인이다.
  - 임시 공고(`prov-…`)를 새 판으로 다시 분석하는 길은 P1에도 없다 [미정].
  - 판 올림이 잦아지면 줄이는 방법을 둔다 [제안]. 과제가 인용한 id가 새 판에 모두 그대로 있으면 과제를 복사하고 확인만 한 번 받는다.

## 2. 인터뷰 승인은 interrupt 그래프로, 반려 포함 [확정: 2026-11-19 사용자]

지금 포크의 인터뷰 과제 승인은 그래프가 아니다. `POST /interviews/{id}/approve`가 판본을 확인한 뒤 DB 트랜잭션 하나로 끝낸다.
반면 인터뷰 뒤의 코딩 과제 빌드 승인은 이미 P1 `build_approval` 그래프를 탄다.
결정 1로 이 승인이 그 공고 지원자 전원의 과제를 정하게 됐으므로, 지원자 명세 승인과 같은 수준으로 불변식 9를 따른다.
구현은 인터뷰 층을 들여오는 통합 PR에서 한다.

빌드 승인 그래프(`graph/build_approval.py`)를 본뜬다.

```
interview_approval (interrupt) ─ approved → finalize_interview → END
                               └ rejected → reject_interview  → END
finalize_interview ─ 교체 충돌·판본 바뀜 → interview_approval (사유를 붙여 다시 기다림)
```

- **thread는 인터뷰 판본마다 하나다** (`interview-{id}-r{판본}`). 판본이 바뀌면 thread가 달라져, 옛 화면에서 누른 결정이 새 판본에 적용되지 않는다.
  resume하면 노드가 지금 판본과 단계를 다시 보고, 다르면 stale로 끝낸다.
- **interrupt 앞에서는 읽기만 한다.** 지금 approve 엔드포인트의 검사(기능형·템플릿·재료, 확인한 사례·답안과의 일치, 짚은 질문의 답, 질문·숨은 요구·평가 기준)를 이 노드로 옮긴다.
  대기 내용에는 교체 대상(지금 승인된 인터뷰 과제)과 그 과제로 진행한 지원자 수를 싣는다.
  인터뷰 본문은 싣지 않는다. 체크포인트에 사본을 두지 않기 위해서다.
- **결정 값:** `status`(approved·rejected), `reviewer`, `at`, `comment`(반려면 필수), `replaces`(화면이 보여 준 지금 과제 id).
- **`finalize_interview`:** 단계를 approved로 바꾸고, `approve_interview_task(conn, …, replaces=)`와 `evaluation_spec` 기록을 한 트랜잭션에서 한다.
  `InterviewTaskConflict`가 나면 사유를 실어 다시 기다린다.
- **`reject_interview`:** 사유를 인터뷰의 `review_note`에 남기고 단계는 `task_review` 그대로 둔다. `review_note`는 포크의 수정 요청 흐름이 다음 과제 생성에 넣는 칸이다.
  담당자는 기존 수정 흐름으로 고쳐 새 판본을 만들고 다시 승인을 받는다(새 thread). 누가·언제·왜 반려했는지는 체크포인트에 남는다.
- **API는 resume만 한다.** `GET /interviews/{id}/approval`은 thread를 시작하고 대기 내용을 보여 주고, `POST /interviews/{id}/approve`는 resume만 한다 (D2b 구현).
- **State와 결정 모델은 `schemas/`에 둔다.** 체크포인터 허용 목록에 들어가고, 이후 경로를 옮기지 않는다.
- **테스트(InMemorySaver):** 승인, 교체를 명시하지 않았을 때 다시 대기, 판본이 바뀌었을 때 stale, 반려(사유 없으면 다시 대기), API가 resume만 하는지를 확인한다.

## 회사 결정적 사건 저장소 — 같은 회사 안에서 공유 [확정: 2026-11-19 사용자]

인터뷰로 모은 실제 장애 사례(결정적 사건)를 그 인터뷰 하나에만 쓰지 않는다. DB에 저장해 같은 회사의 다른 공고, 특히 새로 올리는 직군의 과제 생성에 다시 쓴다.
쓸 수 있는 사례가 많을수록 과제 생성에 유리하다. 공개 사례(`incidents/public_v1`)는 지금처럼 git 파일로만 두고 DB에 넣지 않는다.

정한 것
1. **공유 범위:** 같은 회사 공고에만 쓴다. 회사는 공고의 회사 id(`postings/company.py`)로 가른다. 다른 회사의 과제나 LLM 입력에는 쓰지 않는다.
   - **공고의 회사는 사람이 입력한 값을 쓴다 [확정: 2026-11-19 사용자 — 인증 전 "일단 회사 입력할 수 있게"].** 사람이 정한 값(`posting_company`)이 공고 데이터(온톨로지 공고의 회사·임시 공고의 회사 칸)보다 먼저다.
   - 입력하는 곳은 세 군데다: 임시 공고 등록의 회사 칸(`POST /postings/suggest`), `PUT /postings/{id}/company`(온톨로지 공고도), 실행 만들기 `POST /runs`의 `company`(공고에 회사가 없을 때 정하고, 다른 회사면 409).
   - 회사는 필수가 아니다. 회사가 없는 공고는 공개 사례만 쓴다.
2. **공유 승인을 따로 받는다:** 등록(pending)만으로는 쓰지 않는다. 사람이 공유를 승인한(shared) 사례만 쓴다. 공유 승인은 interrupt 그래프로 받는다(불변식 9).
   - 등록할 때 가명화와 같은 로컬 탐지기로 검사한다. LLM 입력으로 가는 칸(원리·증상·원인·처방·단서·표면·인정 조치·가설, 기능형 재료)에 연락처·링크가 있으면 등록하지 않는다.
   - LLM에 보내지 않는 칸(원문 오류 문구·피할 이름 등)의 링크는 막지 않는다. 로그 속 사내 주소처럼 정상적으로 들어갈 수 있어서다.
   - 사람 이름·회사·제품 등으로 보이는 표현은 공유 승인 화면에 칸별 개수로만 보인다.
3. **재사용할 때 정답이 새지 않게 한다.**
   - 공고가 쓰던 사례를 계속 쓴다(같은 공고 지원자 비교 가능성, 불변식 3). 그 공고의 공통 과제가 쓴 사례를 승인된 것부터(최근 승인 순), 그다음 초안만 있는 것 순으로 앞에서부터 본다.
     - 아직 쓸 수 있는 회사 사례를 만나면 그 사례를 그대로 쓴다. 보관 뒤 고른 대체 사례도 이렇게 고정된다.
     - 공개 사례나 사례 없는 과제를 만나면 회사 사례로 바꾸지 않는다. 회사 사례는 공통 과제가 아직 없는 공고부터 쓴다.
     - 더 쓸 수 없는 회사 사례(보관·반려)는 건너뛰고 "다른 사례로 바뀜"을 표시한다. 회사의 공유 사례가 하나도 남지 않았으면 공개 사례로 바뀌고 같은 표시를 한다.
     - 경험 검증만 다시 만들 때(공통 과제 유지)는 고르지 않고, 그 과제 사례의 재사용 표시만 다시 센다.
   - 새로 고를 때는 다른 공고가 덜 쓴 사례를 먼저 고른다. 이미 다른 공고가 쓰는 사례면 명세에 표시한다(두 공고에 모두 지원한 사람은 함정·정답을 안다).
   - 밖으로 샌 사례는 보관(retired)한다. 그러면 새로 고르지 않고, 그 사례를 쓰던 공고는 다음 과제부터 다른 사례로 바뀐다(표시).

P1 쪽 (구현됨)
- **저장소:** `spec/company_incidents.py`, 표 `company_incident`.
  - id는 `co:<직군>:<12자>`, 내용은 공개 사례와 같은 형식이다.
  - 등록한 뒤 내용은 바꾸지 않는다. 고치려면 새로 등록하고 이전 것은 보관한다.
- **API `/incidents`:** 등록, 목록(회사·상태), 상세(그 사례를 쓴 공고 수), 공유 승인 thread 시작·resume, 보관.
  - 지금은 손으로 등록한다(`source=manual`).
  - TODO(auth): 회사별 열람 제한은 인증이 생긴 뒤에 한다.
- **공유 승인 그래프:** `graph/incident_share.py`. thread는 (사례, 내용 지문)마다 하나이고, 대기 내용에 사례 본문을 싣지 않는다.
- **과제 생성:** `draft_spec`이 위 규칙으로 고른 회사 사례를 그 직군 사례로 고정해 넘긴다. 과제 표시는 `FLAG_COMPANY_INCIDENT`다.
- **빌더:** 명세의 `source_incident`로 공개 사례는 파일, 회사 사례는 DB에서 찾는다.
  - 찾지 못하면 다른 재료로 바꾸지 않고 실패한다. 예전에는 말없이 그 직군의 다른 공개 사례로 빌드했다.
  - 빌더 DB 역할에 읽기 권한을 준다(`docker/builder/db-role.sql`, 배포 때 다시 실행).

인터뷰 쪽 — 통합할 때 할 일
- `finalize_interview`(결정 2)가 확인한 사례를 회사 사례로 등록한다(pending). 출처는 `{"kind": "interview", "interview_id", "revision"}`이고, 기능형 재료(`feature`)도 함께 넣는다.
  공유 승인은 따로 받는다.
- 지금 포크처럼 사례를 `pub:<직군>:interview-<id>`로 만들지 않는다. 공개 사례 id 공간을 쓰면 빌더가 찾지 못한다.

아직 정하지 않은 것 [미정]
- **"동시에 모집 중인 공고끼리는 같은 사례를 피한다":** 공고의 모집 상태 정보가 P1에 없어서, 지금은 "덜 쓴 사례 먼저 + 표시"로 대신한다.
- **공개 사례로 시작한 공고를 회사 사례로 바꾸는 명시적 동작:** 지금은 바꾸지 않는다.
- **인증 뒤 회사 판별:** 지금은 입력한 회사를 그대로 믿으므로, 다른 회사 이름을 입력하면 그 회사의 공유 사례가 과제와 LLM 입력에 쓰인다. 인증 없는 `GET /incidents`도 같다.
  인증을 붙일 때 입력자·사례 열람자를 회사와 묶는다.
- **결정 4(가명화 범위):** [확정: 2026-11-19 사용자] — 아래 「포크 대화 흐름 이식」의 결정 4. 담당자 글은 탐지기로 가명화한 뒤에만 LLM 으로 간다.

## 포크 대화 흐름 이식 (#262) [확정: 2026-11-19 사용자 "포크도 옮겨서 구현", "1,2,3 진행해줘"]

포크의 핵심은 채용담당자가 **에이전트와 대화로** 과제 재료(실제 사례·처음 시도한 대응·성공 기준·기준 답안)를 명세하는 것이다.
이 레포는 회사 사례를 17칸 양식(`POST /incidents`)으로만 받았다 — 양식은 직접 입력용으로 남기고, 대화를 이 레포로 옮긴다.
포크 대화는 사례를 **만드는** 앞단, 회사 사례 저장소(위 절)는 **보관·공유·고르는** 뒷단이다.

### 나눔

| 단계 | 범위 | 상태 |
|---|---|---|
| D1 | 기존 공고에서 시작 → 팀 맥락(고정 질문) → 사례 대화(LLM 후속 질문) → 처음 시도한 대응 → 성공 기준·기준 답안·답안 검증 → 사례·답안 확인. 결과는 인터뷰 안에만 | 구현 (#262) |
| D1b | 프롬프트 3개를 가상 대화 표본(dev 5·test 5)으로 실제 qwen 평가 → CURRENT (`eval/interview/`) | 구현 (#263) — test 유도 1건은 사용자 결정으로 판정 제외, test-03 미완(처음 대응 단계 503 3번) 원인은 후속 |
| D2a | 역량 2~3개 → 기능형 공통 과제 생성(`interview:{id}` 초안) → 지원자 질문에 답할 범위 → 과제·질문 수정 | 구현 (#266) — 새 프롬프트 2개는 판 파일만 |
| D2b | 승인 interrupt 그래프(반려, 위 §2) → 그 순간의 사례를 `co:` 로 등록(공유 대기) → 공통 과제 승인(위 §1) → 대응표 삭제. 빌드는 따로 요청 | 구현 (#266) |
| D2c | 회사 사례 모음(공유 승인된 같은 회사 사례)·공개 사례에서 고르기 | 구현 (#266) |
| D2 평가 | `interview_feature_seed`·`interview_targeted_answer` 가상 표본 평가 → CURRENT (`eval/interview_task/`) | 구현 (#266) — feature_seed v1, targeted_answer v2 (v1 은 dev 해법 누설로 미달) |
| D3 | 채용 방향 문답 → 공고 초안, 성공 기준 ↔ 실제 채점 결과 연결, `/evaluation`(결정 3), 내장 화면 여부 | 뒤 |

가져오지 않는 것: 공용 프롬프트·템플릿 판 변경(gen_hidden v10·gen_starter v11·plan_contract v32·java 템플릿 v4 — 대화와 무관, 따로 평가),
`docs/demo`·`interview-concepts`, 코드에서 부르지 않는 `interview_incident`, 프롬프트 옛 판(v1~v3 — 옛 입출력 스키마 이름을 쓴다),
옛 작업본 복구(`recover_trap_step` — 이 DB 에는 포크 작업본이 없다).

### 설계

- **대화는 API + 형 있는 상태, 승인만 그래프.** 포크 흐름은 아무 단계로 돌아가 고치고 앞 단계를 고치면 뒤 검증을 다시 하는
  마법사라서 한 줄로 흐르는 그래프에 넣으면 더 복잡해진다. 불변식 9 가 interrupt 를 요구하는 것은 승인뿐이다 (D2).
  상태는 `schemas/interview_state.py`(포크 API 응답과 같은 칸 이름), 업무는 `interview/service.py`, 표는 `public.recruiter_interview`.
- **판본 + 인터뷰별 잠금.** 같은 인터뷰의 요청을 한 줄로 세운다(이름 대응표 덮어쓰기 방지, uvicorn 워커 1개 전제). 대응표는 DB 가 그 판본을 받은 뒤에만 저장한다.
- **사례 id 는 `co:<직군>:<12자>`.** 포크의 `pub:<직군>:interview-…` 은 공개 사례와 섞이고, 빌더가 공개 사례 파일에서 찾다가 못 찾아
  금지어 검사가 빠졌다. 첫 초안 때 정해 인터뷰 동안 고정하고, D2 에서 그 id 로 등록한다.
- **기준 답안은 `PublicIncident.known_incident_cases`.** 비면 직렬화에서 뺀다(`exclude_if`) — 기존 사례 지문(`prompt_ref`)·공통 과제 키·
  회사 사례 `content_sha256` 이 바뀌지 않는다 (프롬프트 173판 출력 스키마 글·공개 사례 24건 해시를 바꾸기 전·후 대조).
- **프롬프트는 판 파일을 바이트 그대로, CURRENT 는 평가 뒤.** `interview_incident_extended` v4 · `interview_answer` v4 · `interview_answer_check` v2.
  새 작업은 평가 전에 CURRENT 를 두지 않는다(prompt-registry, 2026-11-16 사용자) — CURRENT 가 없으면 인터뷰 API 는 '준비 중'(503).
  포크 평가 기록은 포크 서버에만 있고 입력이 탐지기 가명화로 바뀌었으므로 가상 대화 표본으로 다시 평가했다(D1b, #263 — 기록은 각 `PROMOTIONS.md`).
  프롬프트 본문에 포크 표본에 맞춘 규칙(감사 이력 취소·풀 크기)이 있어 과적합을 함께 본다.
  출력 스키마는 프롬프트 본문에 렌더되므로 클래스·필드·설명을 포크와 같게 둔다. 입력 칸만 `PseudoTextField`.

- **D2a 과제 생성 (#266).** 코딩 템플릿은 직군 기본(`TEMPLATE_FOR_SUB`) 하나 — 포크처럼 세 템플릿 중 고르게 하면 TaskItem 에
  template_id·feature_seed 를 더하고 빌더를 고쳐야 한다. 대신 기능형 재료(새 프롬프트 `interview_feature_seed`)를 사례의 `feature` 칸에 붙인
  `InterviewSpec.coding_incident` 를 두고, D2b 승인 때 이 사례를 `co:` 로 등록하면 빌더가 지금 방식(source_incident → DB)으로 재료를 찾는다.
  기준 답안 블록(`known_cases_block`)은 인터뷰 공고 자신의 기능형 생성 입력(`seed_block`)에만 넣고 이슈형 `incident_block` 에는 넣지 않는다 —
  회사 사례 모음으로 다른 공고가 써도 채점 근거가 생성 프롬프트로 가지 않게(`DraftContext.with_known_answers` 는 인터뷰 생성기만 켠다).
  무거운 생성기(build_common → draft_feature_task → 요청 글 → 슬롯)는 `TaskMaker` 로 묶어 테스트는 가짜로 바꾼다 — 실제 경로는 D2 평가에서.
  - **코딩 템플릿 없는 직군 — 사례형, 명세가 곧 과제 [확정: 2026-11-26 사용자 — 바로 켬].** 과제 종류는 인터뷰를 시작할 때 정한다
    (`interview/task.task_kind_for` — 직군 기본 코딩 템플릿이 있으면 기능형, 없으면 사례형 `incident`, `InterviewState.task_kind`. 이 칸 전에 만든 행은 직군으로).
    예전에는 인터뷰를 다 한 뒤 ⑦ 역량 고르기에서 '템플릿 없음'(422)으로 막혔고, 공개·회사 사례를 고를 때도 기능형 재료를 요구해(`feature_fit`)
    템플릿 없는 직군 공고의 사례 고르기가 422 였다 (2026-11-26 운영 — 담당자가 인터뷰를 버림). 사례형은 공고 경로(`nodes/spec.py`)와 같은 갈래:
    `build_common(task_kind="incident")` → `draft_task`(기준 답안 없는 `incident_block`) → 슬롯. 요청 글(문제 분석 판)은 기능형만 (공고 경로도 같다).
    seed 의 기능형 재료 정리·재현 분석·함정 틀은 코딩 템플릿 기준이라 건너뛰고 확인한 사례를 그대로 재료로 쓴다 (등록 검사 `_registrable` 은 같다).
    승인 검사는 종류별 (사례형은 템플릿·기능형 재료 없이 종류·재료 id 일치), 확인한 사례는 기능형 칸 없이 `co:` 로 등록해 다른 공고의 사례형 과제가
    다시 쓴다. 시작 코드 빌드 요청은 409 ('문서형(사례형) 과제는 시작 코드를 만들지 않습니다'). 남은 것: 승인한 사례형 과제를 지원자에게 내보내는 길
    (지원자용 문서 렌더·API·Wing 의 문서형 과제 화면과 제출)과 `draft_task` 를 인터뷰에서 정리한 사례로 평가하기.
    `data.ml`·`infra.*`·`sw.algorithm` 처럼 기능형 재료는 있고 템플릿만 없는 직군도 지금은 사례형이다 (템플릿이 생기면 기능형).
  - **재료 재현 분석 (2026-11-25, #301).** 인터뷰 사례로 기능형 재료를 새로 만들 때(seed 단계, `interview_feature_seed` 뒤) `analyze_material` 이
    그 재료가 빌드 하네스에서 재현되는지 짚는다 — 공개 재료를 그대로 쓰면 부르지 않는다 (평가로 한 번 본다). 입력은 가명화한 재료 블록(제목·조직·출처 제외, 저장본 검사
    `stored_json`)과 직군 템플릿 정보(`interview/task.template_json` — 템플릿 CURRENT).
    공유 승인된 회사 사례(co:)를 고르면 다시 쓸 때마다 지금 템플릿으로 본다 (2026-11-25 #308 4차 — 이 분기는 분석을 부르지 않아 #311 전에
    등록한 재료를 다시 써도 표시가 없었다. 재현 여부는 템플릿 판에 따라 달라 등록 때 한 번으로는 부족하다). 재료에 등록한 인터뷰의 토큰이 남아 입력은
    `shared_json`(그 재료에 있는 토큰까지 허용, 표시 검사도 같은 집합), 그 전에 등록 규칙(`blocked_findings`)으로 연락처·링크를 다시 보고, 입력 칸은
    등록 규칙의 LLM 입력 칸만(notes 제외). 회당 qwen 한 번. 재현 가능이 '예'가 아니거나, 템플릿에 없는 이름을 쓰거나,
    재료 사유와 분석 사유가 다르면 과제 검토 표시('재료 재현 분석: …')로 남기고 승인을 막지 않는다. 재현 가능 판정이어도 빠진 정보(gaps)가 있으면
    기전과 함께 표시한다 ('재현 가능 판정 · 빠진 정보 확인 필요', 2026-11-25 #308 팩트체크 — yes 판정에 묻힌 의문이 둘: 세션 유지 재료의 '커넥션 하나를
    쥐는가', 떼어 둔 결제 대행 표본의 '외부 결제 API 흉내'. yes 오판은 재료의 사고 대신 처방의 부작용으로 함정이 바뀌어도 빌드가 통과할 수 있다).
    분석이 실패해도 과제는 만들고 고정 문구를 남긴다.
    표시는 `InterviewGeneration.seed_flags` 로 생성 마무리까지 넘겨 과제 review_flags 에 합친다. 프롬프트 CURRENT 가 없으면 건너뛴다.
    코드 `interview/material_analysis.py`, 평가 `eval/interview/run_material_analysis.py` — 기록 `prompts/analyze_material/PROMOTIONS.md`.
  - **보강 질문 (2026-11-25, #308 검사 5 첫 판) [확정: 2026-11-25 사용자 — ⑧ 에서 묻고 ⑦ 로 되돌려 다시 만들기].** 인터뷰 사례의
    재료 분석이 빠진 정보(gaps)를 내면 생성 마무리가 `InterviewSpec.reinforce_questions` 로 최대 셋(`r1`~`r3`, gaps 글 그대로 — 가명화 검사를
    거친 글, 2026-11-26 #318 3단계에서 둘 → 셋 [확정: 사용자 D6])을 ⑧ 에 둔다. 담당자는 `POST /interviews/{id}/reinforce`
    `{answers: {r1: "…", r2: null}, revision}` 로 답한다 — null·빈 글은 '모름', 모든 질문에 답이나 모름.
    #318 3단계부터 질문에 종류(`kind`)가 있다: `design`(함정 틀 검사 2 — 업무 요구를 못 지킬 수 있는 허용 설계를 정답에서 뺄지, `design`
    에 재료 설계 원문·`choices` 에 '뺀다'·'남긴다')이 먼저, 그다음 `gap`(빠진 정보 — 틀 사유의 재현 근거(검사 1) → 틀 빈칸 → 재료 분석 빈칸 순).
    설계 질문은 '뺀다'·'남긴다'로 시작하는 답만 코드가 읽는다 (`ReinforceAnswer.choice`, 그 밖은 남긴다 + 표시). 허용 설계가 둘뿐이면 빼면
    하나만 남아 그대로는 못 빼므로 '뺀다 — <대신 인정할 설계>' 를 받는다 — 그 글은 문답으로 다음 재료 만들기 입력에 들어간다. 답은 가명화해 `InterviewState.reinforce_answers` 에 두고 과제를 버린 뒤 ⑦ 로 간다(revise common 과 같은
    길). 다음 과제 만들기의 seed 가 문답을 기능형 재료 입력(`interview_feature_seed` 의 인터뷰 글에 덧붙임)과 재료 분석 입력(재료 블록의
    `reinforcement` 칸)에 넣고, 답이 있으면 다시 묻지 않고 '재료 재현 분석: 보강 답 반영 — 답 n개 · 모름 m개' 표시만 남긴다 (한 번만 오간다).
    답하지 않고 승인해도 된다 — 막지 않는다. 사례 확인이 취소되면(`unconfirm` — 사례가 바뀜) 답도 비워 새 재료에 다시 묻는다.
    회사 사례는 물을 담당자가 없어 빠진 정보를 표시로만 둔다. 생성 그래프는 바꾸지 않는다 (⑥ 으로 자동으로 돌아가는 안은 그래프 도중 멈춤이
    필요해 뒤로). 한계: 같은 재료라도 분석 표시가 회마다 흔들려(운영 확인 2026-11-25: 4회 중 3회만 빠진 정보 표시) 질문이 뜨지 않을 수 있다.
  - **함정 틀 (#318, 1~3단계).** 명세를 쓰기 전에 숨길 것·공개할 것·공개 쪽 금지·허용 설계 대조를 정하는 단계 — `docs/design/trap-frame.md`.
    seed 단계에서 재료 분석 다음에 `trap_frame` 프롬프트로 틀을 만들고(인터뷰·회사 사례만, 회사는 `shared_json` 길, 공개 사례는 건너뜀), 코드가 틀 적용 재료
    (`interview/trap_frame.apply_frame`)를 만든다. feature 단계는 틀 적용 재료로 명세 초안을 만들고(숨은 요구·허용 설계를 재료에서 복사하므로 따라 바뀜), 등록하는
    재료(`spec.coding_incident`)는 원 재료 그대로다. 생성을 마칠 때 틀 적용 재료와 틀을 공통 과제 행(`common_task.framed`)에 둬 빌드 계약 단계가 쓴다.
    틀의 판단(허용 설계 충돌·금지 엔티티·근거 빈칸·바꾼 것)은 검토 표시로 보이고 막지 않는다. 프롬프트 CURRENT 가 없으면 단계를 건너뛴다 — 2026-11-26 첫 CURRENT v3 (`prompts/trap_frame/PROMOTIONS.md`).
    3단계 검사 (코드, 표시만): 검사 1 재현 근거(템플릿 실패 사유 성립 조건의 조절값 ∪ 재료 harness·분석 갈림 조절값 → 빈칸이면 표시·보강 질문),
    검사 2 설계 질문(위 보강 질문 `design` — '뺀다'면 다음 과제 만들기에서 틀 적용 재료가 그 설계를 뺀다), 검사 3 공개 중립성(명세 1단계 자료
    본문·추가 요구 답·사실에서 틀의 금지 낱말과 금지 엔티티의 저장 꼴 — `interview/frame_leaks.py`, 2단계 자료는 보지 않음). 검사 3 은 과제 글에서
    다시 계산하는 표시라 `InterviewSpec.trap_frame` 에 틀을 두고 담당자가 글을 고칠 때마다 다시 계산한다.
  - **보이는 글 검사(결정적).** 과제 JSON 전체에서 채점·승인용 칸(유지할 구조·함정·관찰·행동 기준·숨김 수용 기준·허용 설계·id)만 빼고
    전부 본다 — 확장 슬롯·2단계·면접 확인 질문 포함, 새 칸은 기본 검사 대상. 짚은 질문의 답(지원자가 정확히 물으면 그대로 준다)도 본다.
    기준 답안 조각(공백·문장부호 빼고 14자)이 있으면 '기준 답안 누설', 가명화 토큰이 남으면 '토큰 노출' 표시 — 공통 과제는 지원자에게
    그대로 나가고 토큰을 되돌리는 단계가 없다. 두 표시는 글이 바뀔 때마다 다시 계산한다. 답할 범위 초안은 자료 id·기준 답안 복사·길이
    초과면 한 번 더 받고, 두 번 다 걸리면 503 (담당자가 직접 적는다).
  - **답 초안 입력 형식 검사(결정적).** 답할 범위 초안은 과제 글 일부(`TARGETED_TASK_FIELDS` — 상황·요구·사실·추가 요구·자료)와 숨은 조건을
    LLM 에 다시 보내고, 보내기 전에 칸마다 가명화 출력 검사(`derived` — 연락처·링크 형식, 대응표에 없는 토큰)를 한다. 생성한 과제 글은 이 검사를
    거치지 않고 저장되므로 LLM 이 예시 값으로 지어 쓴 URL·이메일·타임스탬프(10자리 숫자가 휴대전화 형식에 걸림)가 남으면 같은 글을 매번
    거절했다(2026-11-26, 503 '다시 시도'). 같은 칸·같은 판정으로 '답 초안 입력 형식' 표시를 다시 계산하고(생성 마무리는 짚은 질문까지 넘긴다),
    초안 요청은 LLM 을 부르기 전에 422 와 칸 경로로 알린다. 승인은 막지 않는다 — 입력이 가명화돼 있어 지어낸 예시 값이고, 토큰 표시와 같은 급.
    확장 슬롯·2단계 자료의 예시 값은 다시 LLM 에 가지 않아 표시하지 않는다. 운영 공통 과제 32건 중 11건의 보이는 글에 이 형식이 있었고
    (url 24·email 6·휴대전화 형식 4 — 전부 타임스탬프나 줄바꿈을 사이에 둔 숫자), 초안 입력 칸에 있던 것은 3건.
  - **사례 표시.** 생성기는 `co:` 사례에 '공유 승인된 회사 사례' 표시를 붙이므로 공통 과제 자신의 표시를 '채용담당자 인터뷰 사례(공유 승인 전)'로 바꾼다.
  - **오류.** 시작 전 검증(역량·확인한 사례·준비된 프롬프트)은 요청에서 바로 422·409·503. 생성이 시작된 뒤의 실패(근거 부족·역량 누락·모델 출력을
    쓰지 못함)는 생성 표시의 고정 문구 사유로 남는다 (#280 — 아래 '과제 만들기 실행'). 고친 글의 형식 오류는 칸 위치만 알린다(입력 글을 싣지 않는다).
    실패하면 초안을 저장하지 않는다.
  - **고치기.** 담당자가 고친 과제·질문은 바뀐 글만 가명화한다(`pseudonymize_changes` — 목록은 id 로 짝짓고 새 항목·새 키는 전부).
    공통 과제의 뼈대(트랙·유형·측정 역량·사례·기술 환경·확장 슬롯 구성)는 고정, 행동 기준은 비울 수 없고 평가 기준은 다시 만든다.
    자료·숨은 조건이 그대로면 담당자가 다듬은 질문·정한 답을 두고, 바뀌면 질문을 다시 만든다. 질문을 고치면 짚은 질문의 답은 지운다(의도 —
    답은 `/answers` 로만 넣어 누설 검사를 거친다). 같은 역량을 다시 고르면 만든 과제를 지우지 않는다.
  - **회사 사례 등록 검사(D2b 보완).** 기능형 재료에 연락처·링크가 있으면 과제를 만들 때 다시 받는다(503) — 승인 때 등록이 막히지 않게.
    확인한 사례 쪽 칸이면 다시 받아도 같으므로 사례를 고치라고 한다(422).

- **D2b 승인 (#266).** 위 §2 를 구현했다 — `graph/interview_approval.py`, 확정은 `interview/approval.py`·`InterviewService.finalize_approval`.

    가명화한 대화(행)는 남기지만, 삭제는 행째 지워 목록·상세(404)에서도 사라진다. 진행 중인 인터뷰는 같은 잠금 안에서 폐기 정리를 먼저 한다.

    정리가 실패하면 500 `interview_delete_failed` 이고 행이 남아 다시 지울 수 있다 (폐기 때 실패했을 수 있어 다시 지운다, 개인정보 점검 M3).

  - **한계 (privacy-auditor)**
    - 회사 경계는 사람이 입력한 공고 회사를 믿는다 — 인증 전에는 다른 회사 이름을 적은 공고로 그 회사의 공유 사례 목록·본문을 볼 수 있다(위 「인증 뒤 회사 판별」 [미정]과 같은 위험, 이 목록이 읽기 면을 하나 더한다).
    - 다른 인터뷰에서 온 회사 사례에는 그 인터뷰의 가명화 토큰(`[PERSON_1]` 등)이 있을 수 있다. 이 인터뷰의 대응표와 다른 사람을 가리키므로 되돌리지 않는다(되돌리는 기능도 없다).
      지원자에게 보이는 글에 남으면 '토큰 노출' 표시가 승인자에게 보인다. 이 토큰이 든 글로 답할 범위 초안을 부르면 '인터뷰에 없는 토큰'으로 거절될 수 있다 — 담당자가 직접 적는다.
    - 인터뷰 목록 `GET /interviews` (2026-11-20 — Wing 이 다른 브라우저·담당자의 인터뷰를 보게): 목록에는 공고 메타데이터·단계·시각·승인자만
      싣지만, 목록에서 얻은 인터뷰 id 로 상세(`GET /interviews/{id}`)를 열면 담당자 원문 임시 저장(최대 하루)·가명화한 대화·기준 답안이 보인다.
      인증 전 보호막은 nginx Basic 인증뿐이라, 회사 없이 전부 보는 것은 막고 `company` 를 필수로 했다 [확정: 2026-11-20 사용자] — 회사
      이름은 짐작할 수 있으므로 완전한 경계는 아니다. 목록·상세를 회사·계정 단위로 제한하는 것은 인증 뒤 [미정].
    - 회사 사례의 기능형 재료(feature)는 원래 인터뷰의 기준 답안으로 만든 것이라 숨은 요구·인정 설계에 그 내용이 들어 있다 — 과제 재료라 의도한 것이고, 기준 답안 문장 자체(known_incident_cases)는 싣지 않는다.

### 결정 4 — 인터뷰 내용 저장 [확정: 2026-11-19 사용자 "1,2,3 진행해줘"]

- 담당자 글(대화·양식·고친 사례)과 맥락에 넣는 공고 줄은 `nodes/pseudonymize/interview.py` 가 지원서와 같은 탐지기(Kiwi 포함)로 가명화한 뒤에만
  LLM 으로 간다. 비밀 값(키·비밀번호·토큰)은 가명화하지 않고 거절한다. 회사 이름은 표기 변형까지 ORG 토큰으로 먼저 넣는다.
  LLM 이 쓴 글(질문·사례 초안·기준 답안)은 저장 전에 패턴 탐지기·위조 토큰 검사.
- **DB 에는 가명화한 글만.** 이름 대응표는 `data/interviews/<id>/mapping.json`(700/600)에만 두고 과제 승인·인터뷰 폐기 때 지운다.
  승인·폐기 없이 마지막 수정 뒤 **30일**(`INTERVIEW_MAPPING_TTL_DAYS`) 지나면 폐기로 본다 [30일은 Claude 제안 — 사용자가 세부 선택을 맡김].
- **단계별 임시 저장(원문)은 처음 쓴 때부터 최대 하루**(`INTERVIEW_DRAFT_TTL_HOURS=24`) — 다른 단계를 저장해도 연장되지 않고, 하루가 지난 뒤 저장하면
  남은 것을 버리고 새로 시작한다. 그 단계를 제출하면 바로 지운다. 임시 저장은 30일 방치 판정의 활동으로 세지 않는다 (열어 둔 화면의 자동 저장이
  대응표를 무기한 살리지 않게). 정리는 앱 안 주기 작업(`INTERVIEW_SWEEP_MINUTES`).
- **원문으로 남기는 예외:** 공고의 회사명·직무명(`company`·`title` — 공고 표에 이미 원문으로 있는 공개 정보)과 사례 확인자 이름(`reviewer`, 선택 —
  `approved_by`·`decided_by` 같은 직원 식별자, 인증이 붙으면 계정 id 로 바꾼다). LLM 입력에는 넣지 않는다.
- 비밀 값 거절은 붙여 넣은 자격 증명 모양만 본다(설정 `key: 값`·환경 변수·Bearer·AWS·GitHub·Slack·JWT·URL 안 계정) — 평범한 장애 설명('비밀번호는 해시로 저장')은 막지 않는다.
- 담당자가 화면의 가명화 글을 고쳐 보내면 대응표에 있는 토큰은 살린다. 한계: 진짜 토큰 바로 뒤에 붙여 쓴 라벨 값('담당자: [PERSON_1] 실명')은
  라벨 탐지기가 건너뛸 수 있다 — 담당자는 신뢰하는 사용자이고, 실수로 넣은 개인정보를 막는 것이 목표다.

### 회사 사례로 넣는 시점 [확정: 2026-11-19 사용자]

과제를 승인할 때 그 순간의 사례를 `co:` 로 등록하고 공유 승인을 기다린다 (D2). ⑥ 사례·답안 확인 단계에 '모음에 보태기' 버튼은 두지 않는다.
그 공고 자신은 사례를 모음에서 고르지 않고 직접 쓰므로 공유 승인과 무관하다 — 공유 승인은 다른 공고가 쓰기 위한 것이다.

## 과제 만들기 실행 — 명세 생성 과정과 같은 방식 (#280) [확정: 2026-11-20 사용자]

과제 만들기는 LLM 을 여러 번 불러 10분 넘게 걸린다 (2026-11-20 운영 첫 생성 11분 35초 — 기능형 초안의 형식 오류 재시도가 62%).
요청 하나로 끝까지 돌리면 새로고침하면 진행이 사라진 것처럼 보이고, nginx `/task-api/` 600초에 504 가 났다 (서버는 계속 돌아 저장).
그래서 명세 실행처럼 백그라운드 그래프로 돌리고 화면은 상태를 폴링한다. 그래프·판정 규칙은 pipeline-graph 스킬 '채용담당자 인터뷰 과제 만들기'.

- **단계:** `seed` 재료 정리(인터뷰 사례만 LLM) → `feature` 기능형 초안 → `request` 요청 글 → `slots` 확장 슬롯 → `finish` 질문·저장.
  확장 슬롯은 공고 전체 역량·근거로 만든다 — 공통 과제는 ⑦ 에서 고른 역량, 슬롯은 공통 과제가 다루지 않은 역량을 먼저 확인한다 [확정: 2026-11-26 사용자 — 설계 검사 #332 S-F18. 예전에는 고른 역량만 넘겨 그 규칙이 성립하지 않았다]. 반려 사유·팀 맥락(수정 요청)은 세 생성기 모두에 넘긴다 (#332 S-F17).
- **상태:** `InterviewState.generation` = thread·시작 시각·고른 역량·실패 사유 + 단계 산출물(이어서 할 때 읽는다, 가명화한 글만). 생성 중·실패·중단일
  때만 있고 과제를 저장하면 비운다. 체크포인트에는 id 만 둔다.
- **이어서 하기:** 실패하거나 서버 재시작·배포로 끊기면 그 단계부터 같은 thread 로 — 끝난 단계는 다시 하지 않는다. 역량을 다시 고르거나 다른 저장을
  하면 그 생성은 버리고 처음부터.

### API (화면 계약)

| 메서드 | 경로 | 동작 |
|---|---|---|
| `POST` | `/interviews/{id}/generate` | `{revision, competency_ids}` → 검증 뒤 **202** + 인터뷰(`generation.status=running`). 과제는 응답에 없다. 검증 오류는 바로 422·409·503 |
| `GET` | `/interviews/{id}/generation` | 폴링용 `{status, current_node, started_at, reason, revision}`. `status` = `running`·`failed`·`interrupted`·`idle`(만드는 중이 아님 → 인터뷰를 다시 읽는다). `current_node` = 도는 중이면 지금 단계, 실패·중단이면 이어서 할 단계 |
| `POST` | `/interviews/{id}/generation/resume` | `{revision}` → 실패·중단한 단계부터 이어서, **202** + 인터뷰. 도는 중이거나 이을 단계가 없으면 409 |
| `GET` | `/interviews/{id}` | `generation` = `null`(만드는 중이 아님) 또는 `{status, thread_id, started_at, competency_ids, reason}` — 단계 산출물은 싣지 않는다 |

- 생성 중에는 그 인터뷰의 상태 변경(다시 만들기·역량 선택·답·수정 요청·폐기·삭제·승인 대기·결정)이 409 `interview_generating`. **임시 저장
  (`PATCH …/drafts`)만 된다.**
- 생성은 단계마다 저장하므로 `revision` 이 계속 오른다 — 다음 요청에는 마지막 폴링·인터뷰의 `revision` 을 쓴다.
- 화면(admin-fe, #280 C): 202 를 받으면 진행 화면(단계 목록·걸린 시간 — 명세의 `RunPipeline` 재사용), 2.5초 폴링(`useRunProgress` 처럼 탭이 숨으면 쉼),
  `running` 이 끝나면 인터뷰를 다시 읽는다. 화면을 열 때 `generation.status=running` 이면 바로 진행 화면 — 새로고침 문제의 핵심. `failed` 는 사유,
  `interrupted` 는 '서버가 다시 시작돼 멈춤' + 이어서 하기·역량 다시 고르기. 폴링도 기존 Task API 클라이언트(`Authorization` 직접,
  `credentials: 'omit'`) — EventSource 는 헤더를 못 넣는다.
