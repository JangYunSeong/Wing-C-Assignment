CURRENT 가 아닌 버전·평가
- **v1 스모크** (2026-11-07, premium gpt-4.1, 2회, `…-plan-contract-gpt41`): 결정적 검사는 2/2 통과였지만 손 예시와 견주면 쓸 수 없는 계약.
  - 상황·요구에 나온 기존 API(`PATCH /deliveries/{id}/status`)가 빠짐. 공개 요구 r4("기존 API 형식 유지")를 조회 API 에 잘못 연결했고, 요청자 헤더도 조회 API 에 붙임.
  - 자료에 있는 선택 운영 값(연결 대기 5000·스레드 32)을 생략 — 채점 환경이 지원자가 본 조건과 달라진다.
  - 목록 응답 항목 모양을 적을 방법이 없음 (`logs: array`).
  - → 결정적 검사를 보탬 (`starter/contract.py`): 명세·공개 테스트·숨은 케이스에 나온 `METHOD /path` 가 계약에 있어야 함, 자료에서 뽑히는 운영 값은 HiddenPlan 에 있어야 함, 응답 `returns`(엔티티 id·목록 `m1[]`)가 계약 엔티티를 가리켜야 함. 새 검사로 v1 결과를 다시 보면 문제 4건.
  - 비용 $0.034 (2회), 회당 약 7초.
- **v2** — v1 + 기존 API·엔티티도 계약에, 자료의 운영 값은 모두, 응답 `returns`, 요청자 같은 입력은 그 값을 받는 API 에, 테스트·케이스는 계약의 API 만.
  스모크 (2026-11-07, premium gpt-4.1, 2회, `…-plan-contract-gpt41-v2`): 2/2 첫 답에서 통과(새 검사 포함), 두 회차 구조 같음.
  - 손 예시와 같은 것: `PATCH /deliveries/{id}/status`(요청자 헤더 `X-Actor`·본문 `status`·200/404), 배송 건별 감사 기록 조회(목록 `returns: m2[]`),
    감사 필드의 뜻(요청자·시각·이전 상태·요청 상태·결과), HiddenPlan 운영 값 4개 모두 손 예시 하네스 값(풀 8·대기 5000·스레드 32·동시 32),
    숨은 케이스 h1 → `pool_acquire_timeout`(PATCH 32건 동시)·h2 → `rollback_left_success`(저장 단계 오류 주입).
  - 다른 것 (계약이 정하면 되는 선택): 규칙 위반 400(손 예시 409), 조회 경로 `/audit-logs`(손 예시 `/audits`), 필드 이름(`requestedAt`·`previousStatus`·`requestedStatus` ↔ `createdAt`·`fromStatus`·`toStatus`),
    `trackingNo` 없음. 2회차는 요구에 없는 `limit` 쿼리를 더함 — refs(r3)를 달아 결정적 검사로는 못 잡는 작은 범위 넘침.
  - 비용 $0.044 (2회), 회당 약 9초.

## v3 (2026-11-07, CURRENT — 위 표)

계약 스키마가 바뀐다 (`SeedRule` rows·groups, `HiddenCase.data`) — v1·v2 출력은 새 스키마를 통과하지 못하므로 v3 와 CURRENT 변경을 같은 PR 에 둔다.
입력 `PlanContractInputV3`(+ `seed_rules`: 검사와 같은 값 — 지원자 몫 작은 id 10행, 버스트 행 = concurrency × bursts). v1·v2 는 노드가 그 버전의 입력 모델로 줄여 준다 (`for_prompt`).

스모크 (premium gpt-4.1, 2회씩, `…-plan-contract-gpt41-v3*`, 합계 $0.25):
- `v3` ($0.100): 2/2 실패. ① **검사 오탐** — 공개 테스트·숨은 케이스 글의 구체 id(`PATCH /deliveries/1/status`)를 계약의 `{id}` 와 못 맞춤 → `_api_refs` 를 경로 변수 자리 = 아무 한 마디로 고침.
  ② 시드 rows = 96 + 10 으로 hc2 행을 빠뜨림, 재요청("늘린다")에도 또 1행 모자람 → 필요한 행 수를 정확히 적는 문제 문장.
- `v3b` ($0.098): 2/2 실패. 버스트 행을 32·42·50 으로 씀 — 재요청에 "concurrency(32) × bursts(3) = 96" 을 적어 줘도 32. 처음에 비어 있는 감사 기록 엔티티에 data 를 붙임(재요청에선 rows 0 으로 스키마 위반).
  → **곱·합은 LLM 에 맡기지 않고 코드가 맞춘다** (`seed_rows.fit_seed`: 버스트 행 = 곱, 빈 엔티티 data 뺌, 모자란 시드는 처음 값이 같은 끝 범위를 늘리거나 범위 덧붙임 — 바꾼 것은 `PlanResult.adjustments` 로 승인 화면에).
- `v3c` ($0.048): **2/2 첫 답 통과** (재요청 0). 코드가 맞춘 것: 버스트 32 → 96(2/2), 시드 42 → 138 · 150행. 배정 예: hc1 id 55~150(96행, 버스트, READY) · hc2 id 43~54.
  API·운영 값은 v2 와 같은 구조 (손 예시와 다른 점도 v2 와 같음: `/audit-logs` ↔ `/audits`, 규칙 위반 400 ↔ 409, 필드 이름). 숨은 케이스 글에 LLM 이 적은 id(11~42 등)는 배정 범위와 다름 → 숨은 테스트 입력에 "배정 범위가 우선" 표시.

생성 스모크 (v3c 계약 `contract-1`, gpt-4.1, `…-generate-gpt41-v3c`, $0.13): 생성기 4종 1회 호출로 정적 검사 통과, 모두 컴파일, 시작 코드 기존 테스트 통과, 행 부족·없는 id 실패 0.
- hc1(동시 32×3): 흔한 구현은 의도한 사유 `pool_acquire_timeout` 로 실패(32/32), 허용 구현 d1 은 **통과** — 숨은 테스트가 둘을 가른 첫 실행.
- hc2(저장 실패 주입): 둘 다 실패 — 숨은 테스트가 테이블 이름을 경로에서 짐작(`deliveries`, 실제 `delivery`)해 주입이 안 걸림. 정규식만 고쳐 다시 빌드(LLM 없음)하니 흔한 구현은 의도한 사유 `rollback_left_success` 로 실패,
  d1 참조 구현은 실패 기록을 못 남김(`record_missing` — 저장이 커밋 때 일어나 catch 를 지나고, 커밋 뒤 콜백의 기록은 커밋되지 않음: 설계가 적은 함정에 참조 구현이 빠짐). 다음: 테이블 이름을 템플릿 규칙으로 계약에 (언어별), 6단계 수리 배정.

## v4 (2026-11-07, CURRENT — 위 표)

v3 계약의 수리 루프에서 계약 모호: 명세 r1 "상태 변경 **요청**마다 감사 기록(… 이전 상태 …)" · 수용 기준은 성공·규칙 위반만(404 언급 없음) 인데 계약이 `beforeStatus` 를 필수로 둠
→ 흔한 구현·허용 구현 모두 없는 배송 건(404) 요청을 기록하다 같은 not-null 오류로 '없음' 기존 테스트를 깸. 손 예시는 404 요청도 기록하고 `from_status` 를 null 허용.
v4 = v3 + "실패한 요청도 기록하는 엔티티는 실패 경로마다 기록 필드 값이 있는지 보고, 없으면 선택(required false) + 언제 비는지 제약에, 명세가 기록하지 않는다고 할 때만 기록하지 않음을 응답 설명에".

- 계약 스모크 (gpt-4.1, 2회, `…-plan-contract-gpt41-v4`, $0.049): 2/2 첫 답 통과. 2/2 이전 상태 필드를 **선택**으로 —
  run 1 `beforeStatus` "배송 건이 없으면 null" (의도대로), run 2 `prevStatus` "처음 변경이면 null" (선택이라 충돌은 풀리지만 이유가 틀림).
  run 1 은 결과 값에 `RULE_VIOLATION`·`NOT_FOUND` 를 더함(명세보다 세분), '기록하지 않음' 문구를 GET 404 에 붙임(무해하나 자리 틀림).
- 수리 루프 1회 (run 1 계약, gen_starter v2, 허용 설계 1, `…-loop-contract-v4`, $0.177): **기존 테스트를 깬 참조 구현 0** (계약 모호 해소).
  흔한 구현은 hc1·hc2 모두 의도한 사유로 실패. 허용 구현 d1 은 hc2 에서 `record_missing` (커밋 때 나는 오류를 트랜잭션 메서드 안 catch 로 잡으려다 놓침 — 템플릿 스택 조건에 없던 것, 보탬),
  다시 만들어도 같음 → 당시 배정 규칙이 숨은 테스트를 의심해 다시 만들었고 새 숨은 테스트가 컴파일 안 됨 → `failed`. 배정 규칙 고침 (흔한 구현이 의도한 사유로 잡히면 테스트는 그대로, 사람 확인).
