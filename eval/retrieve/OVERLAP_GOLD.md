# 대조 겹침 정답 만들기 — 절차와 판정 기준

대조(compare) 겹침을 재는 정답(gold)을 만드는 절차. 정답·검토표·판정 결과는 전부 git 밖 `data/eval/overlap/` 에만 둔다
(지원자 데이터 — 불변식 1). 이 문서의 예시는 모두 가상이다.

## 절차

1. **실행** — `run_overlap` 으로 이력서마다 주장·검색 상위 30·선택·판정 입력을 저장한다.
   이력서마다 공고가 다르면 `--pairs <pairs.json>` (resume·split·posting_id 만 읽음).
2. **판정자 1** — `judge_overlap` CURRENT 로 판정 (외부 API 는 가명화본만 — 불변식 2).
3. **판정자 2** — 다른 계열 판정자. API 모델이면 `run_judge_consensus` 가 직접 부르고,
   Claude 는 **Claude Code 에이전트로만** 판정한다 (Anthropic API 사용 금지):
   `judge_packets` 로 패킷을 만들고, 새로 띄운 에이전트가 `packets/` 만 읽고 `out/<이력서>.json` 을 쓴다.
   에이전트에게는 다른 판정 결과·작성 의도(매니페스트) 파일을 열지 말라고 명시한다.
4. **합의** — `run_judge_consensus --second-dir …` : 두 판정이 같은 칸은 합의 정답, 다른 칸은 `disagreements.md`.
5. **사람 검토** — 불일치만 사람이 정한다 (아래 기준). 표의 `최종`·`확신`·`메모` 를 채워 `disagreements_reviewed.md` 로 저장.
   검토표에는 판정자 이름과 시스템 예측을 넣지 않는다 (검토자 쏠림 방지).
6. **고정** — `overlap_gold build` 로 `gold.json` 을 만들고 `overlap_gold score` (또는 `run_topdown`) 로 채점한다.
   확신 '하' 를 뺀 수치(`--exclude-low`)도 함께 본다.

held-out(test) 이력서는 정답만 만들고 지표는 결정할 때 한 번만 낸다 (`--metric-splits`, `--report-splits` 기본 dev).

## 판정 기준 (사람 검토·판정자 지시 공통)

판단 순서 — 행마다:

1. 관련 내용이 전혀 없으면 **none**.
2. 기술·도구 이름만 있고 그걸로 한 일이 없으면 **mention** (목표·배경 설명만 있어도 mention).
3. 이 문장만 보고 면접관이 "이 역량을 해봤네" 라고 할 수 있으면 **action**, 가까운 일의 일부·주변만이면 **related**.

역량 유형별 규칙:

| 상황 | 판정 | 예 (가상) |
|---|---|---|
| 역량 이름에 도구가 있음 (Kafka, Elasticsearch, Spring) | 그 도구나 같은 종류 제품을 다뤘으면 action, 다른 방식으로 비슷한 일이면 related | "Kafka 운영" ← RabbitMQ 로 메시지 처리 구현: related |
| **포괄 역량** (서버 애플리케이션 개발, 응용 SW 구현, 업무 IT 시스템 개발·운영, SW 아키텍처·구조 설계, 웹 애플리케이션 개발·운영 …) | 구체 행동이 그 범주에 분명히 들어가면 **action**. 더 구체적인 역량이 같은 문장을 설명해도 포괄 역량을 related 로 낮추지 않는다 | "주문 조회 API 구현" → 서버 애플리케이션 개발: action |
| 환경 구성 ↔ 서비스 개발·배포 | 테스트용 환경만 구성했으면 related, 서비스를 만들거나 배포했으면 action | Docker 로 테스트 DB 띄움 → 컨테이너 서비스 배포: related |
| 단어만 같음 ("파이프라인", "검색", "운영") | 하는 일이 다르면 none, 일부 겹치면 related | CI 배포 파이프라인 → 데이터 파이프라인: none |
| 결과·지표만 있음 | 그 결과를 낸 행동이 문장에 함께 있으면 그 행동으로 판단 | "캐싱 적용으로 응답 4초→1초" → 성능 튜닝: action |
| AI 계열 역량끼리 (RAG, 에이전트, 모델 서비스 적용, AX) | 역량 이름이 가리키는 일을 했는지로 판단 | RAG 구축 → "AI 에이전트 개발": 에이전트·툴 호출이 없으면 none 또는 related |

포괄 역량 기준은 [확정: 2026-11-04] — 가상 held-out 검토에서 "구체 역량이 설명하면 포괄 역량은 related 상한" 으로
판정한 행이 사용자 이력서 정답·두 판정자 합의(action)와 엇갈려, 공고가 포괄 역량을 요구할 때 구체 행동을
보인 것으로 친다(action)로 통일했다. 다른 이유(예: "개발·운영" 인데 화면만 만듦)로 낮추는 것은 그대로 허용.

일관성:

- 같은 문장이 여러 역량의 근거로 나오면 같은 기준을 똑같이 적용한다.
- 애매하면 낮은 쪽, 확신 '하'.
- 지원자가 그 역량을 실제로 가졌는지가 아니라, **이력서 문장이 그 역량을 보여주는지**로 판단한다.
